# 画像分類データ

<!--en:58c1a818-->
ソフトマックス回帰（softmax regression）を訓練してテストするには、弱いモデルと強いモデルを見分けられるほど十分に豊かでありながら、対話型ノートブック内で数秒のうちに訓練できるほどコンパクトな画像分類（image classification）ベンチマークが必要である。古典的な手書き数字の [MNIST](https://en.wikipedia.org/wiki/MNIST_database) :cite:`LeCun.Bottou.Bengio.ea.1998`（$70{,}000$ 枚のグレースケール $28 \times 28$ 画像、10 個の数字クラス）は 1990 年代には画期的なベンチマークであったが、今日ではごく単純なモデルでさえ $97\%$ の正解率（accuracy）を超え、畳み込みニューラルネットワークは $99\%$ を上回るため、アーキテクチャの改善効果を確認する余地がほとんど残っていない。その対極にある ImageNet :cite:`Deng.Dong.Socher.ea.2009`（$1.2$ 百万枚のカラー写真、$1{,}000$ カテゴリ）では、実行ごとに数時間の GPU 計算を要する。

<!--en:8e26b233-->
*Fashion-MNIST* :cite:`Xiao.Rasul.Vollgraf.2017` はちょうど良いバランスを備えている。MNIST と同じ規模（訓練用 $60{,}000$ 枚、テスト用 $10{,}000$ 枚からなるサイズ $28 \times 28$ のグレースケール画像で、均等な $10$ クラス）を保ちつつ、数字を衣料品（T シャツ、ズボン、プルオーバー、ドレス、コート、サンダル、シャツ、スニーカー、バッグ、アンクルブーツ）に置き換えている。Fashion-MNIST では、線形ソフトマックス回帰の正解率は約 $83\%$ に達する一方、畳み込みネットワークは $90\%$ を超える。本節では、以降のいくつかの章にわたって画像分類器にデータを供給する `FashionMNIST(d2l.DataModule)` クラスを構築する。

<!--en:b17ecc77-->
## データセットの読み込み

<!--en:176884aa-->
Fashion-MNIST には訓練画像 $6{,}000$ 枚とテスト画像 $1{,}000$ 枚が $10$ 個の衣類カテゴリそれぞれに含まれており（合計で $60{,}000$ 枚と $10{,}000$ 枚）、8 ビット符号なし整数として $[0, 255]$ の範囲で格納されている（$0$ が暗い背景を表す）。オブジェクト指向設計（:numref:`sec_oo-design`）に従い、`FashionMNIST` は `d2l.DataModule` を継承し、`batch_size` および任意の空間サイズ変更タプル `resize`（デフォルトは $(28, 28)$）を受け取る。

<!--en:87d23308-->
`torchvision.datasets.FashionMNIST` はデータセットをダウンロードし、各分割のすべての画像を 1 つの `uint8` テンソルに保持する。以下で定義するデータローダはこのテンソルを読み込み、ミニバッチ単位でまとめて変換する。`transforms.Compose` パイプラインは 1 枚の画像をリサイズし、そのピクセル輝度を float32 テンソルとして $[0, 1]$ の範囲にスケーリングする。この変換は、`data.train[i]` のようにデータセットへ直接インデックスアクセスするときや、`data.train` を独自のローダに渡すときに適用される。

<!--en:ec960caa-->
Gluon 組み込みの Fashion-MNIST ヘルパーは非標準の訓練・テスト分割を使用するため、`FashionMNIST.read` は公式の gzip 圧縮された IDX バイトファイルを直接ダウンロードして解析し（16 バイトの画像ヘッダと 8 バイトのラベルヘッダをスキップする）、`to_dataset` がピクセル値を float32 で $[0, 1]$ の範囲にスケーリングする。

<!--en:39dafe97-->
`tf.keras.datasets.fashion_mnist.load_data()` は、公式の訓練分割とテスト分割を `(images, labels)` の NumPy 配列として返す。

<!--en:34e29cd6-->
データセットをインスタンス化し、各分割のサイズを確認しよう。

<!--en:6bf891a9-->
Fashion-MNIST には 2 つの分割しか用意されていないため、訓練中は $10{,}000$ 枚のテスト分割を検証セット（validation set）として使用する（テストセットで繰り返し評価することの統計的影響については :numref:`chap_classification_generalization` で分析する）。さらに、`text_labels` を追加し、整数のクラスインデックス $0, \ldots, 9$ を人間が読める衣類名に変換できるようにしよう。

## ミニバッチの読み込み

<!--en:246f68c9-->
深層学習フレームワークでは、サイズ $n$ のミニバッチに含まれる、チャネル数 $c$（グレースケールなら $c = 1$、RGB カラーなら $c = 3$）、高さ $h$、幅 $w$ の各画像は、フレームワークに応じて*チャネルファースト*のレイアウト $(n, c, h, w)$ または*チャネルラスト*のレイアウト $(n, h, w, c)$ のいずれかで格納される。

<!--en:78e754d8-->
MXNet は画像をチャネルファーストのレイアウト $(n, c, h, w)$ で格納する。

<!--en:81fbd3bc-->
PyTorch は画像をチャネルファーストのレイアウト $(n, c, h, w)$ で格納する。

<!--en:2becfc30-->
TensorFlow は画像をチャネルラストのレイアウト $(n, h, w, c)$ で格納する。

<!--en:3977e682-->
JAX は画像をチャネルラストのレイアウト $(n, h, w, c)$ で格納する。ここでは `tf.data.Dataset` を軽量なヘルパー `TensorFlowDataLoader` でラップして `.as_numpy_iterator()` と `__len__` を公開し、各エポックで NumPy のミニバッチが直接得られるようにする。

<!--en:8b8388c8-->
次に、`get_dataloader(self, train)` を `FashionMNIST` に追加し、フレームワーク標準のデータローダをラップする。これにより、エポックごとに訓練分割を再シャッフルするとともに、最後の端数のミニバッチ（$60{,}000 = 937 \times 64 + 32$）も保持して、すべての画像がエポックごとに 1 回ずつ処理されるようにする。

<!--en:14da29fe-->
ヘルパー `batchify` は、ローダが各ミニバッチを読み込む際にそれをリサイズする。

<!--en:c7d69d37-->
ヘルパー `batchify` は、ローダが各ミニバッチを読み込む際に、それを float32 で $[0, 1]$ の範囲にスケーリングしてリサイズする。ミニバッチ全体に対する 1 回の演算は画像ごとに個別の演算を繰り返すよりもはるかに低コストであるため、このローダは画像単位の変換を経由しない。

<!--en:bf3b82c3-->
1 つのミニバッチ `(X, y)` を `train_dataloader()` から取得し、単一画像のレイアウトならびにミニバッチ全体のテンソルの形状と dtype を確認しよう。

<!--en:e7d36e8d-->
データ例を束ねてミニバッチにすると、画像の先頭にバッチ軸が追加される。一方、ラベルは画像ごとに 1 つの要素を持つ 1 次元ベクトルとして得られる。

<!--en:c4629ba6-->
ミニバッチあたり $64 \times 28 \times 28 \times 4 \approx 200\textrm{ KB}$（$\sim 190\textrm{ MB}$ で $60{,}000$ 枚の float32 訓練画像すべてに相当）と小さいため、データセット全体が RAM に余裕をもって収まる。それでも、データローダ単体でベンチマークをとること（モデルを接続せずに 1 パス全体の時間を `train_dataloader()` について計測すること）は極めて重要な習慣である。どの訓練エポックも、そのデータパイプラインより速く実行することはできないからである。

<!--en:2683844a-->
## 画像の確認

<!--en:60b66265-->
どのようなモデルを訓練する前にも、必ずラベル付き画像のサンプルを目視で確認すべきである。ラベルのずれ、輝度の反転、あるいは誤ったリシェイプによる画像の崩れは、実行時エラーを起こさないまま訓練を台無しにするからである。そこで、単一チャネルの軸を除去し、テキストラベルをタイトルに添えたグレースケール画像のグリッドを描画する `visualize` メソッドを `FashionMNIST` に追加する。

<!--en:a6c48d84-->
検証ローダが常に決定論的な順序で画像を返すことを利用して、各クラスの最初の 3 枚の検証画像をカテゴリごとに 1 列ずつ表示してみよう。

<!--en:1dc92377-->
ざっと目を通すだけでも、線形分類器が直面する難しさが予見できる。ズボンとバッグは紛れもないシルエットを持ち、サンダル・スニーカー・アンクルブーツは明確な履物のクラスタを形成している。一方、4 つの上半身の衣類（T シャツ、プルオーバー、コート、シャツ）はほぼ同じ箱型の胴体輪郭を共有しており、$28 \times 28$ の解像度ではかろうじて判別できる程度の襟、袖、ボタンのわずかな違いしか見られない。

<!--en:30ac03ff-->
## まとめ

<!--en:4ff99acb-->
Fashion-MNIST は、訓練用 $60{,}000$ 枚およびテスト用 $10{,}000$ 枚のグレースケール $28 \times 28$ 画像を均等な $10$ 個の衣類カテゴリにわたって提供しており、線形モデル（$\sim 83\%$）と畳み込みネットワーク（$>90\%$）の性能差を見分けられるほど豊かでありながら、数秒で訓練できるほど小さい。本節で構築した `FashionMNIST(d2l.DataModule)` パイプラインは、生の `uint8` ピクセルを `float32` で $[0, 1]$ の範囲に再スケーリングし、任意の空間リサイズに対応するとともに、再シャッフルされたミニバッチと整数ラベルを各フレームワーク標準のチャネルレイアウトで供給する。ローダ単体のベンチマークはエポック時間の下界を与え、ラベル付き画像の一覧を目視確認することで、訓練開始前に表面化しない形状やラベルの不整合を発見できる。

- **エポックごとの再シャッフル（`shuffle=train`）：**訓練時はエポックごとに全 $60{,}000$ 個のインデックスを再シャッフルし、検証時は決定論的な順序で反復

[フレームワークのテンソル規約]{.kicker}

<!--en:c59b6981-2-->
単一のグレースケール画像（$c = 1$、$h = 28$、$w = 28$）は 3D テンソルとして格納され、チャネル軸の位置はフレームワークに依存する

- **チャネルラスト $(h, w, c) = (28, 28, 1)$：**このフレームワークはチャネル軸を末尾に配置（ミニバッチでは `NHWC`）

<!--en:ee88cca1-->
- **もう一方の規約：**チャネルファースト $(c, h, w)$（`NCHW`）は各チャネルを 1 枚の連続した平面として格納し、いずれも平坦化すると同じ $784$ 個の特徴量になる

<!--en:45502e6e-->
::: {.slide title="画像とラベルのミニバッチ全体の確認"}

<!--en:250b91a1-->
[4D 画像テンソルと 1D ラベルベクトル]{.kicker}

<!--en:dfc87e63-->
$n = 64$ 枚の画像を束ねると `X` の先頭にバッチ軸が追加され、1D 整数ベクトル `y` と対になる

<!--en:ec5ae56b-->

<!--en:76a108cb-->

[システムのボトルネック分析]{.kicker}

<!--en:0e92e41a-->
ニューラルネットワークを接続する前に、必ず 1 パス全体の時間を `train_dataloader()` 単体で計測する

<!--en:88677add-->
- **エポック時間の厳密な下界：**データ読み込みとモデル実行は生産者・消費者パイプラインをなすため、どの訓練エポックもデータローダ単体より速くはならない

<!--en:531fcaa9-->
::: {.slide title="データパイプラインのボトルネック診断"}

<!--en:4449fc1d-->
[生産者・消費者のオーバーラップ]{.kicker}

<!--en:ade3b69c-->
バックグラウンドの CPU ワーカーがバッチ $b + 1$ を先読みする間に GPU がバッチ $b$ を計算するとき、エポックの実経過時間は次式に従う

<!--en:432b519e-->
- **小さいバッチサイズ（$n = 1$ または $16$）：**バッチごとの Python ディスパッチのオーバーヘッドが支配的となり（`T_load >> T_compute`）、GPU がデータ待ちになる

<!--en:953472f5-->
- **ワーカー数のスケーリング：**`num_workers=0` はステップ間で直列にブロックするが、$T_{\text{load}} < T_{\text{compute}}$ になればワーカーを増やしても高速化は 0 になる

<!--en:55577406-->

[防御的なデータ確認]{.kicker}

<!--en:0ed0c665-->
表面化しないデータバグ（ラベル対応のずれ、空間軸の転置、チャネルの混線）は構文エラーを起こさない。必ず最初にラベル付き画像の一覧を描画する

<!--en:c9708f00-->
- **単一チャネルの除去：**`X` を `(-1, *self.resize)` にリシェイプすることで、長さ $1$ のチャネル軸を `(n, 1, h, w)` または `(n, h, w, 1)` のいずれからも取り除く

[視覚的な誤り予測]{.kicker}

<!--en:b1db23f1-->
各カテゴリの最初の 3 枚の検証画像（クラスごとに 1 列）を表示すると、線形テンプレート分類器が苦戦する箇所がただちにわかる

::: {.slide title="理解度チェック：形状・バッチ・視覚的デバッグ"}

<!--en:26a317d8-->
[理解度チェック]{.kicker}

<!--en:33f6c107-->
`FashionMNIST` パイプラインの理解度を 3 つの実践的な質問で確認しよう

<!--en:b16f38c9-->
1. **ミニバッチ数：**`batch_size=256` に切り替えたとき（§{sec_softmax_scratch}）、1 訓練エポック（$60{,}000$ 枚の画像）では何個のミニバッチが生成され、最後のミニバッチには何枚の画像が含まれるか。

<!--en:0d67d6d5-->
2. **視覚的バグと数値的バグ：**次の 4 つのバグのうち、`data.visualize` の一覧表示で目視によりただちに発覚するのはどれで、見逃されるのはどれか。*(a)* ラベルが $+1$ ずれている、*(b)* 画像が $(h \leftrightarrow w)$ と転置されている、*(c)* ピクセルが未正規化のまま $[0, 255.0]$ にある、*(d)* エポックごとにすべての画像が二重に重複している。

<!--en:1602c854-->
3. **アップサンプリング不変性：**`resize=(32, 32)`（$1{,}024$ ピクセルへの双線形補間 $\mathbf{x}' = \mathbf{A}\mathbf{x}$）を設定した場合、線形ソフトマックス分類器は新たな表現力を獲得するか。

<!--en:074c68ab-->
**解答：** **(1)** $60{,}000 = 234 \times 256 + 96$ より、エポックあたり $235$ ミニバッチとなり、最後のバッチは $96$ 枚である（検証は $39 \times 256 + 16 \to 40$ バッチ）。**(2)** *(a)* と *(b)* は目視で明白である（誤ったタイトル、横向きの衣類）。*(c)* は `imshow` が `[vmin, vmax]` を自動スケーリングするため隠れてしまい、*(d)* は `len(dataloader)` の確認を要する。**(3)** 獲得しない。任意の線形スコア $\mathbf{w}'^\top(\mathbf{A}\mathbf{x}) + b = (\mathbf{A}^\top\mathbf{w}')^\top\mathbf{x} + b$ は、すでに元の $784$ ピクセル上の線形スコアだからである。
