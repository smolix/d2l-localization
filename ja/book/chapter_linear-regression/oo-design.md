# 実装のためのオブジェクト指向設計

<!--en:0b062db3-->
:numref:`sec_linear_scratch` では、生のテンソルから線形回帰を実装し、1 つのモデルと 1 つのデータセットに直接結び付けられた独立な 12 行の `train` 関数で訓練した。今後、多層パーセプトロン（multilayer perceptron）、畳み込みネットワーク（convolutional network）、リカレントネットワーク、Transformer へと進むにあたり、データローダやエポックのループ、評価指標の平均計算、リアルタイムのプロットを毎節書き直していては、新しいアイデアが反復的な定型処理の下に埋もれてしまう。

<!--en:5bbb8438-->
モデリングに集中しつつ、訓練ハーネスのすべての行を見通しよく変更可能な状態に保つため、本書では `d2l` ライブラリを 3 つの明快なオブジェクト指向（object-oriented）の抽象化（:numref:`fig_oo_design`）を中心に構成する。これは PyTorch Lightning のようなフレームワークに着想を得たものである :cite:`Falcon.ea.2019`。

<!--en:2af4f292-->
1. **`Module`（モデル）：**訓練可能なパラメータを保持し、`forward` による順伝播（forward pass）を定義し、`loss` を計算し、`training_step` と `validation_step` を定め、`configure_optimizers` を通じてオプティマイザを返す。

<!--en:c0ea323f-->
2. **`DataModule`（データ）：**データセットのダウンロード、前処理、分割をカプセル化し、イテラブルな `train_dataloader()` と `val_dataloader()` を公開する。

<!--en:7565dc6c-->
3. **`Trainer`（訓練ループ）：**任意の `Module` と任意の `DataModule` を接続し、エポックごとのミニバッチ訓練パスと検証パスを実行し、バッチ間で評価指標を平均化して、リアルタイムの学習曲線（learning curve）を `ProgressBoard` 上にプロットする。

<!--en:d9bad7a4-->
![`d2l` 訓練ハーネスの中核をなす 3 つのクラス。`DataModule` は訓練用と検証用のミニバッチを供給し、`Module` はモデル・損失・オプティマイザを定義し、`Trainer` は訓練ループと検証ループを駆動する。](../img/mdl-linreg-oo-classes.svg)

<!--en:e0ac1db6-->
## ユーティリティ

<!--en:9605999e-->
中核となる 3 つのクラスを構築する前に、ノートブック内の定義を読みやすく自己完結した形に保つ 2 つの小さな Python ユーティリティを導入する。

<!--en:1896af79-->
1. **`@add_to_class(Class)`：**教科書やノートブックにおいて、60 行のクラスを 1 つの巨大なコードブロックとして提示すると、各メソッドが登場するたびに説明するのが難しくなる。デコレータ `@add_to_class(Class)` を使えば、まずクラスの骨格だけを定義しておき、後のコードセルで新しいメソッドを段階的に追加できる。

<!--en:96adce25-->
2. **`HyperParameters`（`save_hyperparameters()`）：**`self.a = a; self.b = b; ...` のような記述をすべての `__init__` メソッドの先頭に書くのは、純粋なボイラープレートである。`HyperParameters` を継承して `self.save_hyperparameters()` を呼び出すと、呼び出し元のフレームが検査され、すべての `__init__` 引数（`ignore` に指定されたものを除く）が `self` の属性として自動的に束縛される。

<!--en:e994fee1-->
簡単なクラス `A` と、すでにインスタンス化されたオブジェクト `a` で試してみよう。

<!--en:edd11414-->
次に、別のセルで新しいメソッド `do` を追加する。Python はメソッドを呼び出し時にクラス上で解決するため、既存のインスタンス `a` からも直ちに `do` を利用できる。

<!--en:54bd4e3f-->
2 つ目の補助クラスは、コンストラクタのボイラープレートを取り除くものである。これがないと、コンストラクタは `self.lr = lr` や `self.batch_size = batch_size` のような反復的な代入で埋め尽くされてしまう。深層学習におけるコンストラクタ引数の大半はハイパーパラメータであるため、`d2l.HyperParameters` を継承して `self.save_hyperparameters()` を呼び出すことで、すべてのコンストラクタ引数（`ignore` に指定されたものを除く）を `self` の属性として自動的に束縛する。内部では Python の `inspect` モジュールを使って呼び出し元のスタックフレームを検査しており、その実装は :numref:`sec_utils` にある。

<!--en:a7b9d20c-->
本節の残りで構築するすべてのクラスは `HyperParameters` を継承する。

<!--en:0281e568-->
## モデル

<!--en:ce374478-->
`Module` クラスは、本書で実装するすべてのモデルの基底クラスである。このクラスは、各フレームワーク固有のニューラルネットワーク用コンテナと `d2l.HyperParameters` の両方を継承する。デフォルトの動作は次のとおりである。

<!--en:7667c9ac-->
- `model(X)` を呼び出すと `model.forward(X)` が実行される。

<!--en:8a22a3a6-->
- `training_step(batch)` は、特徴量 `batch[:-1]` をモデルに通し、予測をラベル `batch[-1]` と比較して、ミニバッチの平均損失を返す（後の章のモデルでは、`'loss'` を含む評価指標の辞書を返す場合もある）。

<!--en:e03db1cb-->
- `validation_step(batch)` は、検証データのミニバッチに対して同じ損失を計算する（なお :numref:`sec_softmax_scratch` では、`Classifier` が `validation_step` をオーバーライドして `'loss'` と `'acc'` の両方を報告する）。

<!--en:29615dca-->
- 補助関数 `as_metrics` は、単一のスカラーまたは辞書の戻り値を評価指標の辞書へと正規化し、`Trainer` が任意の名前付き量を統一的に記録できるようにする。

<!--en:9d0d26c2-->
MXNet では、このコンテナは `nn.Block` である。

<!--en:e5df3e7f-->
PyTorch では、このコンテナは `nn.Module` である。

<!--en:81762897-->
TensorFlow では、このコンテナは `tf.keras.Model` である。

<!--en:1ef8561b-->
JAX では、このコンテナは Flax の `nnx.Module` である。

<!--en:1646ff34-->
慣例として、すべてのミニバッチはタプルであり、末尾の要素がラベルテンソル、それより前の要素がモデルの入力である。`training_step` と `validation_step` はどちらも `*batch[:-1]` をアンパックして `self(...)` に渡し、`batch[-1]` に対する損失を計算して、その結果を単に*返す*だけである（それ自体では出力、プロット、ログ記録を一切行わない）。モデルがトレーナの存在をまったく意識しないようにしているのは意図的な設計上の選択であり、これによりどのようなカスタムループからでも隠れた副作用なしに `Module` を訓練・評価できる。

<!--en:1973420a-->
本章では、各ステップは単一のスカラー、すなわちミニバッチの平均損失を返す。:numref:`sec_softmax_scratch` 以降では、その代わりに評価指標名をミニバッチ平均に対応付ける辞書（常に `'loss'` を含み、`'acc'` などの量も併せ持つ）を返す場合がある。小さな補助関数 `as_metrics` は、単なるスカラーの損失を `{'loss': out}` へと正規化し、トレーナが両者を統一的に扱えるようにする。

<!--en:af9c78fb-->
### Module としての線形回帰

<!--en:8be254f5-->
フレームワークの組み込み層を使う前に `Module` が実際にどう動くかを確認するため、スクラッチ実装した線形回帰のパラメータ $(\mathbf{w}, b)$、順伝播、二乗損失（squared loss）、およびスクラッチ実装の `SGD` 更新器を `LinearRegressionScratch(d2l.Module)` にまとめてみよう。

<!--en:cda42036-->
次に、`forward` と `loss` を追加する。これらは :numref:`sec_linear_scratch` の `linreg` および `squared_loss` と同一であり、モデルインスタンスから `self.w` と `self.b` を読み取るだけである。

<!--en:a6686047-->
続いて、スクラッチ実装したミニバッチ SGD の更新則を再利用可能な `SGD(d2l.HyperParameters)` クラスにまとめ、`LinearRegressionScratch.configure_optimizers` から返すようにする。

<!--en:d89ef5f2-->
最後に、`configure_optimizers` でモデルと `SGD` オプティマイザを結び付ける。

<!--en:69e3dc6d-->
`SGD` には `.data()` が返す基底配列を渡す。誤差逆伝播法（backpropagation）の実行中には、この配列の `.grad` 属性が勾配を受け取る。

<!--en:864d49c6-->
## データ

<!--en:44c6f214-->
基底クラス `DataModule` は、データセットにおいて `Module` に対応するものである。具体的な各データセットのサブクラスは `train_dataloader()` と `val_dataloader()` を実装する（通常はどちらも `get_dataloader(train=True/False)` に処理を委譲する）。

<!--en:618e6ee5-->
:numref:`sec_synthetic-regression-data` で作成した合成回帰データの生成器を `SyntheticRegressionData(d2l.DataModule)` にまとめよう。このクラスはあらかじめ `num_train + num_val` 個の例（デフォルトでは訓練例 1,000 個、検証例 1,000 個）を生成しておくため、`Trainer` は毎エポック終了後に訓練損失（training loss）とホールドアウトされた検証損失（validation loss）の両方を追跡できる。

<!--en:0bf27647-->
### 各エポック用のローダ

<!--en:1be1b249-->
`get_dataloader` の内部では、エポックごとに 1 回反復でき、各エポックの開始時に訓練分割をシャッフルし直す一方で、検証分割は決定論的な順序で読み出すオブジェクトが必要になる。`get_tensorloader` メソッドは、分割されたテンソルからこのオブジェクトを構築する。

<!--en:906a7b29-->
このオブジェクトは、:numref:`sec_linear_scratch` のスライスごとのインデックス順列ロジックを包む `ArrayLoader` クラスとしてスクラッチで記述する。

<!--en:3f5404da-->
`TensorDataset` は先頭の例軸に沿ってテンソルを揃え、`DataLoader` はそれらをミニバッチへとスライスし、`shuffle=True` のときにはパスごとに自動でシャッフルし直す。

<!--en:f3d180ce-->
`from_tensor_slices` は複数のテンソル間で各例を対応付け、`shuffle` はバッファからサンプリングし（一様な訓練シャッフルには分割全体のサイズを使い、検証の順序を保つには `1` を使う）、`batch` はそれらをミニバッチにまとめる。

<!--en:8a44c864-->
`get_tensorloader` は指定された分割をスライスし、テンソルを `ArrayLoader` で包む。

<!--en:0c2236b3-->
`get_tensorloader` は指定された分割をスライスし、テンソルを `ArrayLoader` で包む（1 サンプルずつミニバッチを組み立てる Gluon の `DataLoader` とは異なり、`ArrayLoader` はテンソルあたり 1 回のベクトル化されたスライスでバッチ全体を取得する）。

<!--en:2fb4a44d-->
これで `SyntheticRegressionData.get_dataloader` はわずか 2 行になり、訓練分割または検証分割のいずれかをスライスして `get_tensorloader` に委譲するだけである。

<!--en:0e6b5e14-->
この合成データセットをインスタンス化し、先ほど単純なジェネレータがつまずいた 2 パスのテストをもう一度試してみよう。

<!--en:6b833440-->
今度はどちらのパスでも全 $32$ 個のミニバッチ（末尾の $8$ 例の端数を含む）が得られ、パスごとに新しいランダムな順序で始まる。さらに都合がよいことに、データセットを反復処理することなく `len(loader)` を直接取得できる。

<!--en:4723154f-->
## 訓練

<!--en:0148ef68-->
### 訓練ループと履歴

<!--en:f912df6a-->
次に、`Trainer` を構築する。これは `Module` と `DataModule` を結び付けるエンジンである。`trainer.fit(model, data)` を呼び出すと、データローダを準備し、モデルとそのオプティマイザを設定して、`max_epochs` 回のパスを実行する。各エポックでは、`fit_epoch` が訓練ミニバッチを一通り処理し（パラメータを更新しつつ訓練の評価指標を平均化する）、続いて検証ミニバッチに対して `validate` を呼び出し、エポック平均を `self.history` に記録して `ProgressBoard` のリアルタイムプロットを更新する。

<!--en:7bbf9706-->
:numref:`sec_scheduler` で扱う学習率スケジュール（learning-rate schedule）に対応するため、`prepare_optimizer` は、任意選択でタプル `(optimizer, scheduler)` が `configure_optimizers` から返された場合にそれもアンパックする。

<!--en:ff8d32c8-->
`prepare_model` はパラメータを共有するモデルの 2 つのビュー（訓練用と評価用）を作成し、ドロップアウトやバッチ正規化（batch normalization）のような層が各モードで適切に動作するようにする。`prepare_optimizer` は Optax の勾配変換を `nnx.Optimizer` で包み、変換構造をキャッシュすることで、繰り返し訓練を行う際にコンパイル済みの JIT カーネルを再利用できるようにする。

<!--en:14782a83-->
`fit(model, data)` メソッドは、:numref:`sec_linear_scratch` の `train` 関数と同じ外側ループを実装する。3 つの準備用フックを実行した後、`max_epochs` エポックにわたってループを回す。各エポックでは、`fit_epoch()` が訓練ローダを一通り走査して訓練の評価指標の平均を返し、`validate()` が検証ローダ（存在する場合）を評価し、`record()` がその両方を記録・プロットする。

<!--en:31b6a56c-->
なお、`fit` は現在のエポック番号を `self.epoch` として公開し、直接は何も返さない。記録されたすべての曲線は `trainer.history` に格納される。これは分割名と評価指標名（`'train_loss'`、`'val_loss'`、および後に登場する `'val_acc'`）をキーとするリストの辞書である。したがって、`trainer.history['val_loss'][-1]` によって最終的な検証損失を直ちに取得できる。`'loss'` を先頭にソートしておくことで、モデルが異なってもプログレスボード上の曲線の色が常に一貫する。

<!--en:05d75079-->
これら 2 本の曲線は同じ位置には描画されない。その理由を :numref:`fig_oo_epoch_timeline` に示す。エポック $e$ の訓練損失は、そのエポック内の全ミニバッチステップにわたる平均であり、各ステップはそれぞれ異なるパラメータで計算されるため、`fit` はこれをエポックの中央である $e + \frac{1}{2}$ に描画する。一方、検証損失はそのエポック終了時点のパラメータを用いて 1 度だけ計算され、$e + 1$ に描画される。

<!--en:632290d1-->
![プログレスボード上の 1 エポック。パラメータが改善するにつれて個々のミニバッチの損失（灰色）は減少し、その平均である訓練損失が $e + \frac{1}{2}$ に描画される。検証損失はエポック終了時点のパラメータで計算され、$e + 1$ に描画される。](../img/mdl-linreg-epoch-timeline.svg)

<!--en:2c64989a-->
### エポック平均

<!--en:28577fae-->
エポックの最後のミニバッチは `batch_size` より小さくなることが多いため（たとえば $1{,}000 = 31 \times 32 + 8$）、バッチごとの平均損失を重みなしで単純平均すると、最後のバッチに含まれる 8 個の例が、それ以前の各バッチに含まれる 32 個の例とまったく同じ発言力を持ってしまう。補助クラス `Averager` は各バッチの評価指標にそのバッチサイズ `n` で重み付けして累積するため、`avg.mean()` は常に分割全体にわたる正確な例単位の平均を返す。

<!--en:b55ca022-->
### 訓練パスと検証パス

<!--en:58703ff3-->
次に、`validate` と `fit_epoch` は、4 つのフレームワークそれぞれにおいてバッチごとの検証ループと訓練ループを実行する（:numref:`chap_rnn` のリカレントネットワークに備え、任意の勾配クリッピング（gradient clipping）用の `gradient_clip_val` も用意してある）。

<!--en:b1645821-->
このトレーナは本書の残りの章すべてであらゆるモデルを実行するため、単純な線形回帰だけに必要なものよりわずかに長くなっている。それでもアルゴリズムの中核は :numref:`fig_linreg_sgd_cycle` とまったく同じ 4 ステップの SGD サイクル（順伝播、損失の計算、逆伝播（backward pass）、パラメータ更新）であり、後の章に向けたフックがいくつか追加されているものの、ここではまだ使われない。

<!--en:d6deb0fb-->
2 つの `if` ブロックは、勾配クリッピングと学習率スケジューラのためのフックである。`.detach()` を呼び出してから評価指標を `Averager` に渡すことで、累積する損失の和が各ミニバッチの計算グラフ（computational graph）をメモリ上に保持し続けるのを防ぐ。また、`model.train()` と `model.eval()` は、今後導入するドロップアウトやバッチ正規化などの層の挙動を切り替える。

<!--en:d3592d43-->
損失はすでにミニバッチ平均になっているため、`self.optim.step(1)` にはバッチサイズとして `1` を渡す。前のバッチの損失に対して `wait_to_read()` を呼び出すことで、MXNet の非同期バックエンドに対して Python の先行を多くても 1 ミニバッチ分に抑え、メモリ使用量に上限を設ける。

<!--en:afdeaf52-->
Python から TensorFlow の演算を 1 つずつ即時実行（Eager 実行）すると大きなオーバーヘッドが生じるため、この `prepare_model` のオーバーライドではダミーの順伝播を 1 回実行し（これにより Keras がすべての層の変数を実体化する）、`train_step` と `val_step` を `tf.function` で包んで高速な融合グラフへとコンパイルする。

<!--en:28744b54-->
`_trainer_train_step` と `_trainer_validation_step` を `@nnx.jit` でデコレートすることで、順伝播、損失、勾配、オプティマイザの更新が単一の融合された XLA 計算へとコンパイルされる。`has_aux=True` を渡すことで、`nnx.grad` は `out['loss']` を微分しつつ、勾配とあわせて評価指標の辞書全体も返すことができる。

<!--en:7a93eb4e-->
### プログレスボード

<!--en:66310bc6-->
最後に、`ProgressBoard` はノートブックの実行中にエポックごとの学習曲線をリアルタイムで描画する（描画なしのスイープを実行する際には `trainer.board.display = False` によって非表示にできる）。

<!--en:765b63c7-->
## 線形回帰の再訓練

<!--en:cc6c6283-->
新たに組み立てた `Module`、`DataModule`、`Trainer` の各クラスをエンドツーエンドでテストするため、`LinearRegressionScratch` を `SyntheticRegressionData` 上で 10 エポック訓練し、復元されたパラメータを確認してみよう。

<!--en:577e31cd-->
検証損失は :numref:`sec_linear_scratch` とまったく同じ軌跡をたどり、エポックごとに約 $7\times$ の倍率で急減して $5 \times 10^{-5}$ 付近のノイズフロアに達する。訓練曲線もその真上に重なっている（パラメータがわずか $3$ 個なのに対し例が $1{,}000$ 個あるため、モデルはラベルノイズをほとんど記憶しない）。最終的な検証損失とパラメータの復元誤差を数値で確認しよう。

<!--en:592cd636-->
訓練損失と検証損失はいずれもノイズフロアである $0.00005$ まで滑らかに減少し、復元されたパラメータも $(\mathbf{w}^*, b^*)$ と約 1,000 分の 1 以内で一致している。これにより、オブジェクト指向のハーネスが独立したスクラッチ実装のループを忠実に再現しつつ、以降の章をボイラープレートから解放することが確認できた。:numref:`sec_linear_concise` では次のステップに進み、手書きのテンソル、二乗損失、`SGD` クラスを各フレームワークの組み込みの層、損失関数、オプティマイザへと置き換える。

<!--en:30ac03ff-->
## まとめ

<!--en:9fc407f6-->
以降の章で反復的な訓練のボイラープレートではなくモデリングに集中できるよう、`d2l` ライブラリはモデル（`Module`）、データセット（`DataModule`）、最適化ループ（`Trainer`）を分離し、それらを `@add_to_class`、`HyperParameters`、`Averager`、`ProgressBoard` で支えている。`DataModule` は 1 エポックで枯渇することなくパスごとに訓練例をシャッフルし直す複数エポック対応のローダを返し、`Averager` は各ミニバッチの評価指標に例数で重み付けすることで、端数の最終バッチによってエポック単位の平均が歪むのを防ぐ。`Module` は明快な戻り値の契約（`training_step`、`validation_step`、`configure_optimizers`）を公開しているため、`LinearRegressionScratch` のように生のテンソルから構築したモデルであっても、フレームワークの層から構築したモデルであっても、すべて同じ `trainer.fit(model, data)` の呼び出しで訓練および検証を行える。

    $$B(\lambda, T) = \frac{2 hc^2}{\lambda^5} \cdot \left(\exp \frac{h c}{\lambda k T} - 1\right)^{-1},$$

次の 3 つの問いで、オブジェクト指向の訓練ハーネスに対する理解を確かめよう。

<!--en:9e3959c9-->
1. **サイズ重み付き `Averager` の計算：**$1{,}000$ 個の検証例をサイズ $32$ のミニバッチ（$31$ 個の $32$ 例バッチと $1$ 個の $8$ 例バッチ）に分け、$31$ 個のフルバッチの平均損失がいずれも $0.010$、最後の $8$ 例バッチの平均損失が $0.050$ であったとする。`Averager` が報告するエポック平均はいくらか。また、$32$ 個のバッチ平均を重みなしで単純平均するといくらになるか。

<!--en:fba5f9f5-->
2. **序盤に訓練損失が検証損失を上回る理由：**エポック 1 において、両方の分割がまったく同じ分布から得られているにもかかわらず、プロットされた訓練損失が検証損失より*高く*なることが多いのはなぜか。

<!--en:47c1a7fb-->
3. **拡張する場所：**次の変更を行うには、どのクラスのどのメソッドを修正すればよいか。(a) 損失とあわせて分類の正解率を報告する、(b) SGD から Adam に切り替える、(c) 検証損失が頭打ちになったときに早期停止を行う。

<!--en:557b98b6-->
**解答：**

<!--en:e6257a93-->
1. `Averager` は $(992 \times 0.010 + 8 \times 0.050) / 1000 = 0.01032$ を報告する。重みなしのバッチ平均は $(31 \times 0.010 + 1 \times 0.050) / 32 = 0.01125$ を報告し、$9\%$ の過大評価となる（ノイズの大きい $8$ 例が本来の重みの $4\times$ を受け取るため）。

<!--en:f59e697a-->
2. `fit_epoch()` はエポックの進行全体にわたって訓練損失を平均化する（ステップ 1 の高い初期損失から始まり、$x = 0.5$ にプロットされる）のに対し、`validate()` はそのエポックの全 $32$ 回の勾配ステップがすでに損失を下げた*後*のモデルを評価するためである（$x = 1.0$ にプロットされる）。

<!--en:4b7f4aae-->
3. (a) `Module.validation_step` をオーバーライドして `{'loss': ..., 'acc': ...}` を返すようにする。(b) `Module.configure_optimizers` を変更する。(c) `Trainer.fit` を 1 度サブクラス化して `self.history['val_loss']` を検査するようにする（モデルやデータセットのクラスは一切変更不要）。
