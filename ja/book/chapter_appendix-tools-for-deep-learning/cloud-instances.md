# クラウドコンピューティング

<!--en:f354a725-->
大半の読者は、本書のノートブックをノート PC、デスクトップ GPU、あるいは Colab のようなホスト型サービス（:numref:`sec_hosted_notebooks`）上で実行しているだろう。しかし遅かれ早かれ、プロジェクトはこの 3 つのいずれにも収まらなくなる。前処理がホスト型セッションの制限時間を超えてしまったり、モデルが 80 GB のアクセラレータメモリを必要としたり、実験に複数の GPU が同時に必要になったりするためである。これに対する通常の解決策はマシンを時間単位で借りることだが、そこでは 2 つの問いが生じる。どのマシンを借りるべきであり、完了した結果を得るのにいくらかかるのか。そして、いつ消えてもおかしくないマシン上でどのように作業すればよいのか。

<!--en:e15a7879-->
料金は毎月変動するため、以下に示す数値は時点を明記した例であり、価格カタログではない。だが、価格が変わっても通用する考え方が 2 つある。マシンは時間あたりの料金ではなく完了した結果あたりのコストで選ぶこと、そしてレンタルしたインスタンスは使い捨てとして扱い、重要なものはすべて永続ストレージにコピーしてからインスタンスを削除することである。なお、本書自身のノートブックが必要とするハードウェアは控えめである。いずれも 24 GB の RTX 4090 カード上で実行されており、大半は 8 GB 未満しか使用しないため、24 GB のレンタル機があれば単一 GPU のノートブックはすべて動作する。複数のカードを必要とするのは、:numref:`chap_performance` のマルチ GPU に関する各節のみである。

<!--en:0b494136-->
## レンタル市場

<!--en:039d70c2-->
### プロバイダの 3 つのティア

<!--en:30316478-->
GPU のレンタルは 3 種類の事業者によって提供されており、それらの違いはハードウェアそのものよりも、それを取り巻く周辺サービスと運営主体にある（:numref:`fig_tools_cloud_spectrum`）。

<!--en:f33c04bb-->
![クラウドの選択肢は、マネージドな統合環境やガバナンスと引き換えに、価格のばらつきや運用上の責任を受け入れる関係にある。](../img/tools-cloud-spectrum.svg)

<!--en:6c780629-->
* AWS、Google Cloud、Microsoft Azure などの**ハイパースケーラ**は、ID 管理、仮想ネットワーク、マネージドストレージをはじめとするあらゆる周辺サービスを備えた総合クラウドの一部として GPU を販売している。オンデマンドの GPU 料金は最も高く、最大規模のインスタンスではクォータの引き上げ申請や営業窓口への問い合わせが必要になることも多い。データがすでにそのクラウド上にある業務や、コンプライアンス要件の下にある業務、より大規模なマネージドシステムの一部として組み込まれる訓練に適している。また Google は本書の JAX コードを実行できる TPU も貸し出しており、2026 年 11 月時点で v5e チップ 1 基の料金は 1 時間あたり \$1.20 である。

<!--en:0444c838-->
* Lambda、Nebius、Voltage Park、CoreWeave などの **GPU スペシャリスト**は、高速なインターコネクトと機械学習用イメージを備えたアクセラレータを貸し出しており、それ以外の周辺サービスはほとんど持たない。2026 年 11 月時点で、このティアにおける H100 の料金は GPU 時間あたり約 \$2〜6 であり、Lambda、Nebius、Voltage Park では新規アカウントから営業担当を介さずに起動できる。ハイパースケーラの他のサービスを必要としない本格的な訓練の実行に適している。

<!--en:821cbf86-->
* Vast.ai や RunPod などの**マーケットプレイス**は、大手クラウドが扱わないコンシューマ向け GPU も含め、多数の独立した運営者からマシンを集約している。時間あたりの料金は最も安く、2026 年 11 月時点で RTX 4090 が 1 時間あたり \$0.30〜0.50、H100 が約 \$1.80 から出品されている。品質は出品枠ごとにばらつきがあり、ホストの信頼性、ディスク速度、ネットワーク品質はホストによって異なるうえ、コードは見ず知らずの第三者のマシン上で動作する。講義の課題や公開データであれば問題ないが、機密性の高い用途には、RunPod の Secure Cloud のような審査済みのデータセンターティアでジョブを実行しない限り不向きである。

<!--en:e7ccf5d8-->

<!--en:a6cce338-->
ここで 2 つの但し書きが重要になる。第 1 に、マルチ GPU ノードの料金はおおむね GPU 数に比例するが、インターコネクトはそうではない。NVLink を備えた 8×H100 マシンは PCIe 接続のカード 8 枚とは別物の道具であり、通信負荷の高い訓練（:numref:`sec_training_systems`）ではその差が顕著に現れる。第 2 に、新しい世代ほど仕事量あたりのコストが安いとは限らない。2026 年 11 月時点で B200 インスタンスは GPU 時間あたり約 \$7〜14 かかるため、より大きなメモリ容量や FP8/FP4 のスループットをジョブが活かせるときに限り元が取れる。

### 完了した結果あたりのコスト

<!--en:af6755f3-->
時間あたりの料金は総額のなかで最も目につきやすい項目にすぎず、実際の総額にはセットアップ時間、デバッグ中のアイドル時間、実行後も課金され続けるストレージ、データエグレス、そしてエンジニアの作業時間も含まれる。したがって、より高速で高価な GPU を使った方が、*完了した*実験あたりのコストはかえって下がることがある。以下のモデルでは、最も遅い GPU で 8 時間かかるジョブについて、マーケットプレイスの 3 種類の GPU のうちどれが最も安くジョブを完了できるかを計算する。自身の前提条件に書き換えて再実行してみてほしい。

<!--en:d4185e1b-->
クラウドの請求額は \$5.40、\$8.60、\$9.92 となり、請求額だけを見れば安価なカードが有利である。ここにエンジニアの作業時間 0.5 時間分を加えると総額は \$35.40、\$38.60、\$39.92 となり、差はずっと縮まるものの順位は変わらない。しかし、遅いカードで高速なカードより 30 分のデバッグ作業が 1 回多く必要になれば、その総額は \$65 を超えて順位が逆転するため、試行錯誤の回数も時間単価と同様にコストモデルへ組み込むべきである。ワークロードの規模はさらに重要である。7B モデルの LoRA ファインチューニングであれば 1 基のコンシューマ向け GPU で数時間で済むかもしれないが、小規模な言語モデルの事前学習（pretraining）には数千 GPU 時間を要し得る。時間単価のわずかな差を比較する前に、まずワークロードを見積もる必要がある。

<!--en:89cb8cd2-->
見落としやすいコストが 2 つある。

<!--en:870a1ee4-->
* **スポットおよび中断可能な容量**は半額以下に割引されることが多く、チェックポイント保存と再開を確実に行えるジョブ（:numref:`sec_training_systems`）に向いており、対話型セッションやチェックポイントなしの実行には向かない。AWS は 2 分前に終了を通知し、Google Cloud はデフォルトで最大 30 秒のシャットダウン猶予を与えるが、Vast.ai の中断可能インスタンスはより高い入札が入った瞬間にプロセスを強制終了して停止する。復旧手順は長時間の実行の最中ではなく、開始前にテストしておくべきである。

<!--en:4031bbf8-->
* **エグレス料金。**2026 年 11 月時点で、AWS と Azure はインターネットへのデータ送信に対し、月間最初の 100 GB を超えた分に GB あたり約 \$0.09 を課金する。140 GB のチェックポイントを 1 か月間毎日ダウンロードすると約 \$370 かかり、マーケットプレイスの RTX 4090 を 24 時間稼働させ続ける料金（\$0.44 で 720 時間、約 \$320）を上回る。データと計算機は同一リージョンに置き、大きなアーティファクトを頻繁に移動するワークフローでは、RunPod をはじめエグレス料金を課さないプロバイダを選ぶとよい。

## レンタルマシンでの作業

<!--en:181ce5c9-->
### インスタンスのセットアップと事前確認

<!--en:444ebe16-->
起動したばかりのインスタンスは未知のマシンであり、最初の数分間の確認が長時間の実行を安心して任せられるかを左右する。まずはドライバ、CUDA、コンテナランタイムがプリインストールされたプロバイダ最新の深層学習用イメージから始めること。素の OS イメージから始めると、後から再現しなければならない環境構築の手間が増える。接続には、どのプロバイダでも同じ手順で使える :numref:`sec_interactive_development` の SSH トンネル、または VS Code Remote SSH を用いる。SSH の切断で訓練が強制終了しないよう長時間ジョブは `tmux` 上で実行し、最初にマシンの状態を確認する。

<!--en:501c4493-->
モデルに 1 バッチを通し、チェックポイントを 1 回書き出して読み込み直す短いスモークテストを実行すれば、プロバイダのヘルス指標では見逃される問題を検出できる。壊れたドライバ、空き容量不足のディスク、読み取り専用のマウント、そしてストリーミングが遅すぎて GPU を稼働させ続けられないデータセットなどである。

<!--en:3be3f75a-->
### 使い捨てのインスタンスと永続的な結果

<!--en:58d2e1d2-->
レンタルしたインスタンスは、プリエンプトされたり、クラッシュしたり、誤って削除されたりする可能性があり、その上の作業内容はこれら 3 つのいずれが起きても失われないようにしなければならない。

<!--en:3c76535a-->
![計算機をプロビジョニングして安全に接続し、永続ストレージへチェックポイントを保存したうえで VM を削除する。代替マシンではそのストレージから処理を再開する。](../img/tools-cloud-lifecycle.svg)

<!--en:1d06494e-->
:numref:`fig_tools_cloud_lifecycle` のワークフローは、マシンの寿命と作業の寿命を切り離している。コードは Git に保存し、インスタンス上へクローンする。データとチェックポイントは、ジョブ側で制御するスケジュールに従って永続オブジェクトストレージ（S3、GCS、またはプロバイダのボリューム製品）にコピーする。こうしておけば、インスタンスを失った際の損失は高々直近のチェックポイント以降の作業分にとどまり、代替マシンがストレージから処理を再開できる。

<!--en:a4f4c885-->
実験が終わったら、インスタンス、ディスクやスナップショット、予約済み IP アドレス、不要になったバケットなど、課金対象となるものをすべて削除する。初日に請求アラートを設定しておくこと。アイドル状態の GPU も稼働中の GPU と同じ料金で課金される。また、アラートの通知は実際の利用より遅れて届くため、認証情報が漏洩した際の損失に上限を設けるのはアカウントの GPU クォータである。

<!--en:ace9a186-->
以上で、完了した結果あたりのコストに基づいてレンタルマシンを選び、マシンに障害が起きても作業内容を安全に保てるようになった。1 年の大半の日数で稼働し続ける GPU は、やがて借りるよりも購入する方が安くなる。:numref:`sec_hardware_buyers` では、どのハードウェアを購入すべきかを検討する。

## まとめ

<!--en:822c7fbc-->
本書のノートブックの大半は必要な GPU メモリが 8 GB 未満であり、単一 GPU のノートブックはすべて 24 GB のカードに収まるため、多額のレンタル費用が発生するのは主に言語モデルの規模からである。クラウド GPU 市場はハイパースケーラ、GPU スペシャリスト、マーケットプレイスにまたがり、同一の半導体でも数倍の価格差があるとともに、マネージドな統合機能、信頼性、運用上の信頼水準も大きく異なる。マシンを比較する際は、時間あたりの表示価格ではなく、セットアップ、デバッグの試行回数、永続ストレージ、データエグレス、およびエンジニアの作業時間を織り込んだ完了結果あたりの総コストで常に判断する。スポット容量はチェックポイント保存と再起動が可能なジョブの計算料金を削減できる一方、対話的な作業やチェックポイントなしの実行には不向きであり、またクラウドをまたぐエグレス料金は大容量チェックポイントの反復転送に対して急速に負担となる。レンタルしたインスタンスはすべて使い捨てとして扱い、構築済みイメージから起動し、`tmux` を用いて SSH トンネル経由で接続し、チェックポイントを永続ストレージへ順次保存して、実行が終わり次第すべての課金対象リソースを削除する。

## 演習問題

<!--en:a6b18485-->
1. [code] **ピークメモリとバッチサイズ。** 本書のノートブックの大半は GPU メモリの使用量が 8 GB 未満にとどまるため、:numref:`tab_cloud_prices` にある 24 GB カードではより大きなバッチをとる余裕がある。:numref:`sec_lm_bert` のエンコーダのファインチューニングを GPU 上（たとえば :numref:`sec_hosted_notebooks` のホスト型ノートブック）で、元のバッチサイズと半分のバッチサイズでそれぞれ 1 回ずつ実行せよ。両方の実行について、:numref:`fig_bg_allocator` における GPU メモリの 3 つのビューそれぞれのピーク値を記録せよ。
    1. 3 つのビューのうち、実行がカードに収まるかどうかを決めるのはどれか。また、それはなぜか。
    1. そのビューのピーク値をバッチサイズの一次関数として当てはめ、24 GB カードおよび 80 GB カードに収まる最大のバッチサイズを予測せよ。切片はメモリのどの部分を表すか。
    1. 2 回の実行の間のバッチサイズ（24 GB カードが利用できる場合はその予測値のバッチサイズでもよい）で実行し、実測されたピーク値を線形予測と比較せよ。
   :exlabel:`ex_cloud-instances-peak-memory`

<!--en:b16ce611-->
1. **信頼境界。** あるファインチューニングのジョブが、インスタンス上に保存されたアクセスキーを用いてオブジェクトストレージから訓練データを読み込み、インスタンスのローカルディスクにチェックポイントを書き出すとする。
    1. データは公開データセットであり、ジョブはマーケットプレイスのホスト上で実行されるとする。ジョブの実行中、ホスト運営者はデータセット以外に何を読み取ったり書き換えたりできるか。データが公開されていても問題になるのはそのうちどれか。また、インスタンスのディスクを暗号化してもホスト運営者からそれらを守れないのはなぜか。
    1. データが病院の医療記録であり、ジョブをハイパースケーラへ移すとする。ジョブの実行中、依然としてデータやチェックポイントを読み取れる立場にあるのはどの主体か。また、技術的な統制以外に、記録をアップロードする前に整えておかなければならないものは何か。

<!--en:95619864-->
1. [code] **コストモデルにおけるエンジニア工数。** `#cloud-instances-cost-model` では、`complete` の列は請求額に `setup_hours * engineer_per_hour` を加算している。
    1. `engineer_per_hour` の値がいくらであっても、`setup_hours` が 3 つの GPU すべてで同じである限り、この項によって最安となる GPU が変わらない理由を説明せよ。
    1. 結果を待ったり実行状況を確認したりするエンジニアが、`wall_hours` のうちの割合 $f$ をそれに費やすとする。この時間に `engineer_per_hour` を掛けた額を `complete` に加え、H100 と RTX 4090 の総コストが等しくなる $f$ の値を求めよ。この値は、RTX 4090 での 8 時間の実行中に何分間の対応時間が生じることに相当するか。
    1. エンジニア工数の項を両方とも除外せよ。請求額だけで H100 が RTX 4090 と並ぶには、いくらの `relative_speed` が必要か。
    1. :numref:`tab_cloud_prices` に挙げたマーケットプレイスの 1 つから 3 つの GPU の本日のオンデマンド価格を取得し、日付を記録したうえで損益分岐点となる割合 $f$ を再計算せよ。その値は 2 倍を超えて変化するか。
   :exlabel:`ex_cloud-instances-engineering-time`

<!--en:47408d3e-->
1. [code] **スモークテスト用スクリプト。** 長時間の実行に入る前にレンタルマシンが通過すべきスクリプトを作成せよ。このスクリプトは、任意の小さなモデルを `d2l.FashionMNIST` 上で訓練し、最初に失敗したチェック項目で明確なメッセージを出して終了するものとする。
    1. 次の 4 つのチェックを実装せよ。コマンドラインで指定されたアクセラレータが認識されること、チェックポイント用ディレクトリに指定バイト数以上の空き容量があること、アクセラレータ上で訓練ステップが 1 回実行できること、そして `d2l.save_checkpoint` で書き出して `d2l.load_checkpoint` で読み込み直したチェックポイントがすべてのパラメータとオプティマイザのテンソルを厳密に再現することである。
    1. 5 つ目のチェックとして、データイテレータが供給する毎秒バッチ数と、すでにデバイス上にあるバッチに対してモデルが維持できる毎秒訓練ステップ数とを比較する処理を追加せよ。なぜこれら 2 つの速度を別々に測定しなければならないのか。
    1. 手元のマシンで各障害を意図的に発生させよ。ディスクの実際の空きを超える容量を要求し、チェックポイント用ディレクトリを読み取り専用にし、バッチごとに `time.sleep` を入れてイテレータを遅延させよ。root はディレクトリの権限を無視するため、読み取り専用テストは非 root ユーザーで実行すること。このスクリプトがなければ、1 時間ごとにチェックポイントを書き出す 8 時間の実行において、それぞれの障害はいつ発覚していたか。また、実行を決して停止させない障害はどれか。
   :exlabel:`ex_cloud-instances-smoke-test`

1. **NVLink か PCIe か。** ● 2 つのプロバイダが GPU 時間あたり同じ料金で 8 基の H100 を提供している。一方のノードは GPU 間を NVLink で接続し、もう一方は PCIe 5.0 のみで接続している。データ並列ジョブでパラメータ数 $N$ の Transformer を BF16 勾配で訓練すると、通信時間には $S = 2N$ バイトが関与する（:numref:`sec_multi_gpu`）。各 GPU はステップあたり $b$ トークンを処理し、これには $6Nb$ FLOPs を要する（:numref:`sec_scaling-laws`）。バス帯域幅 $1/\beta_\textrm{link}$ を片方向の公称速度（NVLink は 450 GB/s、PCIe は 64 GB/s）とし、両ノードとも H100 の密な BF16 演算性能 989 TFLOPS の 40% を実効維持するものとする。また、通信と計算はオーバーラップしないと仮定する。
    1. $N = 1.3 \times 10^9$ のとき、$b = 16{,}384$ および $b = 4{,}096$ における各ノードのステップ時間を計算せよ。トークンあたりのコストで NVLink ノードと並ぶには、PCIe ノードの価格をどの割合だけ引き下げる必要があるか。
    1. 通信時間と計算時間の比は、両方の時間が $N$ に比例して増大するため、このパラメータ数に依存しない（:numref:`sec_hardware`）。各ノードにおいて、通信時間と計算時間が等しくなる GPU・ステップあたりのトークン数を求めよ。
    1. 勾配累積（:numref:`subsec_mp-accumulation`）では、$N_{\textrm{accumulation}}$ マイクロバッチごとに 1 回だけ通信する。これにより上で求めた閾値はどう変化し、また訓練の何が変化するか。

<!--en:5e51df06-->
1. **スポット容量での再実行。** ● あるジョブが $T$ 時間の計算を必要とする。スポット容量上では、中断は到着間隔の平均時間 $M$ のポアソン過程に従って発生する。各中断の後、代替インスタンスの起動に $R$ 時間かかり、ジョブはゼロから再開される。スポット容量の料金はオンデマンド価格の割合 $q$ であり、再起動にかかる時間も課金対象となる。代替インスタンスの起動中には中断は発生しないものとし、完了までの実経過時間の期待値は次の式で与えられる。

   $$\mathbb{E}[T_{\textrm{wall}}] = \left(e^{T/M} - 1\right)(M + R).$$

   問題 :exref:`ex_hosted-notebooks-checkpoint-interval`b（:numref:`sec_hosted_notebooks`）では、復旧作業中にも中断が発生し得る場合に対応する式を導出している。そこでは因子 $M + R$ が $M e^{R/M}$ に置き換わる。
    1. $T = 8$ h、$R = 0.25$ h、$q = 0.5$ のとき、$M = 24$、$8$、$4$ h のそれぞれについて、期待スポットコストがオンデマンドコストに占める割合を計算せよ。
    1. $R \ll M$ かつ $q = 0.5$ とする。スポット容量の方が期待値において安くなるのは、$T$ が $M$ のある定数倍未満のとき、かつそのときに限ることを示し、その倍数を求めよ。
    1. 今度は、ジョブが計算時間 $\tau = \sqrt{2 \delta M}$ 時間（:citet:`Young.1974` による問題 :exref:`ex_hosted-notebooks-checkpoint-interval`a の間隔）ごとにチェックポイントを書き出すとし、1 回の書き出しに $\delta$ 時間かかるとする。中断によって失われるのは直近のチェックポイント以降の作業のみである。$\mathbb{E}[T_{\textrm{wall}}]$ の式を長さ $\tau + \delta$ の 1 区間に適用し、スポット容量の方が期待値において安くなる最大の $q$ を、$\delta = 2$ min、$R = 0.25$ h、および $M = 24$、$8$、$4$、$2$、$1$ h のそれぞれについて求めよ。

<!--en:11def560-->

**解答：**

<!--en:7b95968f-->
1. **切片 $1.8\text{ GiB}$** はバッチサイズに依存しないメモリ（パラメータ、勾配、オプティマイザ状態、CUDA コンテキスト）を表す。OOM になるかどうかは**物理 VRAM に対するアロケータの予約済み・ピーク割り当てメモリ**で決まる。

<!--en:45812d13-->
2. 読み取り専用ディレクトリは最初の保存を行う**実行開始 1 時間後**にクラッシュする（1 時間分の計算が無駄になる）。低速なデータローダは**エラーを一切出さず**、GPU 稼働率 $20\%$ のまま黙って遊休させ、$5\times$ のコストを発生させる。

<!--en:068a3a0f-->
3. 4090 の請求額 $\$5.40$（GPU 計算分が $\$3.40$、残りのストレージ・エグレスが $\$2.00$）に並べるには、$(8.0 / s + 0.5) \times 2.50 = 3.40$ $\implies$ $8.0 / s = 0.86$ $\implies$ **`relative_speed` $\approx 9.3\times$** が必要となる。
