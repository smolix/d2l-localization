# ノートブック

<!--en:4b265849-->
ここまでに読んできたすべての節では、本文のすぐそばにコードが並び、各コードセルの下にその出力が表示されていた。読み進めるなかで、セルの一部を書き換えてみたいと思ったことがあるかもしれない。学習率を小さくしたり、層の幅を広げたり、訓練データを半分にしたりして、何が起きるか確かめるといった試みである。本書はまさにそのために書かれている。各節は 1 つの Jupyter ノートブックであり、文章・数式・コード・実行結果を 1 つのドキュメントに収め、1 セルずつ編集して実行できるようになっている。

<!--en:222e5070-->
セルを 1 つずつ実行すると、スクリプトでは決して生じない疑問が浮かび上がる。画面上の出力を生み出したのは、どのコードなのかという問題である。ノートブックは実行したすべての内容をその実行順に記憶するが、その順序はページ上の並びと一致するとは限らない。したがってノートブックには、再起動したが最後、作成者本人を含め誰にも再現できない結果が表示されうる。その対策は、結果を信用したり共有したりする前に、ノートブックを再起動して先頭から実行し直すことである。

<!--en:67c5ee3e-->
以下では、ノートブックがどこに状態を保持し、それをどう確認するかを説明したうえで、手元のマシンに本書のノートブック環境を構築し、エディタやリモート GPU から操作する方法を解説する。何もインストールしたくない場合は、:numref:`sec_hosted_notebooks` の手順で同じノートブックを Colab や Kaggle 上で無料実行できる。ノート PC 以上のハードウェアが必要な場合は、:numref:`sec_cloud_instances` を参照されたい。

<!--en:223df25a-->
## ノートブックの実行モデル

<!--en:ca31af2b-->
通常の Python スクリプトは毎回先頭から再実行されるため、データセットの読み込みや前処理のような時間のかかる処理が実験のたびに繰り返される。これに対しノートブックは、実行と実行のあいだも稼働し続ける Python プロセス（*カーネル*）を保持する。データを一度読み込めば、それをメモリに置いたまま何度でもモデルを試行錯誤できる。インラインの図表と解説文を織り交ぜられる点も相まって、この実行モデルは教育と研究の双方で威力を発揮する。

<!--en:9b8fb374-->
しかし同じメモリは、そこに値を書き込んだコードよりも長く生き残る。変数を代入したセルを編集したり削除したりしても、変数の値はそのまま残るのである。したがって、この*状態*（state）がどこに存在し、いつまで持続するのかを把握しておく必要がある。

<!--en:753d0092-->
### ドキュメントとカーネル

<!--en:8389c217-->
ノートブックは 2 つの要素からなる。*ドキュメント*はセルと保存された出力を格納するものであり、読み書きや共有、コミットの対象となる。*カーネル*は稼働中の状態を保持するものであり、インポート済みモジュール、変数、乱数生成器（random number generator）、開いているファイル、コンパイル済みプログラム、およびアクセラレータのメモリがそこに含まれる。ドキュメントはセルを上から下へと並べるが、カーネルが知っているのはセルを*実行した*順序だけである。この 2 つの順序の混同が、ノートブックにおける多くのバグを引き起こす。

<!--en:3fa3a42f-->
![ドキュメントはセルを上から下へ並べ、カーネルは実行順に状態を蓄積する。カーネルの再起動と全セル実行は、ドキュメントの順序（読者が再現できる唯一の順序）を再現し、両者の不一致を暴き出す。](../img/tools-kernel-state.svg)

<!--en:33eb86c8-->
:numref:`fig_tools_kernel_state` に典型的な失敗例を示す。編集セッションの途中で、まずデータ読み込みセルを実行し、あとからその*上*にモデル定義セルを書いたとする。カーネルはすでに `data` を保持しているため、その場では問題なく動作する。しかし、このドキュメントは実際には起きなかった経緯を語っていることになる。表示された順序どおりにセルを実行する読者や、翌日再起動したあとの作成者自身は、`NameError` に直面する。

<!--en:2810c168-->
実行カウンタ（`In [3]`、`In [1]`、…）は、カーネル起動以降のセルの実行回数を順に番号付けしたものであり、過去の履歴の手がかりではあっても依存関係グラフではない。次の 2 つのセルは、ドキュメントの順序に沿った無害な状態の例である。2 つ目のセルは、1 つ目のセルが実行されて初めて動作する。

<!--en:7e12c6e4-->
この依存関係は読み進める順序に従っているため問題ない。しかし、それより*下*にある代入や、すでに削除したセルに依存するセルは問題である。セルは小さく保ち、関数定義と実験の実行は分け、多数のセルにまたがってグローバル変数を書き換えるのではなくデータを明示的に受け渡すべきである。

<!--en:27209795-->
### カーネルの再起動と全セル実行

<!--en:2959c439-->
**カーネルを再起動してすべてのセルを実行**（Restart Kernel and Run All Cells）は、カーネルに蓄積された状態を破棄し、白紙の状態からドキュメントを読み進める順序どおりに再実行する操作である。これにより、ノートブックを共有する前にカーネルの隠れた状態や実行順序への依存を検出できる。ノートブックの保存・共有・コミットの前には、必ずこれを実行する。本書のビルドでも同じテストを適用しており、すべてのノートブックを新しいカーネルで先頭から末尾まで実行し、ウェブサイト上の出力はその実行結果から生成している。

## ローカル環境での本書の実行

<!--en:70591487-->
### セットアップ

<!--en:73dc16fc-->
パッケージのバージョンが変わると数値結果や API さえも変化するため、本書では環境をピン留めしている。:numref:`chap_installation` で説明した各フレームワーク用のノートブックアーカイブには、ノートブック一式、`d2l` パッケージ、および CPU 環境用と GPU 環境用の `uv` ロックファイルが含まれている。展開したディレクトリで一度だけ環境を作成し、そのなかで JupyterLab を起動する。

<!--en:20a82c89-->
NVIDIA GPU を搭載した Linux 環境では、代わりに `pylock.gpu.toml` を同期する。`--no-sync` オプションは、ロックファイルで確定した環境を uv が書き換えないようにするための指定である。[GitHub リポジトリ](https://github.com/smolix/d2l-neu)をクローンした場合は、代わりに `make` を使って環境を構築する（設定手順は :numref:`sec_developers_guide` で解説する）。

<!--en:6ffb4182-->
ノートブック内で選択する*カーネル*は、パッケージをインストールした環境に属していなければならない。1 つの Jupyter サーバーから複数のカーネルを参照できるため、サーバー自身の Python プロセスがどのカーネルでノートブックを実行するかを決めるわけではない。

<!--en:ff792284-->
### 簡単な事前確認

<!--en:1f8f1679-->
コードを変更する前に、実行環境の簡潔な識別情報を記録しておこう。

<!--en:57f1fb0a-->
これにより、環境構築でよくある 2 つのミスを 1 つのセルで検出できる。別の環境のカーネルを選んでしまうミス（`sys.executable` が想定外の場所を指す）と、データへの相対パスが解決できないディレクトリからノートブックを開いてしまうミスである。このセルはホームディレクトリを `~` に省略し、作業ディレクトリの末尾の要素だけを表示するため、保存された出力から個人固有のパスが漏れることはない。

## エディタでの作業

<!--en:53f4fc5a-->
### JupyterLab

<!--en:479463d2-->
[JupyterLab](https://jupyterlab.readthedocs.io/) は、ファイルブラウザ、ノートブックエディタ、ターミナル、テキストエディタ、デバッガ機能、および実行中カーネルの一覧表示を統合した環境である。インターフェースが進化しても、基本操作は変わらない。

<!--en:178326f0-->
* `Shift+Enter` でセルを実行し、`uv` や Git の操作、ファイルの確認にはターミナルタブを使う。

<!--en:f0cc71a4-->
* 環境名でカーネルを選択し、続いて `sys.executable` を確認する。

<!--en:231e866f-->
* 長時間の計算は、再起動する前にまず割り込み（Interrupt）で停止させる。再起動すると Python の状態が解放され、通常はそのプロセスが保持していたアクセラレータのメモリも解放される。

<!--en:e9399101-->
* 他者に渡す結果を保存する前には、**カーネルを再起動してすべてのセルを実行**を使う。

<!--en:fe509628-->
* **実行中**（Running）パネルを確認し、使わなくなったカーネルを停止する。ブラウザのタブを閉じてもカーネルは停止せず、放置された孤立カーネルが何ギガバイトもの GPU メモリを占有し続けることがある。

<!--en:6be69e8a-->
### VS Code

<!--en:b58c4d03-->
[Visual Studio Code](https://code.visualstudio.com/docs/datascience/jupyter-notebooks) では、カーネル選択、変数インスペクタ、セル単位のデバッグ、ノートブック構造を認識する差分表示を備えており、`.ipynb` ファイルの編集と実行ができる。展開したディレクトリをフォルダとして開き、先ほど作成した環境のインタプリタを選択したうえで、そのインタプリタをノートブックのカーネルに指定する。

<!--en:e23b263d-->
ノートブックが 1 つのプロジェクトへと成長した段階でも、VS Code なら定義への移動、テストの実行、コード整形、Git の差分確認をこなせる。テスト可能なロジックは `.py` モジュールに置き、ノートブックは解説と実験記録のために使うとよい。また、このリポジトリには本書の執筆ワークフロー（フレームワーク表示の切り替え、スライドのプレビュー、編集内容のソースへの同期）を支援する VS Code 拡張機能も含まれており、詳細は :numref:`sec_developers_guide` で解説する。

<!--en:e6bcea0e-->
### デバッグと実行時間計測

<!--en:1b50ae66-->
例外が発生しても終了するのはそのセルだけであり、カーネルは終了せずすべての変数とともにトレースバックを保持している。したがって、次のセルで `%debug` を実行すれば、例外が送出されたフレームでデバッガを開ける。カーネルが対応していればノートブックのデバッガを使い、あるいは失敗する小さな呼び出しをモジュールに切り出してターミナルでデバッグするとよい。「failed」と表示するだけの大雑把な `try/except` ブロックは避けるべきである。原因の診断に必要な例外の型と発生箇所が失われてしまうからである。手軽な時間計測には、IPython のマジックコマンドが標準で用意されている。

<!--en:39fd9c98-->
アクセラレータの実行時間を計測する際には 1 つ注意点がある。GPU の演算は非同期（asynchronous）であるため、ホスト側のタイマは処理の完了ではなく発行（ディスパッチ）だけを測定してしまうことがある。明示的に同期する（またはフレームワークのベンチマーク用ユーティリティを使う）こと、コンパイルされるカーネルを事前にウォームアップすること、そして測定値とあわせて形状・数値精度・デバイス・ライブラリのバージョンを記録することが不可欠である。

## リモートマシン

<!--en:6d505928-->
エディタ、ノートブックサーバー、カーネル、およびアクセラレータは、同じマシン上にある必要はない。GPU のあるマシン側で JupyterLab を動かし、手元のノート PC から編集する構成はよく使われる。

<!--en:2e3a3795-->
![ローカルのエディタは SSH トンネル経由でリモートの Jupyter サーバーとカーネルに接続し、アクセラレータはリモートカーネル側に接続されたままとなる。](../img/tools-remote-layers.svg)

<!--en:1502e546-->
リモートサーバーをループバックアドレスにバインドし、SSH でポートフォワーディングする。

<!--en:522d12fb-->
続いて、トークン付きの `http://127.0.0.1:8888/...` の URL をローカルで開く。認証なしの Jupyter サーバーを決してすべてのネットワークインターフェースにバインドしてはならない。そのポートに到達できる誰もが、起動したユーザー自身の権限でコードを実行できてしまうからである。SSH トンネルが暗号化とアクセス制御を担い、Jupyter のトークンは有効な第 2 の防御境界となる。

<!--en:3b6fb16e-->
VS Code の Remote SSH はサーバー側に小さなコンポーネントをインストールするため、エディタ UI はローカルで動作しつつ、ターミナル・拡張機能・ファイル・カーネルはすべてリモートマシン上に置かれる。ローカルのカーネルからはリモートの GPU を使えないため、Python 環境を選択する前にステータスバーに **SSH** と表示されていることを確認する。いずれの構成でも、リモート計算環境は使い捨てのものとして扱うべきである。再起動やプリエンプション（強制終了）、削除が起きる前に、コードをコミットし、チェックポイントを永続ストレージへコピーしておく必要がある（:numref:`sec_cloud_instances`）。

<!--en:a6cf8eac-->
ノートブックを共有またはコミットする前には、再現性（reproducibility）とプライバシーの最終確認を実施する。カーネルを再起動してすべてのセルを実行すること、セットアップが個人固有のパスや記録されていないダウンロードに依存していないか確かめること、出力からシークレットや非公開データを除去すること、説明や検証に役立つ出力だけを残して冗長な進捗ログを削除すること、そしてあらゆる測定値の解釈に必要な環境とハードウェアを記録しておくことである。

<!--en:30ac03ff-->
## まとめ

<!--en:9e9aa887-->
ノートブックは文章・コード・実行結果を織り交ぜつつ、計算コストの高い状態を実験間でメモリに保持するため、受動的に読むだけでなく自ら手を動かして編集することで真価を発揮する。保存されたドキュメントと稼働中のカーネルは異なる順序で状態を記録するため、両者が一致しているかを確かめるには、カーネルを再起動して先頭からすべてのセルを実行する検証が欠かせない。ローカルでの実行を再現可能に保つには、本書の `uv` ロックファイルから同期した環境内で JupyterLab を起動し、`sys.executable` によって有効なカーネルを確認する。JupyterLab はノートブック・ターミナル・カーネル管理を 1 つのブラウザ上のワークスペースに統合し、VS Code はプロジェクトの成長に伴ってモジュール間の移動・テスト・差分確認・リモート開発の機能を提供する。リモートのアクセラレータ上で作業する際は、認証なしのノートブックサーバーをネットワークに公開するのではなく、SSH トンネルまたは VS Code Remote SSH を介して接続する。

## 演習問題

<!--en:de57ff12-->
1. [code] **順序外の実行。**新しいノートブックで :numref:`fig_tools_kernel_state` の失敗を再現せよ。すなわち、`data` を定義するセルを実行し、その上に `data` を使用するセルを挿入して、新しいセルを実行せよ。その後、カーネルを再起動してすべてのセルを実行すると `NameError` で停止する。
    1. エラーを送出する代わりに値を変化させるような順序外実行のセルの組を作成せよ（たとえば、下の方のセルで学習率を再設定したあと、上の訓練セルを再実行する例など）。このノートブックでカーネルを再起動してすべてのセルを実行すると、どのような結果になるか。2 つの失敗のうち、より危険なのはどちらか。また、それはなぜか。
    1. 保存されたノートブックで、実行カウンタ $1, 2, \ldots, n$ が $n$ 個のコードセルにドキュメント順で表示されているとする。このことから、出力の生成過程について何が保証されるか。:citet:`Pimentel.Murta.Braganholo.ea.2019` は、隠れた状態を 3 種類（再実行されたセル、実行後に編集されたセル、削除されたセル）に分類している。このようなノートブックにもなお含まれうるのは、このうちどれか。カーネルを再起動するとカウンタは $1$ にリセットされるため、再起動の可能性も考慮せよ。
    1. 別のノートブックでは、カウンタ $3, 8, 9$ が 3 つのコードセルに表示されているとする。番号の飛びから、ドキュメントにはもはや残っていない実行について何が読み取れるか。また、この飛び番号は出力が隠れた状態に依存していることの証明になるか。
   :exlabel:`ex_interactive-development-out-of-order`

<!--en:14459144-->
1. **クリーン実行の限界。**カーネルの再起動と全セル実行は、新しいカーネル上でドキュメントを再実行するが、実行先は同じマシンのままである。作成者のマシン上でこのテストに合格する次の 5 つのノートブックを考えよう。
   (i) あるセルはファイルが存在すれば `features.npy` を読み込み、存在しなければそれを計算するが、計算側の分岐にはバグがあり、`features.npy` はリポジトリに含まれていない。
   (ii) すでに削除されたセルからパッケージがインストールされていた。
   (iii) あるセルが `/home/alice/data/train.csv` を読み込む。
   (iv) あるセルが、JupyterLab を起動したシェルで設定されていた環境変数を読み込む。
   (v) シード未設定の乱数生成器を使ってセルが計算した正解率を、本文の段落が引用している。
    1. それぞれのノートブックについて、それをダウンロードした読者が経験する事象を説明せよ。
    1. 代わりに、別の新しいマシン上で、リポジトリを新規にクローンし、ロックファイルから構築した新しい環境のなかでノートブックを先頭から末尾まで実行するとする。この検証によって 5 つの失敗のうちどれが検出されるか。残る失敗については、それを検出する方法を挙げよ。

<!--en:c9659f6a-->
1. [code] **定義前参照の検出器。**● カーネルの再起動と全セル実行は、ノートブックを実際に実行することによってのみ順序外の依存関係を見つけ出す。これに対し静的チェックは、実行せずにドキュメントを読み取って検査する。
    1. `.ipynb` ファイルを読み込み、あるコードセルが参照している名前のうち、それより前のどのセルでも組み込み（ビルトイン）でも束縛されておらず、かつ後続のセルで束縛されている名前をすべて報告する関数を作成せよ。`%timeit` などのマジックコマンドを `IPython.core.inputtransformer2.TransformerManager` で Python コードに変換してから、セルを `ast` で構文解析すること。作成した関数を演習問題 :exref:`ex_interactive-development-out-of-order` のノートブックでテストせよ。
    1. 関数の本体は、関数が定義されたときではなく呼び出されたときに実行される。この理由により検出器が誤検知（フォルスアラーム）を起こすノートブックと、実際の失敗を見逃すノートブックをそれぞれ 1 つずつ構成せよ。さらに、その誤検知を修正せよ。
    1. 次の 2 つの警告を追加せよ。1 つは前のセルが参照したあとに後続のセルで再束縛される名前に対する警告、もう 1 つは同じ名前を参照して再束縛するセル（`pixels = pixels / 255` など）に対する警告である。それぞれの警告は、演習問題 :exref:`ex_interactive-development-out-of-order`a の失敗と、インプレースなセルの反復実行による失敗のどちらを対象としているか。また、いずれかの警告だけで無害なケースと有害なケースを見分けることはできるか。
