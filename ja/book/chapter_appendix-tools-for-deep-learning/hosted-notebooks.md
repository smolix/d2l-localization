# Colab と Kaggle

<!--en:eab65bb5-->
前節では、手元のマシン上に本書のノートブック環境を構築した。しかし、GPU を搭載していないノート PC、ソフトウェアのインストールが禁じられた学校のコンピュータ、あるいはタブレットなど、適切なマシンが手元にない読者も多い。そうした読者の役に立つのが [Google Colab](https://colab.research.google.com/) と [Kaggle](https://www.kaggle.com/code) である。いずれもセッションの間だけ貸し出される仮想マシン上のノートブックをブラウザで開く仕組みになっており、Python と主要なフレームワークがあらかじめインストールされているほか、利用上限の範囲内で空きがあれば無料の GPU も使える。

<!--en:cd3448aa-->
借り物のマシンでは、ローカルマシンにはない問いが生じる。明日になっても残っているものは何か、という問いである。パッケージをインストールし、Fashion-MNIST をダウンロードして、分類器を 1 時間訓練したとしよう。プロバイダは接続時にマシンを作成し、一定時間のアイドル状態や利用上限への到達によってセッションが終了すると、そのマシンを削除する。翌朝になっても、ノートブック本体と永続ストレージ（durable storage）に保存したファイルは残っている。しかし、インストールしたパッケージ、データセット、およびローカルディスクに書き出したチェックポイントは消えている。

<!--en:df108e15-->
その対策は、ランタイムを使い捨て可能なものとして扱うことである。環境を再構築する手順を記録し、残すべきデータを保存するノートブックであれば、Colab でも Kaggle でもローカルカーネルでも同じように動作し、プロバイダがソフトウェアイメージを更新した後でも問題なく動く。以下では、本書の起動ボタンが 2 つのプロバイダへどのようにつながるか、両プロバイダにどのような違いがあるか、そして新しいマシンに変わってもそのまま動くセットアップセルをどう書くかを見ていく。

<!--en:5f7e7c77-->
![ホスト型ランタイムは一時的なものであり、ノートブック、データ、チェックポイントは明示的に保存したときに限り永続化される。](../img/tools-hosted-lifecycle.svg)

<!--en:70177e12-->
:numref:`fig_tools_hosted_lifecycle` にこのライフサイクルを示す。ランタイムは、無操作状態が続いた後に停止したり、セッション上限に達したり、別のソフトウェアイメージで再起動したりすることがある。ランタイムの再構築に必要な手順がすべてノートブックに記録されていれば、セットアップセルを再実行するコストはわずかで済む。本書のノートブックはそのように書かれている。

## 本書のノートブックの起動

<!--en:d359e4ab-->
本書のコードを含むすべてのページには **Run notebook** コントロールがあり、**Colab**、**Kaggle**、**Download** の 3 つの操作を選べる。このコントロールは選択中のフレームワークタブに連動し、そのタブに対応する PyTorch、TensorFlow、または JAX のノートブックを提供する。MXNet のようにホスト型ノートブックがないタブでは、*Notebook unavailable* と表示される。フレームワークを使わないコードのみのページでは、代わりに単一の NumPy ノートブックが提供される。これらのノートブックは公開 GitHub ブランチ上の固定パスに配置されており、ビルド元のソースリビジョンを記録している。`d2l` をインポートするノートブックの先頭には、自動生成されたセットアップセルが入っている。このセルは、プロバイダにプリインストールされたパッケージに互換性があればそれをそのまま使い、互換性がなければ本書で動作確認済みのバージョンをインストールした上で、そのリビジョンに対応する `d2l` の補助モジュールを GitHub からダウンロードする。

<!--en:f4d0ecee-->
![ソースページ、生成されたノートブックブランチ、およびプロバイダでの起動は独立した段階に分かれており、ページとノートブックは固定された対応関係で結ばれている。](../img/tools-notebook-pipeline.svg)

<!--en:4214432d-->
2 つの起動操作では、作業内容の保存先が異なる。

<!--en:4dd002f9-->
* **Colab は GitHub へのポインタを開く。**URL は `colab.research.google.com/github/<org>/<repo>/blob/<branch>/<path>.ipynb` という形式になっており、Colab は開くたびに GitHub からノートブックを取得する。常に最新の公開版が表示されるが、編集内容は書き戻されない。変更を残すには、**File → Save a copy in Drive** を使うか、`.ipynb` をダウンロードする。

<!--en:6be96a56-->
* **Kaggle はコピーをインポートする。**本書はノートブックの raw URL を Kaggle のインポータ（`kaggle.com/kernels/welcome?src=...`）に渡し、これによって自身の Kaggle アカウント内に新しい非公開ノートブックが作成されるため、利用にはアカウントが必要である。このコピーは本書から独立しており、本書が更新されても自動では更新されず、Kaggle 上でバージョンを保存することで変更内容を残せる。

<!--en:1f667ff8-->
いずれの場合も、起動リンクは公開パス上の閲覧可能なノートブックを参照しているため、実行前に中身を確認できる。インターネット上のどのような「Open in Colab」バッジに対しても同様に、自分のアカウント権限で他人のコードを実行する前に、参照元のリポジトリを確認し、セットアップセルを読んでおく必要がある。

## Colab

<!--en:7d6f27f1-->
### 無料枠のリソース

<!--en:6c892c0d-->
Colab の無料枠では GPU と TPU が提供されるが、公式の [FAQ](https://research.google.com/colaboratory/faq.html) ではハードウェアも上限も保証されていない。2026 年 11 月時点の記載によれば、利用可能なアクセラレータの種類は時期によって変わり、利用上限も変動する。ノートブックの実行時間は空き状況や自身の利用状況に応じて最大 12 時間であり、アイドル状態のランタイムはタイムアウトする。無料枠のユーザーには 16 GB のメモリを備えた T4 が割り当てられることが多いが、これもサービスとして保証されているわけではない。

<!--en:5cb02741-->
メニューに表示されるのは要求した構成であって、実際に割り当てられた構成ではないため、ランタイムはコード内で確認する。

<!--en:e87e1244-->
このセルは、起動時に読み込まれる `google.colab` モジュールによって Colab を判別し、作業ディレクトリによって Kaggle を判別する。アクセラレータについては、PyTorch では `torch.cuda.is_available()` と `torch.cuda.get_device_properties(0)`、TensorFlow では `tf.config.list_physical_devices("GPU")`、JAX では `jax.devices()` で確認できる。ただし、アクセラレータが検出されたとしても、ワークロードがそのメモリに収まる保証はない。

<!--en:c365252c-->
無料枠の上位として、Colab は Pay As You Go および Pro、Pro+ サブスクリプションを通じて*コンピューティングユニット*（compute unit）を販売している。残高を保有していればアクセラレータを利用しやすくなるが、特定のハードウェアが保証されるわけではない。単価や消費レートは変動するため、コストを見積もる前に購入ページを確認する必要がある。

<!--en:581c7d5d-->
### ランタイムバージョンとコマンドライン

<!--en:c21c85e7-->
Colab はソフトウェアイメージを定期的に更新するため、先月動いていたノートブックが動かなくなることがある。2025 年 9 月以降、ノートブックでは **Runtime → Change runtime type** から日付付きの*ランタイムバージョン*をピン留めできるようになった。2026 年 11 月時点では、過去のバージョンはリリース後 1 年間利用可能であり、接続には 2〜3 分かかる。Google は、大半の作業では最新のランタイム上でライブラリのバージョンをピン留めする方法を推奨しており、講義資料のように多くの人と共有するノートブックではランタイム自体をピン留めすることを推奨している。

<!--en:6dc18545-->
2026 年 6 月に Linux および macOS 向けにリリースされた [Colab CLI](https://github.com/googlecolab/google-colab-cli) を使えば、ターミナルやコーディングエージェントから同じランタイムを操作できる。`colab new` でランタイムを確保し、`colab exec` でその上のスクリプトやノートブックを実行し、`colab stop` で解放する。

<!--en:aa40fa12-->
### 作業内容の保存

<!--en:6d02b4cc-->
Colab は作業内容を Google Drive に保存する。**Save a copy in Drive** でノートブック本体が保存され、データセットやチェックポイントをセッションをまたいで保持するには Drive のマウント（`drive.mount`）を使うのが一般的である。GitHub から開いたノートブックが自動的に書き戻されることは決してない。また Colab は、手元のマシン上の Jupyter サーバーをブラウザページから操作する*ローカルランタイム*にも接続できる。ただし、これによってセキュリティ境界が移動する。ノートブックはローカルの Jupyter プロセスの権限で実行されるようになり、Drive のマウントも機能しなくなる。信頼できるノートブックだけを接続すべきである。

## Kaggle

<!--en:6e2e675e-->
### 入力、出力、バージョン

<!--en:0b6ef719-->
Kaggle はデータセットとコンペティションを中心に設計されており、そのノートブックもこれに沿った仕組みになっている。Kaggle ノートブックにおけるファイルの扱い方は、次の 3 種類のディレクトリによって決まる。

<!--en:8c9991fd-->
* `/kaggle/input/` には、紐付けられたデータセット、モデル、および他のノートブックの出力が格納され、バージョン管理された上で**読み取り専用**としてマウントされる。紐付けられたデータセットはノートブック内でダウンロードする必要がない。

<!--en:9151f4c8-->
* `/kaggle/working/` は書き込み可能な出力ディレクトリであり、2026 年 11 月時点で 20 GB の容量がある。その中身は、ノートブックの*保存済みバージョン*に対してのみ永続化される。

<!--en:a9283fc2-->
* それ以外の場所はすべて、セッション終了とともに消えるスクラッチ領域である。

<!--en:e23621f2-->
第 2 の大きな特徴はバージョン管理である。**Save & Run All** は、新規セッションでノートブック全体を上から下まで実行し、その入力、コード、出力、およびログをまとめた不変（immutable）なバージョンとして結果を保存する。これは、カーネルを再起動してすべてのセルを実行する習慣（:numref:`sec_interactive_development`）をプラットフォーム自体に組み込んだものである。

<!--en:45cd8e7d-->
### クォータとハードウェア

<!--en:2d2f0dd9-->
2026 年 11 月時点では、各アカウントには P100 1 基または T4 2 基の GPU で週あたり 30 時間（需要に余裕があるときはそれ以上になることもある）の GPU クォータが付与され、これとは別に週あたりの TPU クォータも付与される。1 回のセッションの実行時間は、CPU または GPU で最大 12 時間、TPU で最大 9 時間である。ノートブックのインターフェースにアカウントの現在の値が表示されるため、実行を計画する前に確認しておくとよい。また Kaggle では、アクセラレータやインターネット接続を有効化する前に電話番号認証を求められる場合がある。

<!--en:4a8e21c3-->
インターネット接続はノートブックごとの設定項目であり、一部のコンペティションでは無効化されるため、行儀のよいノートブックでは実行途中にデータをダウンロードするのではなく入力としてデータを紐付ける。[Kaggle CLI](https://github.com/Kaggle/kaggle-cli) を使えば、ターミナルからノートブックやデータセットのプッシュ、実行、プルを行える。そのトークンは必ずプロバイダのシークレットストアに保管し、決してセル内に書いてはならない。

<!--en:07f573ad-->
どちらのプロバイダでも本書のノートブックを実行できる。両者の違いは、ファイルや結果がどこに保存されるか、そして利用上限がどの程度予測可能かという点にあり、その比較を :numref:`tab_hosted_notebook_tradeoffs` にまとめる。

<!--en:eb270f59-->
### セットアップセル

<!--en:368b59fb-->
ランタイムは使い捨て可能であるため、ノートブック自身が環境構築の手順を備えていなければならない。優れたセットアップセルは短く、べき等（idempotent）かつ明示的である。すなわち、バージョンをピン留めし、不足しているものだけをインストールし、シークレットを一切含まない。

<!--en:15461d5b-->
ノートブックの先頭で無条件の `pip install --upgrade ...` を実行するのは避けるべきである。これを実行すると、検証済みのプロバイダ環境が壊れ、起動のたびに時間がかかり、昨日動いていたノートブックで今日になると異なるパッケージが解決される原因になる。代わりに、不足している特定のパッケージだけをピン留めしたバージョンでインストールする。また、ノートブックを一切変更していなくてもプロバイダ側のイメージが変わることがあるため、簡潔な環境フィンガープリントを出力しておけば、結果の解釈やバグ報告に役立つ。

<!--en:a4385794-->
### パスとシークレット

<!--en:537dadf4-->
ポータブルなノートブックでは、プロバイダ固有のパスのハードコーディングも避ける。小さなアダプタで作業ディレクトリを選択し、残りのファイル操作は `pathlib` に任せる。

<!--en:c293e7fc-->
どちらのプロバイダも API トークン用のシークレットマネージャを提供しており、ノートブックはそこからトークンを読み込むべきである。トークンを表示したり、セル出力に残したり、保存するコピーにコミットしたりしてはならない。公開ノートブックは実行可能な出版物であり、そのセル出力も公開内容の一部となるからである。

<!--en:37364118-->
こうした習慣によって、ノートブックは実行先のマシンに依存しなくなる。ただし、それでセッション時間が延びたりアクセラレータが保証されたりするわけではない。長時間の実行や保証されたハードウェアが必要な場合は、:numref:`sec_cloud_instances` で扱うように、自分で管理できるマシンをレンタルする。

<!--en:30ac03ff-->
## まとめ

<!--en:dbb4a686-->
Colab と Kaggle は、上限付きで GPU や TPU を利用できる無料の一時的なノートブックランタイムを貸し出しているが、ハードウェアの割り当ては保証されないため、必ずコード内で確認する必要がある。本書の 2 つの起動ボタンは作業内容の保存方法が異なる。Colab は GitHub へのライブポインタを開くため Drive にコピーしない限り編集内容は保存されないのに対し、Kaggle は独立したスナップショットを自身のアカウントにインポートする。Colab の無料枠の上限は需要に応じて変動し、優先アクセスのための有料のコンピューティングユニットやコンテナイメージを固定するランタイムバージョンのピン留めが用意されている一方、Kaggle は週あたりのクォータを公開しており、Save & Run All の実行ごとに不変なバージョンを記録する。どのホスト型マシンもアイドルタイムアウトやセッション上限で消滅し得るため、べき等なセットアップセル、永続ストレージへの明示的なチェックポイント保存、およびプロバイダのシークレットマネージャによる認証情報の管理を行うことで、プロバイダや時間の経過に左右されないポータブルなノートブックを実現できる。

1. **無料クォータでの事前学習。** ● BERT-base は約 1.1 億個のパラメータを持つ。:citet:`Devlin.Chang.Lee.ea.2018` は 256 系列のバッチで 1,000,000 ステップにわたりこれを事前学習しており、全ステップの 90% では 128 トークンの系列を、残りでは 512 トークンの系列を用いている。NVIDIA の仕様では、T4 の FP16 ピーク性能は 65 TFLOP/s である。1 基の T4 上での訓練がこのピーク性能の 30% を維持すると仮定せよ。
    1. $N$ 個のパラメータを持つモデルを $D$ トークンで訓練するには、約 $C \approx 6ND$ 回の浮動小数点演算というコストがかかる。内訳は、パラメータおよびトークンあたり順伝播で 2 回、逆伝播で 4 回である（:numref:`sec_scaling-laws`）。この方法で BERT-base の訓練コストを見積もれ。T4 で何時間かかるか。また、それは 12 時間セッションで何回分、週 30 時間のクォータで何週間分に相当するか。

    1. :citet:`hoffmann2022training` は、パラメータあたりの訓練トークン数を約 20 とする計算量最適な配分を見出した。この配分の下では、1 回の 12 時間 T4 セッションでどのモデルサイズとトークン数を訓練できるか。これに BERT-base のパラメータあたりのトークン数を比較せよ。

1. [code] **チェックポイント間隔。** ●● アイドル切断やマシンの回収といったホスト型セッションの中断を、中断間の平均時間が $M$ のポアソン過程としてモデル化せよ。訓練では $\tau$ 秒の計算ごとにチェックポイントを書き出し、その書き出しには $\delta$ 秒かかる。中断が起きた後、再接続して最新のチェックポイントを復元するのに $R$ 秒かかり、そのチェックポイント以降の計算は失われる。また、復元中にも中断が起き得るものとする。
    1. $\delta \ll \tau \ll M$ と仮定せよ。1 次近似において、実経過時間のうちチェックポイント保存と失われた計算に費やされる期待割合が最小になるのは次の間隔であることを示せ。

       $$\tau^* = \sqrt{2 \delta M},$$

       これは :citet:`Young.1974` の間隔である。
    1. $\tau$ 秒の計算とそれに続くチェックポイント保存からなる 1 区間を完了するまでの期待実経過時間が次式となることを示せ。

       $$\mathbb{E}[T] = M e^{R/M} \left(e^{(\tau + \delta)/M} - 1\right).$$

       $\mathbb{E}[T]/\tau$ を、$\delta/M \in \{0.01, 0.05, 0.1, 0.25, 0.5\}$ のそれぞれについて数値的に最小化せよ。$\tau^*$ は厳密な最適値からどれだけずれるか。また、$\tau^*$ における期待実経過時間は最小値をどれだけ上回るか。これら 2 つのずれの大きさがこれほど異なる理由を説明せよ。
    1. この過程のモンテカルロシミュレーションを書き、$\mathbb{E}[T]$ の式を $\delta/M$ と $R/M$ のある 1 組の設定の下で検証せよ。
    1. Kaggle のセッションはランダムな時刻ではなく、固定された 12 時間の上限で終了する。中断の時刻があらかじめわかっている場合、チェックポイントのスケジュールはどう変更すべきか。さらにランダムなアイドル切断も起こり得る場合、上の解析のどの部分が依然として成り立つか。

2. Colab 上で Google Drive をマウントせずに、15 分ごとに `/content/checkpoints/` へモデルのチェックポイントを保存した。セッションが 12 時間の上限に達したとき、どのチェックポイントが残るか。

<!--en:e3fe0977-->
3. すでに `import transformers` を実行済みのカーネルで、あるセルが `!pip install transformers==4.57.0` を実行した。それでも `transformers.__version__` が `4.56.1` を出力するのはなぜか。

<!--en:557b98b6-->
**解答：**

<!--en:6d49edc6-->
1. **どこにも残らず失われる。**Colab は GitHub への読み取り専用のポインタを開く。編集内容を残すには、セッションが切れる前に明示的に **File $\to$ Save a copy in Drive** を実行するか、`.ipynb` をダウンロードする必要がある。

<!--en:7e4b77df-->
2. **何も残らない。**`/content` はコンテナとともに削除される一時的な VM のスクラッチディスクである。Colab では、長時間の実行を始める前に `/content/drive` がマウントされていることを確認する（または外部ストレージへ同期する）ようにチェックポイントの保存処理を実装すべきである。

<!--en:dea726bb-->
3. Python はインポート済みのモジュールを `sys.modules` にキャッシュするため、ディスク上の `site-packages` 内のファイルを変更しても、カーネルの RAM 上にすでに常駐しているオブジェクトは再読み込みされない。パッケージ変更後はカーネルを再起動する必要がある。

[要点]{.kicker}

<!--en:16df24f6-->
- **編集内容の保存とハードウェアの確認：**GitHub から開いた Colab ノートブックはすぐに Drive へコピーし、割り当てられた GPU のプロパティをコード内で確認する

<!--en:101fef21-->
- **べき等なセットアップとドリフトログ：**ピン留めされたパッケージをインストールする前に `find_spec` で確認し（インポート済みなら再起動）、JSON 形式の環境フィンガープリントをログに残す

<!--en:bfe798b4-->
- **永続的なチェックポイントとシークレット：**マウントした Drive または `/kaggle/working` へ間隔 $\tau^* = \sqrt{2\delta M}$ でチェックポイントを書き出し、API キーはプロバイダのシークレットストアに保管する
