# 貢献者ガイド

<!--en:0353d411-->
ここまで本書のノートブックを数多く実行してくるなかで、意味の取りにくい文や、数式中で入れ替わった添字、あるいは新しいバージョンのライブラリで失敗するセルを見つけたことがあるかもしれない。修正は、その文章やコードが現れるすべての場所、すなわちウェブサイト、PDF、各フレームワークのノートブック、そして同じセルを引用するスライドのすべてに反映されるべきである。では、たった 1 行の修正がどのようにしてこれらすべての場所に行き渡り、何も壊していないことをどうやって確認できるのだろうか。

<!--en:43ed6569-->
本書はオープンソースソフトウェアと同じ方法で保守されている。すべてのページはバージョン管理下の 1 つの Markdown ファイルを元にしており、ビルドシステムがそれらのファイルから他のすべてを生成する。変更が関係するノートブックが正常に実行され、サイトがレンダリングできれば、レビューの準備が整う。本節では、ビルドの仕組み、変更を提案するための Git ワークフロー、任意で利用できるコーディングエージェント、そして変更が通過すべきチェックについて解説する。同様の課題は、ドキュメント自体が実行可能でなければならないあらゆる機械学習リポジトリで生じる。

<!--en:17cc5f72-->
## ビルドの仕組み

<!--en:cce63472-->
### 1 つのソースと多数のアーティファクト

<!--en:10692b44-->
各節は単一の Markdown ファイルに格納されており、本節のファイルは `chapter_appendix-tools-for-deep-learning/developers-guide.md` である。ビルドでは、これらのソースから他のすべてを派生させる。

<!--en:0f3d901b-->
この設計からは、実用上 3 つの帰結が得られる。

<!--en:331e41ed-->
* **生成されたファイルは決して編集しない。**`.qmd` や `.ipynb` への編集は次のビルドで消去されてしまう。ソースである `.md` を編集して再生成すること。

<!--en:1d67e654-->
* **フレームワークのタブは 1 つのファイルに同居する。**`%%tab pytorch` のタグが付いたコードブロックは PyTorch ビューにのみ現れ、タグのない Python ブロックはそのファイルから生成されるすべてのノートブックに現れる。ファイル内に少なくとも 1 つのブロックでタグ付けされたフレームワークごとに 1 つのノートブックが生成され、タグ付きブロックを持たないファイルからは PyTorch のノートブックのみが生成される。したがって、1 つのソースファイルから最大 4 つのノートブックが生成され、そのすべてが正常に実行できなければならない。「基礎」、「画像モデル」、「深層学習のための数学」、「深層学習のためのツール」の各パートの章は 4 つのフレームワークすべてに対応しており、「発展」パートの章は PyTorch と JAX に（ただし :numref:`chap_reinforcement_learning` は PyTorch のみ）、「言語モデル」パートは PyTorch に対応している。

<!--en:acc22337-->
* **セルの識別子は不変である。**すべての Python ブロックは（`tools/add_cell_ids.py` によって割り当てられる）永続的な ID を持つため、ファイル名の変更や移動があっても、スライド、実行済み出力、およびフレームワークごとのビューから同一のセルを参照できる。

<!--en:623cbf02-->
ソースがノートブックではなく Markdown である理由は、バージョン管理にある。`.ipynb` ファイルはコード、出力、実行回数、エディタのメタデータが混在する JSON であるため、1 語を修正して再実行するだけで、その語以外の多くの行まで変化してしまう。一方、Markdown の diff には変更された本文とコードしか現れない。実行済み出力は別個に保存され、それを生成したコード、そのコードが使用するライブラリのコード、あるいはフレームワークのバージョンが変更されたときにのみ再取り込みされる。

<!--en:b0b597d1-->
本書全体を通じてインポートしてきた `d2l` ライブラリも同じ仕組みで生成されている。`make lib` は `#@save` が付いたすべてのブロックを抽出し、フレームワークごとのモジュールである `d2l/torch.py`、`d2l/tensorflow.py`、`d2l/jax.py`、`d2l/mxnet.py` に書き出す。関数を解説している箇所で加えた修正は、再ビルドによって後続のすべての章に行き渡る。これらのファイルの先頭に直接編集しないよう記されたバナーがあるのはそのためである。:numref:`sec_hosted_notebooks` の Colab および Kaggle 用ノートブックも同様に、独立した `notebooks` ブランチ上に生成される。このブランチはソースから再ビルドされるものであり、手作業で編集することは決してない。

<!--en:0548b902-->
### リポジトリの構成

<!--en:6e9cc751-->
リポジトリのトップレベルには、ソース、ビルドのエントリポイント、およびそれらを説明するドキュメントが置かれている。

<!--en:a4a45156-->
新規クローン直後に `./bootstrap.sh` を実行すると、コミット済み出力の画像を保持する Git LFS のインストールとその画像の取得が行われ、Quarto を含む環境 `.venv-build` が作成される。その後は、GPU を持たないノート PC 上でも `make html` によってコミット済み出力からサイト全体をレンダリングできる。ノートブックの実行はこれとは別のステップである。Makefile の実行には GNU Make 4.3 以降が必要であり、macOS では追加インストール（たとえば MacPorts の `gmake`）としてのみ提供されている。ターゲットの一覧は `make help` で確認でき、詳細は `docs/build-system.md` で解説されている。

## Git の基本

<!--en:b236ea35-->
本書へのあらゆる変更は、各自が作成したリポジトリのコピー上のブランチにおける Git コミットとして扱われる。日常的に Git を使っている読者は先へ進んでよい。まず、そのコピーを作成する。[リポジトリページ](https://github.com/smolix/d2l-neu)で **Fork** をクリックし、フォークしたリポジトリをクローンして変更用のブランチを作成する。

<!--en:3ba5a521-->
ソースの `.md` ファイルを編集したら、変更を記録して公開する。

<!--en:85f8e70e-->
すると GitHub 上で*プルリクエスト*（マージを提案するブランチであり、メンテナがレビューやコメントを行える diff を伴う）の作成が案内される（[`gh` コマンドラインツール](https://cli.github.com/)でも `gh pr create` で同じ操作ができる）。複数の章にまたがる変更よりも、小さく焦点を絞ったプルリクエストのほうがレビューしやすい。

<!--en:0c45ff19-->
## コーディングエージェント

<!--en:16e4fa6a-->
コーディングエージェントとは、リポジトリを読み取り、ファイルを編集し、コマンドを実行する言語モデルである。関数がどこで定義されているかを探すこと、機械的な変更をフレームワークごとの実装へ波及させること、あるいはチェックを実行して失敗箇所を読み取ることといった、範囲の明確な作業で力を発揮する。その利用は任意であり、エージェントによる編集にも人間の編集とまったく同じレビューが必要である。本リポジトリの 3 つの特性により、こうした支援が実用的なものとなっている。

<!--en:26578e40-->
* **ビルド手順が文書化されている。**`CLAUDE.md` と `docs/` には、アーティファクトの再生成・実行・レンダリングの方法がエージェント向けに記されており、同じ手順書が人間の貢献者にも役立つ。

<!--en:edfc3c28-->
* **検証が実行可能である。**編集が正しく機能しているとは、ノートブックが対応するすべてのフレームワークで先頭から末尾まで実行でき、コミット済み出力の監査を通過し、ページがレンダリングできることを意味する。編集、再生成、実行、失敗箇所の調査というループはエージェントが回せるが、最終的な diff とチェック結果の根拠の両方をレビューするのは貢献者である。

<!--en:e2dcd934-->
* **退屈な作業は機械的である。**フレームワーク間の実装の同期、すべての `:numref:` が解決されることの確認、図の再生成はいずれも複数ファイルにまたがる作業であり、エージェントが実行して人間がレビューするのに適している。

<!--en:20b47049-->
有益な依頼とは、たとえば「モメンタムの節の等高線プロットで軸ラベルが誤っているため、ソースを修正し、影響を受けるノートブックを再実行せよ」のように、変更内容とその検証方法を明記したものである。レビューでは 2 つの失敗モードに注意する。第 1 に、プロジェクトのドキュメントで警告していない限り（本リポジトリでは警告している）、エージェントは初心者と同様に生成ファイルを編集してしまうことがある。第 2 に、失敗しているチェックを通すよう求められたエージェントは、原因を直す代わりにチェックやコード自体を弱めてしまうことがある。ノートブックが再び実行できるようになっても、本来教えるべき内容を教えなくなっているかもしれないのである。

<!--en:c46fde9e-->
## 変更の提出

<!--en:c529b02d-->
貢献の内容は 1 行の修正から新しいコードの追加まで多岐にわたり、変更が大きくなるにつれて必要なチェックも増える。1 行の修正であれば、ローカルへのチェックアウトすら必要ない。GitHub 上でソースファイルを開き、編集（鉛筆）ボタンを押せばよい。GitHub がリポジトリのフォークを提案し、編集後はコミットからプルリクエストの作成まで、すべてブラウザ上で案内してくれる。

<!--en:9c99139a-->
コードや本文の変更では、リポジトリをクローンしてブランチを作成し、ソースの `.md` を編集する。編集したファイルは `tools/lint_source.py` で検査する。このスクリプトは、対応が取れていないタブやスライドのマーカ、重複したセル ID、数式に正しく紐づかない数式ラベルを検出し、`--corpus` を付けるとすべての相互参照が実在するラベルを指しているかも検査する。続いて、編集が影響するすべてのノートブックを再実行し、その出力をコミット対象のストアにコピーしてサイトをレンダリングする。

<!--en:da142d4a-->
`#@save` が付いたコードを編集した場合は、ノートブックを実行する前に `make lib` でライブラリを再ビルドする。すると、編集したシンボルを使用している他の節のノートブックも陳腐化（stale）するため、`make audit-outputs` でそれらを一覧表示できる。GPU を持たないノート PC では GPU ノートブックを再実行できないため、`make html` はそのようなノートブックに対してビルドを停止せず警告を出す。プルリクエストには、GPU での実行がまだ必要なノートブックを明記しておくべきである。新しい本文は `docs/writing-guide.md` に、新しいコードは `docs/code-guide.md` に従う。

<!--en:b2c56cd5-->
生の Markdown よりもノートブックを編集したい場合は、`.vscode-extension/` にある VS Code 拡張機能（ビルドとインストールの手順はその README に記載されている）を使うとよい。この拡張機能は、現在の節の生成済みノートブックを適切なカーネルが選択された状態で開き、フレームワークごとのビューを切り替え、スライドデッキをライブプレビューし、1 つのコマンドでノートブックの再実行と出力の取り込みまでこなす。ノートブック上で行った編集は Markdown のソースに書き戻されるため、生成されたファイル自体を直接編集したことには決してならない。この拡張機能が使用する Jupyter カーネルは `make kernels` で登録できる。

<!--en:41d3348a-->
どの手順をとるにせよ、変更が関係するすべてのフレームワークでまっさらな状態から問題なく実行でき、かつ変更されたのが生成ファイルではなくソースであるときに、変更の準備が整ったといえる。

<!--en:30ac03ff-->
## まとめ

<!--en:8828a6c8-->
各節につき単一の Markdown ソースから、ウェブサイト、PDF、フレームワークごとのノートブック、スライド、および `d2l` パッケージが生成される一方、実行済み出力は別個にバージョン管理され、生成されたファイルを手作業で編集することは決してない。本文とコードをプレーンな Markdown に保つことで行単位の見通しのよい Git diff が得られるため、600 以上のノートブックからなる書籍であっても容易にレビュー・保守し続けられる。すべての貢献は同じループをたどる。すなわち、リポジトリをフォークし、目的を絞ったブランチを作成し、`.md` ソースを編集し、リント・影響を受けるノートブックの再実行・出力の取り込み・レンダリングによって検証したうえで、小さなプルリクエストを作成する。ビルドルールが文書化されており検証も実行可能であるため、機械的なマルチフレームワーク作業の多くはコーディングエージェントで自動化でき、人間の貢献者はその結果生じる変更をレビューして責任を持つことができる。

## 演習問題

<!--en:aef59e43-->
1. **フレームワークタブ。**あるソースファイルに、次の順序でちょうど 5 個のコードブロックが含まれているとする。(1) `%%tab pytorch` のタグが付き、`import torch` と `x = torch.arange(6.0)` を実行するブロック、(2) `%%tab jax` のタグが付き、`import jax.numpy as jnp` と `x = jnp.arange(6.0)` を実行するブロック、(3) タグなしのブロック `y = x * 2`、(4) `%%tab pytorch` のタグが付き、`x[0] = 10.0` を実行するブロック、(5) タグなしのブロック `print(y.sum(), x.sum())`。
    1. ビルドはこのファイルからどのノートブックを生成し、それぞれにどのブロックが含まれ、それぞれ何を表示するか。
    1. ある貢献者がブロック (4) のタグを削除し、すべてのフレームワークで実行されるようにしたとする。このとき失敗するのはどのノートブックであり、どのようなエラーが発生するか。両方のノートブックが同じ値を表示するよう、ブロック (4) をタグ付きブロックに置き換えよ。
    1. 生成された PyTorch ノートブック上でブロック (3) を編集し、VS Code 拡張機能がその編集をソースファイルに書き戻したとする。この編集によって変更されるのはどのノートブックであり、提出前に実行しなければならないのはそのうちのどれか。
   :exlabel:`ex_developers-guide-framework-tabs`

<!--en:80709989-->
1. **陳腐化した出力。**コミット対象のストアは、ノートブックの出力をそれを生成したセルの ID（キー）ごとに整理して `outputs/<fw>/<chapter>/<stem>.json` に保持する。各出力とともにフィンガープリントとして、各行の末尾空白を除去したうえでそのセルおよびそれより前のすべてのコードセルのコードを求めたハッシュが保存される。またノートブック全体に対して、ローカルビルドタグを除いたインストール済みフレームワークのバージョン（`torch==2.11.0` であり、`torch==2.11.0+cu128` ではない）と、その節のコードが言及するすべてのシンボル `d2l.X` のライブラリブロック（およびそれらのシンボルがさらに使用するブロック）のハッシュも保存される。これらの値のいずれかが現在のソースや環境と一致しなくなったとき、出力は陳腐化していると判定される。監査スクリプト `tools/audit_outputs.py`（サイトをレンダリングする前に `make html` が実行する）は、ノートブックがホストの搭載数を超える GPU を必要とする場合を除き、陳腐化した画像を警告として報告し、陳腐化したテキスト出力があればビルドを停止する。
    1. ある節に 10 個のコードセルがあり、そのすべてのフレームワーク版が `d2l.Trainer` を呼び出しているとする。次の各編集を行った後、どのフレームワークのどの出力が陳腐化するか。(i) 段落内の誤字を修正した場合、(ii) タグのない 3 番目のコードセル内のコメントの誤字を修正した場合、(iii) すべての行から末尾の空白を削除した場合、(iv) 5 番目と 6 番目のコードセルを入れ替えた場合、(v) 別の節にある `Trainer` メソッドの docstring を（タグなしの `#@save` セル内で）変更した場合、(vi) PyTorch を 2.11.0 から 2.12.0 にアップグレードした場合、(vii) Linux 向け CUDA ビルドの代わりに macOS 向け CPU ビルドから PyTorch 2.11.0 をインストールした場合。
    1. (a) の陳腐化判定のうち、実際には変化しえない出力にフラグを立てているのはどれか。また、(vii) が見逃してしまう実際の出力変化にはどのようなものがあるか。ルールがこの両種の誤りを許容しているのはなぜか。
    1. 新たに実行した結果が保存済みの出力と異なる表示になったとしても、ビルドがそれをもって出力を陳腐化と判定しないのはなぜか。
   :exlabel:`ex_developers-guide-stale-outputs`

<!--en:24a21b14-->
1. [code] **重複する定義。**`make lib` はすべての節の `#@save` ブロックを書籍の順序で収集する。複数のブロックが同じ関数やメソッドを定義している場合、ライブラリはそのうちの 1 つだけを保持する。メソッド `Trainer.prepare_batch` は、すべてのフレームワークで実行されるタグなしのセル `#linear-regression-scratch-training-1`（:numref:`sec_oo-design`）で定義され、さらにデバイス対応を備えた形でセル `#gpus-devices-memory-the-trainer-now-with-devices-1`（:numref:`sec_use_gpu`）の各フレームワーク版で再定義されている。
    1. タグなしの定義の本体と、デバイス対応版の PyTorch 実装の本体の両方にコメント行を追加し、`make lib` を実行したうえで、`d2l/torch.py` 内で両方のコメントを検索せよ。どちらのコメントが書き出され、そこからどのようなルールがわかるか。
    1. `d2l.Trainer.prepare_batch` は、:numref:`sec_oo-design` の PyTorch ノートブックの開始時点ではどちらの定義を保持しており、そのセル `#linear-regression-scratch-training-1` の実行後にはどちらの定義を保持しているか。
    1. ビルドが最初の定義ではなく最後の定義を保持するのはなぜか。
    1. ある貢献者がデバイス対応の PyTorch 版 `prepare_batch` を変更し、すべてのバッチを 16 ビット浮動小数点数にも変換するようにしたとする。異なる結果を表示しうるのはどの節の PyTorch ノートブックか。書籍の順序で :numref:`sec_use_gpu` より前の節か、後の節か、あるいはその両方か。
   :exlabel:`ex_developers-guide-duplicate-definitions`

<!--en:08633609-->
1. [extended] **データフローに基づく陳腐化判定。** ●● 演習問題 :exref:`ex_developers-guide-stale-outputs` のフィンガープリントは、最初に編集されたセル以降のすべてのセルを陳腐化とマークする。これに対しデータフロールールでは、編集されたセルが束縛（bind）する名前を直接、あるいは他のセルを介して読み取るセルのみをマークする。演習問題 :exref:`ex_interactive-development-use-before-define`（:numref:`sec_interactive_development`）の検出器は、各セルが束縛する名前と読み取る名前をすでに抽出している。
    1. `make notebooks-pytorch` で PyTorch ノートブックを生成し、すべてのコードセルについて束縛する名前と読み取る名前を抽出せよ。単一セルのあらゆる編集について、データフロールールが陳腐化とマークするセルと、それらを再計算するために実行しなければならないセル（陳腐化したセルが依存するそれ以前のすべてのセルを含む）を求めよ。両ルールの下で、陳腐化とマークされるセルの割合の平均と、実行しなければならないセルの割合の平均を章ごとに報告せよ。
    1. たとえば乱数生成器の状態を介する場合のように、後続のセルが読み取る名前を束縛することなく、編集によって後続の出力を変化させてしまう本書中のセルを見つけよ。本書のノートブックでは、この種の他のどのようなチャネルが使われているか。

[code] **ノイズを伴う二分探索。** ●● `git bisect` は二分探索によって不具合混入元のコミットを特定する。すなわち、正常と判明しているコミットと不良と判明しているコミットの中間のコミットをチェックアウトし、そのコミットをテストすることで探索範囲を半分に絞る。しかし、モデルを訓練するテストにはノイズが伴う。ノートブックのチェック「検証正解率が 0.9 以上」が、各実行で独立に、確率 $p = 0.9$ で最初の不良コミット $k$ より前のすべてのコミットにおいて通過し、確率 $q = 0.3$ で $k$ 以降のすべてのコミットにおいて通過するとする。コミット 0 は正常、コミット 64 は不良であることがわかっており、$k$ は $\{1, \ldots, 64\}$ 上の一様分布に従うとする。
    1. 1 回のテストにつき 1 回だけ実行するとき、`git bisect` が正しく $k$ を特定する確率はいくらか。
    1. 各テストを $m$ 回繰り返し、通過回数がしきい値以上に達したときにそのコミットを正常と判定するとする。誤ったコミットを特定する確率が多くても 5% となる最小の $m$ とそのしきい値を求めよ。この探索には合計何回の実行を要するか。
    1. 確率的二分法（probabilistic bisection）アルゴリズムは、不具合の位置に関する事後分布を保持し、その中央値でテストを実行して、実行ごとにベイズの定理で事後分布を更新する :cite:`Frazier.Henderson.Waeber.2019`。$k$ に関する事後分布と、$p$ および $q$ で与えられる尤度を用いて、事後分布が 1 つのコミットに 0.95 の確率を割り当てるまでこれをシミュレーションせよ。離散的なコミットの集合上では、中央値でのテストが進行しなくなりうるのはなぜか。これを解決するようテスト対象コミットの選び方を変更し、平均実行回数と誤り率を (b) と比較せよ。
    1. 1 回の実行を $\{\text{good}, \text{bad}\}$ から $\{\text{pass}, \text{fail}\}$ への通信路とみなし、その通信路容量 $C = \max_{p(x)} I(X; Y)$、すなわちすべての入力分布にわたる入出力間の相互情報量の最大値（:numref:`sec_mdl-mutual-information`）を計算せよ。テストを適応的に選んだとしても、各実行が明らかにする量は高々 $C$ ビット（$k$ に関する情報量）である。ファノの不等式によれば、実行結果から計算される推定量 $\hat k$ は、誤り確率を $P_e = P(\hat k \neq k)$ とするとき、$H_b(P_e) + P_e \log_2 63 \geq H(k \mid \text{runs})$ を満たす（ここで $H_b$ は二値エントロピーである）。これを用いて、$k$ を少なくとも 0.95 の確率で特定する任意の戦略における平均実行回数の下界を求めよ。(c) はこの下界にどこまで迫っているか。
