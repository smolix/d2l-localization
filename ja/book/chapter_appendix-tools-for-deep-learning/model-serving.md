# モデルサービング

<!--en:d8564eaf-->
本書で扱ってきた言語モデルは、セルを実行した 1 人のために、ノートブック内でプロンプトを 1 つずつ処理してテキストを生成していた。では代わりに、100 人の同僚が同じ言語モデルへ好きなタイミングでリクエストを送るとしよう。もし GPU がそれらに 1 件あたり 2 秒ずつ順番に応答すれば、最後の同僚は 3 分以上待つことになる。モデルを呼び出すこととサービングすることの間では、何を変えなければならないのだろうか。

<!--en:4b845d92-->
サービングとは、1 基のアクセラレータに多数のリクエストを同時に処理させる仕組みである。1 トークンを生成するには、重みとキー・値キャッシュをメモリから読み出す（:numref:`sec_hardware_buyers`）。すべてのリクエストは重みを共有するため、メモリがアクティブな全リクエストのキャッシュを保持できる限り、多数のリクエストを同じステップで進めるエンジンは全員分の重みを 1 回読み出すだけで済む。本節ではまずユーザーが体感するレイテンシの数値から始め、2026 年 11 月時点におけるローカル用およびサーバー用のエンジンを概観したうえで、エンジンを高速化する技法を解説する。

<!--en:8e52e143-->
## ワークロードとレイテンシ指標

<!--en:94a4c9ff-->
チャットアシスタントのユーザーは、最初の単語が現れるまでの待ち時間と、それに続く単語が表示される速度という 2 つの遅れに気づく。1 つ目はリクエストの到着から計測される**最初のトークンまでの時間**（time to first token、TTFT）である。アイドル状態のサーバーでは、これはすべてのプロンプトトークンを並列に処理し計算律速（compute-bound）となる*プレフィル*に支配される。2 つ目は**出力トークンあたりの時間**（time per output token、TPOT）であり、系列ごと・ステップごとに 1 トークンを生成しメモリ帯域幅律速（memory-bandwidth bound）となる*デコード*に支配される。全ユーザーについて合計した毎秒トークン数であるスループットは、これら両方とトレードオフの関係にある。

<!--en:776644ad-->
![プロンプトのプレフィルは並列処理であり計算負荷が高くなりやすい。一方、自己回帰デコードは系列ごとに 1 トークンずつ進み、メモリ転送に負荷をかける。](../img/tools-prefill-decode.svg)

<!--en:bb6f6412-->
どの数値が重要になるかはワークロード次第であり、ワークロードによって選ぶべきツールが決まる。

<!--en:112f3221-->
:サービングのワークロードと出発点の例（2026 年 11 月時点）

<!--en:8d76a1b1-->
| ワークロード | 最適化対象 | 出発点 |

<!--en:763f96de-->
| 手元のマシン上の個人用アシスタント | 簡便さ、プライバシー | Ollama / LM Studio（llama.cpp）、Mac では MLX |

<!--en:4f415ada-->
| オフラインのバッチスコアリング | ドルあたりのスループット | vLLM オフラインモード |

<!--en:10d53be5-->
| 単一アプリケーションの API | 運用性 | 軽量な認証プロキシ配下の vLLM |

<!--en:72e8b470-->
| マルチユーザー / エージェント型サービス | SLO 下でのグッドプット | vLLM または SGLang、大規模化時は NVIDIA Dynamo |

<!--en:1776ee70-->
| 固定された NVIDIA 環境での最大スループット | GPU あたりのスループット | TensorRT-LLM |

<!--en:179436d5-->
サービスレベル目標（service level objective、SLO）は、TTFT を 1 s 未満にするといったレイテンシ目標を定める。目標も満たした完了リクエストのレートである*グッドプット*こそが、本番環境における評価指標である。過負荷状態では、リクエストがキューに滞留して目標を逃すようになるため、生のスループットが上がってもグッドプットは崩壊しうる。

## ローカルサービング

<!--en:8aed1fd9-->
ユーザーが 1 人のノート PC やワークステーションでは、モデルがメモリに収まるか、そしてどれだけ速く応答するかが問題となる。多くのローカル推論ツールは **llama.cpp** とその **GGUF** ファイル形式を採用しており、コミュニティのリポジトリではオープンウェイトモデルの GGUF 変換版が広く公開されている。ユーザーはラッパを介して llama.cpp を利用することが多い。

<!--en:aff32ff0-->
* **Ollama** は llama.cpp を基盤とし、Apple シリコン上では MLX も利用する。`ollama run qwen3:8b` を実行するとモデルのダウンロード、キャッシュ、サービングが一括で行われ、`http://localhost:11434/v1` で OpenAI 互換 API が提供される。

<!--en:3137bd3e-->
* **LM Studio** は同じエンジンをグラフィカルインターフェース経由で提供し、モデルのどの程度を GPU にオフロードするかを制御できる。

<!--en:ea40b5fd-->
* **MLX** は Apple の配列フレームワークである。パッケージ `mlx-lm` によって Apple シリコン上でモデルの実行とファインチューニングが可能であり、Hugging Face 上の `mlx-community` オーガニゼーションが数千もの変換済みモデルを公開している。

<!--en:7bed0d9f-->
代表的な GGUF の量子化形式には、`Q4_K_M`（重みあたり約 4.9 ビット）、`Q5_K_M`（約 5.7 ビット）、`Q8_0`（約 8.5 ビット）がある。Qwen3-8B の 82 億個のパラメータに対して `Q4_K_M` を用いると $8.2 \times 10^9 \times 4.9 / 8 \approx 5.0$ GB となり、Ollama の `qwen3:8b` のダウンロードサイズである 5.2 GB に近い。この 4.9 ビットという値は Llama 3.1 8B で計測されたものであり、`Q4_K_M` はモデルに応じた割合のテンソルをより高い精度で保持する。最大 32,768 トークンのコンテキスト全体を bf16 でキャッシュすると、ほぼ同程度の容量がさらに加わる。一般にビット数の多い形式ほど品質はよく保たれるため、自身のタスクで影響を計測するとよい。デコード速度は高々、メモリ帯域幅をトークンあたりの読み出しバイト数で割った値になるため、ビット数を増やすごとにメモリだけでなく速度も犠牲になる。定石は、キャッシュ用の余裕を残して量子化後の重みがメモリに収まる最大のモデルを選び、次にその範囲内で収まる最もビット数の高い形式を選ぶことである。

## サーバーエンジン

<!--en:2dd63b8c-->
### オープンソースエンジンと NVIDIA エンジン

<!--en:518ac29a-->
共有サーバーには、複数のリクエストをまとめてスケジューリングするエンジンが必要である。オープンソースの GPU サーバー向けには、**vLLM** が連続バッチング（continuous batching）、ページド KV キャッシュ管理、プレフィックスキャッシュ、テンソル並列（tensor parallelism）、量子化モデルのサポート、および OpenAI 互換サーバーを 1 つのコマンドで提供する。

<!--en:4c2eaadf-->
**SGLang** はこれに最も近い競合エンジンである。その *RadixAttention* :cite:`Zheng.Yin.Xie.ea.2024` は、キャッシュ済みのキーと値をリクエスト間で共有される基数木（radix tree）に保持するため、システムプロンプトを伴うチャット、同じ文書群に対する検索、あるいは木状に広がるエージェント呼び出しのように、多数のリクエストが長いプレフィックスを共有する場面で威力を発揮する。両プロジェクトとも急速に進化しており、複数のアクセラレータバックエンドをサポートしているため、プロンプト長と同時接続数の実際の分布で両者をベンチマークしてから選ぶべきである。

<!--en:469cf17d-->
NVIDIA のツール群は、移植性と引き換えにハードウェア固有の最適化を追求する。**TensorRT-LLM** は NVIDIA がチューニングしたカーネルを用いて PyTorch 上でモデルを実行し、セットアップの手間が増える代わりに定常状態のスループットを高められる。**Dynamo** は vLLM、SGLang、または TensorRT-LLM をバックエンドとして多数の GPU とノードを協調動作させる。プレフィルとデコードを別々の GPU プール上で実行し、ワーカーの負荷やプレフィックスがすでにどれだけキャッシュされているかに応じて各リクエストをルーティングする。これらのツールが重要になるのはデータセンタ規模においてであり、数基の GPU であれば vLLM や SGLang 単体のほうが簡潔である。

<!--en:70576e59-->
### 共通のクライアント API

<!--en:31d9815b-->
ノート PC からサーバーへ移行する際に、アプリケーションの書き直しが必要になるべきではない。これらのツールの多くは OpenAI の Chat Completions API を実装しているため、ベース URL とモデル名を変更するだけで、同じクライアントコードからローカルの Ollama、自前の vLLM サーバー、あるいは商用プロバイダを利用できる。

<!--en:9bc909dd-->
もっとも、同じリクエストを受け付けるサーバーであっても応答の挙動が同じとは限らない。トークン化、サンプリングのデフォルト設定、構造化出力のサポート、ストリーミングの挙動、トークン数の集計方法はいずれもサーバーごとに異なる。小規模な適合性テスト（conformance test）を用意しておき、エンジンを入れ替える前に再実行するとよい。

## エンジンの技法

<!--en:fd3ff5d4-->
組み合わせ可能な 4 つの技法によって、これらのエンジンの速さの大部分を説明できる。

<!--en:a5e13069-->
**連続バッチング。**静的バッチは最も遅いリクエストの完了を待つ。これに対し連続バッチングは、デコードステップの合間に新しいリクエストを受け入れ、完了したリクエストを退出させることで、バッチをほぼ満杯に保つ。

<!--en:62053be5-->
![下の簡易スケジューラと同様に、出力トークン数が 5、2、7、3 のリクエストを 2 つのバッチスロットで処理する例。静的バッチ化は各バッチを最長の要素に合わせてパディングするが、連続バッチングは完了したスロットを次のステップで補充し、12 ステップではなく 9 ステップで完了する。](../img/tools-continuous-batching.svg)

<!--en:08e1a195-->
以下の簡易スケジューラは、この仕組みを数行で表現したものである。演習問題 :exref:`ex_model-serving-arrivals` では、これに到着時刻とメモリバジェットを加えて拡張する。

<!--en:142f2586-->
**ページド KV キャッシュ。**アクティブな各系列のキー・値キャッシュは、系列長とともに増大する。vLLM の PagedAttention :cite:`Kwon.Li.Zhuang.ea.2023` は仮想メモリと同様にこれを固定サイズのブロック単位で割り当てることで、かつてバッチサイズの上限となっていた断片化をほぼ解消する。ここから容量設計の原則が導かれる。すなわち、GPU メモリには重みに*加えて*同時実行される全系列のキャッシュが収まらなければならない。したがって、1 件のリクエストなら収まるモデルであっても、高い同時接続数の下ではメモリを超過しうる。

<!--en:ce8ea209-->
**プレフィックスキャッシュ。**2 つのリクエストがトークン化後のプレフィックス（同じシステムプロンプトや同じ文書）を共有している場合、そのキャッシュされたキーと値は 1 回計算するだけで再利用できる。

<!--en:fd767b0c-->
![プレフィックスキャッシュはトークン化後のプレフィックスが一致する場合にのみ KV 状態を再利用し、その後で各リクエスト固有のサフィックスを計算する。](../img/tools-prefix-cache.svg)

<!--en:a9671e2b-->
商用 API のなかには、プロバイダごとに異なる規則の下で、キャッシュされた入力トークンの料金を割り引くものがある。そのため、プロンプトの可変部分より前に共有される固定的な内容を配置すれば、プレフィル時間だけでなく費用も節約できる。

<!--en:761e9843-->
**投機的デコーディングと量子化。**投機的デコーディング（speculative decoding）では、小規模なドラフトモデルが複数のトークンを提案し、ターゲットモデルが 1 回の並列パスでそれらを検証する。提案の大半が受理される場合には、ターゲット分布を保ったままデコーディングを高速化できる。一方、量子化はデコード時に読み出すバイト数を削減する。重みあたりのバイト数が減れば毎秒トークン数は増えるが、極端に低いビット幅では品質が劣化する。近年の NVIDIA テンソルコアは FP8（Hopper および Ada 世代以降）と NVFP4（Blackwell 以降）をサポートしており、vLLM や SGLang は 4 ビットの AWQ 重みも読み込める。ローカル環境では GGUF 形式が同じ役割を果たす。

## 運用

<!--en:f5398fb9-->
ポートを待ち受けているだけのエンジンには、共有サービスに必要な制御機構がまだ備わっていない。エンジンの前段にプロキシを置いて認証、TLS、レート制限を担わせ、エンジン自体のポートは外部に公開しないようにする。受付制御（admission control）では、メモリ不足（out-of-memory）エラーが起きた後ではなく、メモリが枯渇する*前*にリクエストを拒否またはキューイングすべきである。クライアントからのキャンセルを伝播させ、放棄された生成処理が計算資源を消費し続けないようにする。TTFT、TPOT、およびエンドツーエンドのレイテンシは、閉ループのクライアント群による平均値ではなく、現実的な到着パターンの下での p50 と p95 として計測する。デフォルトでは生のプロンプトをログに残さないようにする。さらに、モデル、トークナイザ、量子化、エンジンのバージョンを一括でピン留めする。より高速でも異なる応答を返すサーバーは別物のシステムであるため、ロールアウトの可否はレイテンシだけでなくタスク品質でも判定しなければならない。

<!--en:e0a2b9d7-->
ここまでで、モデルとユーザーのキャッシュが 1 枚のカードに収まるか、そして最初にどのエンジンを試すべきかを見積もれるようになった。負荷の下でサーバーがどのようにリクエストを受け入れ、順序付けるべきかという問いはまだ残されており、演習問題のシミュレータでこれを探究する。

## まとめ

<!--en:bcb43b23-->
サービングのレイテンシは、最初のトークンまでの時間（TTFT）を決める計算律速のプレフィルと、出力トークンあたりの時間（TPOT）を決める帯域幅律速のデコードに分かれる。ローカルでの Ollama、LM Studio、MLX から、共有サービス向けの vLLM や SGLang、さらには大規模な NVIDIA 環境にわたる TensorRT-LLM と Dynamo の組み合わせまで、ワークロードに合わせてエンジンを選ぶ必要がある。ローカルの GGUF 形式やサーバーの AWQ、FP8、NVFP4 による量子化は、極端に低いビット幅で品質が劣化するまでは、削減した重みのバイト数をそのまま高速なトークン生成へと変える。現代のエンジンは連続バッチング、ページド KV キャッシュ、プレフィックスキャッシュ、投機的デコーディングを組み合わせており、クライアント側のプロンプトの並べ方によって再利用できるプレフィックス状態の量が決まる。OpenAI 互換の Chat Completions API によりローカルとクラウドのサーバー間でクライアントコードの移植性は保たれるものの、細かな挙動の違いがあるため、エンジンを切り替える前には小規模な適合性テストを行うべきである。最後に、メモリ容量にはモデルの重みと同時接続する全ユーザーの KV キャッシュがともに収まらなければならず、本番環境での運用には受付制御、クライアントのキャンセル伝播、テールレイテンシの監視、およびモデルとエンジンのバージョンの一括ピン留めが不可欠である。

## 演習問題

<!--en:6088e58b-->
1. **バッチサイズの上限。**コマンド `vllm serve Qwen/Qwen3-8B` は、$L = 36$ 層、次元 $d_h = 128$ のキー・値ヘッド $H_\textrm{kv} = 8$ 個をもち、bf16 の重みが $B_w = 16.4$ GB を占めるモデルをサービングする。キャッシュも同様に bf16 で保存される。これをメモリ帯域幅が $\beta = 3.35$ TB/s、密な bf16 演算レートが 989 TFLOP/s（:numref:`tab_gpu_specs`）である H100 SXM 上でサービングせよ。1 回のデコードステップでは、バッチ全体に対して重みを 1 回読み出し、アクティブな全系列のキャッシュを読み出す。それぞれが $n$ 個のキャッシュ済みトークンを保持する $b$ 本の系列に対し、このステップ（すなわち各系列の出力トークンあたりの時間）にかかる時間はおよそ次の式で与えられる。

   $$t(b) = \frac{B_w + b\, n\, B_\textrm{kv}}{\beta},$$

   ここで、$B_\textrm{kv}$ はトークンあたりのキャッシュサイズである。
    1. 各層はキー・値ヘッドごと、トークンごとに 1 つのキーベクトルと 1 つの値ベクトルを保存するため、$B_\textrm{kv} = 2 \cdot L \cdot H_\textrm{kv} \cdot d_h \cdot (\textrm{bytes per element})$ となる（:numref:`sec_kv-cache`）。$B_\textrm{kv}$ を計算せよ。次に、TPOT とスループット $b / t(b)$ を、$n = 2048$ のもとで $b \in \{1, 8, 64, 256\}$ について評価せよ。$b$ が大きくなるときスループットはどの値に近づき、$t(b)$ のどの項がそれを決めるか。また、82 億個のパラメータに対してパラメータ・トークンあたり 2 FLOPs として計算し、bf16 演算レートと照らし合わせて、$b = 256$ におけるステップが依然としてメモリ転送によって律速されていることを確かめよ。
    1. ある対話型サービスが TPOT を最大 20 ms 以内に抑えると約束している。実行できる最大のバッチサイズはいくらか。これに対し、:numref:`tab_serving_workloads` のオフラインスコアリングジョブであればどのバッチサイズを選ぶか。また、それはなぜか。
    1. エンジンがカードのメモリのうち 72 GB を重みとキャッシュに使用し、各系列が平均 2,048 トークンを保持するとする。ページドキャッシュ以前は、サーバーはリクエストごとにその最大長分の連続領域を 1 つ予約していた。各系列が `--max-model-len` である 32,768 トークン分を予約するとき、何本の系列が収まるか。またそのとき、予約されたキャッシュのうち実際にトークン状態を保持している割合はいくらか。:citet:`Kwon.Li.Zhuang.ea.2023` はそのようなシステムで 20.4%〜38.2% という値を計測しているが、ここで求めた割合がそれより低くなるのはなぜか。さらに、キャッシュを 16 トークンのブロック単位で割り当てる場合には何本の系列が収まるか。部分的にしか埋まっていないブロックが無駄にするメモリ量の上界を求めよ。
    1. 2 つの割り当て方式のそれぞれにおいて、対話型サービスのバッチサイズを決める上限はメモリと TPOT 目標のどちらか。
   :exlabel:`ex_model-serving-batch-limits`

1. [code] **適合性テスト。**:numref:`subsec_model-serving-contract` では、エンジンを入れ替える前に小規模な適合性テストを行うことを勧めている。

1. **投機的サンプリング。**● :citet:`Leviathan.Kalman.Matias.2023` の投機的デコーディングでは、次トークン分布 $q$ をもつドラフトモデルがトークン $x \sim q$ を提案し、次トークン分布 $p$ をもつターゲットモデルがそれを確率 $\min(1, p(x) / q(x))$ で受理する。棄却された場合、トークンは次の残差分布から代わりに抽出される。

   $$p'(x) = \frac{\max(0, p(x) - q(x))}{\sum_{x'} \max(0, p(x') - q(x'))}.$$

    1. 出力されるトークンが $p$ に従うこと、および受理確率が $\beta = \sum_x \min(p(x), q(x))$ となることを示せ。
    1. 各ラウンドにおいて、ドラフトモデルは $\gamma$ 個のトークンを順次に提案し、ターゲットモデルの 1 回のパスがそれらすべてにスコアを付ける。ターゲットモデルは最初の棄却までの受理されたトークンを出力し、続けて自身のトークンを 1 つ出力する（棄却後は $p'$ から抽出し、$p$ からは全 $\gamma$ トークンが受理されたときに抽出する）。$\alpha$ を、第 1 小問の受理確率 $\beta$ を系列の各位置にわたって平均した値とし、各ドラフトトークンが独立に確率 $\alpha$ で受理されると仮定する。1 ラウンドで出力されるトークン数の期待値が $(1 - \alpha^{\gamma + 1}) / (1 - \alpha)$ となることを示せ。ドラフトの 1 ステップにはターゲットの 1 ステップの $c$ 倍の時間がかかり、スコアリングのパスにはターゲットの 1 ステップ分の時間がかかるとする。通常のデコーディングに対する期待高速化率を導出し、最適な $\gamma$ を $c = 0.05$ および $\alpha \in \{0.6, 0.8, 0.9\}$ について求めよ。
    1. スコアリングのパスがターゲットの 1 ステップ分の時間で済むのは、メモリ転送によって律速されている間だけである。サーバーが $b$ 本の系列をまとめてデコードし、各系列がラウンドあたり $\gamma + 1$ 個の位置にスコアを付けるとする。キャッシュは無視し、重みは bf16 で保存し、パラメータ・トークンあたり 2 FLOPs として数えよ。$b$ がいくつを超えると、演習問題 :exref:`ex_model-serving-batch-limits` の H100 上で $\gamma = 4$ のときにこのパスが計算律速になるか。このことは、単一ユーザーの場合と比べて、高負荷サーバーにおける投機的デコーディングに何を意味するか。

[extended] **負荷下でのグッドプット。**●● 演習問題 :exref:`ex_model-serving-arrivals` のシミュレータを、時計がデコードステップではなく秒単位で進むものへと拡張せよ。対象は、演習問題 :exref:`ex_model-serving-batch-limits` の H100（重みとページドキャッシュ用に 72 GB を使用）上で稼働する Qwen3-8B とする。1 ステップでは、$p$ 個のプロンプトトークンと、デコード中の $b$ 本の系列それぞれの 1 トークンを処理し、これらの系列は合わせて $K$ 個のキャッシュ済みトークンを保持している。パラメータ数 $N$、密な bf16 演算レート $F$、および演習問題 :exref:`ex_model-serving-batch-limits` の記法を用いると、このステップにかかる時間は次の式となる。

   $$t_\textrm{step} = \max\left(\frac{2N(p + b)}{F}, \frac{B_w + K B_\textrm{kv}}{\beta}\right),$$

   ただし、ここではアテンションスコアの FLOPs は無視している。リクエストは毎秒 $\lambda$ 件のポアソン過程として到着し、プロンプト長は 500 から 4,000 トークンの一様分布に従い、出力長は 1 に平均 250 の指数確率変数を加えて小数点以下を切り捨て、2,048 を上限とした値とする。リクエストの TTFT が 1 s 以下であり、かつ出力トークン間の平均時間である TPOT が 50 ms 以下であるとき、そのリクエストをグッドプットに算入する。
    1. 受け入れられたすべてのプロンプトを 1 ステップ内で完全にプレフィルせよ。シミュレーションを行う前に、$t_\textrm{step}$ から飽和レートを見積もれ。次に、$\lambda$ を軽負荷から飽和を十分に超える領域までスイープし、スループットとグッドプットを毎秒リクエスト数でプロットせよ。グッドプットがピークに達するのはどのレートであり、事前の見積もりと比べてどうなっているか。
    1. 長いプロンプトを完全にプレフィルすると、デコード中のすべての系列で次のトークンが遅延する。ステップあたりのトークン数（デコードトークンを含む）をバジェット以下に制限し、1 つのプロンプトを複数ステップに分割するチャンク化プレフィル :cite:`Agrawal.Kedia.Panwar.ea.2024` を実装せよ。512、2,048、8,192 トークンの各バジェットについてスイープを繰り返せ。グッドプットを最大化するバジェットはどれか。また、その答えは 2 つの SLO にどのように依存するか。
    1. TTFT の目標をもはや満たせないと判明した時点でリクエストを拒否する受付制御を追加せよ。飽和を超えた領域でグッドプットはどう変化するか。受付制御がない場合に、スループットが高いままグッドプットが崩壊する理由を説明せよ。
    1. すべてのクライアントが 10 s 後にリクエストを放棄して 1 回だけ再送するものとせよ。放棄されたリクエストをサーバーが生成し続ける場合とキャンセルする場合とで、グッドプットを比較せよ。
    1. 拒否されたリクエストも未達成として数えたとき、到着する全リクエストの少なくとも 90% が両方の SLO を満たす最大のリクエストレートと、それを達成する設定を述べよ。

静的バッチ化は最長の生成が終わるまで $b$ 件のリクエストを拘束するため、短い応答が先に終わるたびに GPU スロットが無駄になる。

<!--en:e2374378-->
- **反復単位のスケジューリング（連続バッチング）：**
  - *毎回のデコードステップ*の終了時に、エンジンは `<eos>` を出力したか `max_tokens` に達した系列を確認する
  - 完了した系列はただちに退出して KV キャッシュブロックを解放し、キューで待機中のリクエストがすぐ次のステップからバッチに入る

<!--en:f04035e4-->
- **出力トークン数 `[5, 2, 7, 3]` のリクエストを 2 スロットで処理した結果：**連続バッチングは全 4 件のリクエストを **12 ステップではなく 9 デコードステップ**で完了する（ステップ数 $25\%$ 削減、スロット稼働率は $71\%$ から $94\%$ へ向上）

<!--en:9c345563-->
::: {.slide title="連続バッチングスケジューラのコードによるシミュレーション"}

<!--en:86fa69b7-->
[実行可能なスケジューラ]{.kicker}

<!--en:956d53cb-->
わずか 10 行の Python コードで、反復単位の連続バッチングループの中核となる状態マシンを表現できる。

<!--en:24d8be3d-->
- **ステップごとのスロット補充：**
  - ステップ 1 は `(5, 2)` で始まる。2 ステップ後に 2 トークンのリクエストが完了し（残りは `(3,)`）、7 トークンのリクエストがただちにスロット 2 に入る（`(3, 7)`）
  - ステップ 5 で最初のリクエストが完了すると、最後の 3 トークンのリクエストが残り 4 トークンとなった 7 トークンのリクエストに合流し（`(4, 3)`）、単独実行となる末尾は最後の 1 ステップだけになる

<!--en:0a78e147-->

<!--en:993f397d-->
[エンジンの技法 2]{.kicker}

<!--en:e64996d6-->
- **連続領域確保の無駄（`max_len=32,768`）：**$4.83\text{ GB/seq}$ を H100 の空き VRAM $55.6\text{ GB}$ から予約するため、**$b = 11$ 系列**しか収まらず、予約済み KV メモリの $93.7\%$ が未使用のまま残る（$n = 2{,}048$ 時）

<!--en:065fdfad-->
- **PagedAttention（16 トークンの仮想ブロック）：**$2.36\text{ MB}$ のブロックをオンデマンドで割り当て（内部の無駄は $< 0.7\%$）、同時実行容量を **$16.7\times$ の $b = 184$ 系列**へ拡大するため、$20\text{ ms}$ の TPOT SLO（$b = 167$）が先に制約となる

<!--en:ae76088e-->
::: {.slide title="プレフィックスキャッシュとキャッシュヒットのためのプロンプト設計"}

<!--en:8cc6044e-->
[エンジンの技法 3]{.kicker}

<!--en:724274b8-->
複数のリクエストが先頭のトークン列（システム指示、few-shot の例、リポジトリのコンテキストなど）を共有している場合、**プレフィックスキャッシュ**はプレフィルを再実行せずに計算済みの KV ブロックを再利用する。

<!--en:d13f2600-->
- **連鎖ブロックハッシュ：**因果的自己アテンションではトークン表現が先行するすべてのトークンに依存するため、16 トークンの各ブロックは $\text{hash}(\text{parent\_block\_key}, \text{token\_ids})$ をキーとする

<!--en:adcaf5c9-->
- **30 ターンのコーディングエージェント（基本コンテキスト $20\text{K}$ ＋ターンあたり $1\text{K}$ 追加）：**
  - キャッシュなしのプレフィル計算量は $\sum_{k=0}^{29} (20 + k)\text{K} = \mathbf{1{,}035{,}000\text{ tokens}}$ に達する
  - プレフィックスキャッシュありでは $20\text{K} + 29 \times 1\text{K} = \mathbf{49{,}000\text{ tokens}}$ のみで済む（**プレフィル計算量を $21\times$ 削減**）

<!--en:ec27b42a-->
- **プロンプト設計の原則：**システムプロンプトの 1 行目に秒単位のタイムスタンプを入れてはならない（ブロック 0 からハッシュ連鎖が無効化されるため）。変動するメタデータはプロンプトの*末尾*に置く

<!--en:a89d9df7-->
::: {.slide title="投機的デコーディングとサーバー量子化"}

<!--en:8f14c006-->
[エンジンの技法 4]{.kicker}

<!--en:99ef6cb8-->
- **ドラフト提案と並列検証：**小規模なドラフトモデル $q$（コスト $c \ll 1$）が $\gamma$ トークンを提案し、ターゲットモデルの 1 パス $p$ が全 $\gamma+1$ トークンを並列に検証することで、厳密なターゲット分布を保つ（$2.80\times$ の高速化：$\alpha=0.8, \gamma=4, c=0.05$ の場合）

<!--en:82cb739c-->
- **高負荷サーバーでの注意点：**並列検証が実質無償になるのはメモリ律速の間だけであり、H100（$I^* \approx 295$）ではバッチ $b > 295/(\gamma+1) = 59$ を超えると計算律速になる

<!--en:cd977368-->
::: {.slide title="チャンク化プレフィル、受付制御、運用"}

<!--en:804dd38b-->
[本番運用の信頼性]{.kicker}

<!--en:b1542776-->
- **チャンク化プレフィル：**長い 16K プロンプトを固定のステップバジェット（例：$2{,}048$ トークン/ステップ）に分割し、アクティブなデコードトークンを相乗りさせることで、プレフィルのバーストによる TPOT の急増を防ぐ

<!--en:b4716b67-->
- **受付制御・キャンセル伝播・一括ピン留め：**キュー長が TTFT の SLO を超えたら到着リクエストを早期に拒否し、切断された HTTP ストリームを中断し、前段に TLS・認証・レート制限プロキシを置き、`(model_sha, tokenizer, quant, engine)` を一括でピン留めする

[理解度チェック]{.kicker}

<!--en:a2fc0fd0-->
以下の 3 つのシナリオでサービングシステムの計算を確認してみよう。

<!--en:9a741ecd-->
1. 検索拡張生成（RAG）サービスにおいて、共有の 2,000 トークンのシステムプロンプトの後に、50 文書のコーパスから検索された 3 つの文書が続くとする。リクエスト 1 が `[Doc A, Doc B, Doc C]` を検索し、リクエスト 2 が `[Doc B, Doc A, Doc C]` を検索したとき、ブロックハッシュ方式のプレフィックスキャッシュの下でリクエスト 2 はどの KV ブロックを再利用するか。また、どうすればキャッシュヒットを増やせるか。

<!--en:040a11d1-->
2. Qwen3-8B をサービングする H100（平均コンテキスト $n = 2{,}048$、メモリバジェット $72\text{ GB}$）において、サービスが $\text{TPOT} \le 20\text{ ms}$ の SLO（$b_{\max,\text{SLO}} = 167$）を課すとする。連続領域の `max_model_len=32768` 割り当て（$b_{\max,\text{mem}} = 11$）と PagedAttention（$b_{\max,\text{mem}} = 184$）のそれぞれにおいて、バッチサイズを制限するのはどちらの制約か。

<!--en:557b98b6-->
**解答：**

<!--en:e857af46-->
1. リクエスト 2 が再利用するのは **2,000 トークンのシステムプロンプトのみ**である。位置 2001 に置かれるのが `Doc B` であり `Doc A` ではないため、トークン 2001 以降のすべてのブロックハッシュが変化する。検索された文書を**正規化された ID 順**（`[Doc A, Doc B, Doc C]`）に並べれば、部分集合の先頭文書が一致するたびにプレフィックス全体を再利用できる（関連度順による位置バイアスとのトレードオフになる）。

<!--en:609faaad-->
2. **連続領域確保**では、**メモリ容量が先に制約となる**（$11 \ll 167$ であり、GPU が遊休状態になる）。**PagedAttention** ではメモリに $184$ 系列が収まるため、**$20\text{ ms}$ の TPOT レイテンシ SLO が先に制約となり**、バッチサイズは $b = 167$ で頭打ちになる。

<!--en:a2cd1cc1-->
::: {.slide title="概念チェック：KV キャッシュ、バッチ化、プレフィックス再利用（続き）"}

<!--en:929b7671-2-->
[理解度チェック]{.kicker}

<!--en:4b0228ef-->
3. ドラフトコスト $c = 0.05$、受理率 $\alpha = 0.8$、ドラフトトークン数 $\gamma = 4$ の投機的デコーディングにおいて、標準のバッチサイズ 1 のデコーディングに対する期待高速化率はいくらか。

<!--en:23db34b8-->
**解答：**

<!--en:19f1302a-->
3. ラウンドあたりの期待トークン数は $= (1 - 0.8^5) / (1 - 0.8)$ $= 0.67232 / 0.2 = \mathbf{3.362\text{ tokens}}$、所要時間は $1 + 4(0.05) = \mathbf{1.20\text{ target steps}}$ となり、**$\mathbf{2.80\times}$ の高速化**が得られる。

[重要ポイント]{.kicker}

<!--en:9096ab99-->
| サービングの構成要素 | 物理的・アルゴリズム的原理 | 本番エンジニアリングの原則 |

<!--en:986a80e3-->
| **プレフィルとデコード** | プレフィルは並列かつ計算律速（TTFT を決定）、デコードは逐次かつ帯域幅律速（TPOT を決定） | プレフィルはテンソルコアとプレフィックスキャッシュで最適化、デコードはバッチ化と量子化で最適化 |

<!--en:6c5590a7-->
| **バッチデコードのスケーリング** | $t(b) = (B_w + b \, n \, B_{\text{kv}}) / \beta$ | バッチ化は重み読み出し $B_w$ を償却し、KV キャッシュ帯域幅 $b \, n \, B_{\text{kv}}$ または TPOT の SLO が $b$ の上限となる |

<!--en:09713019-->
| **連続バッチング** | 各デコードステップで完了系列を退出させスロットを補充 | 静的パディングの空き時間を解消し GPU スロット稼働率を向上 |

<!--en:e99d33b4-->
| **PagedAttention** | KV キャッシュを 16 トークンの仮想ブロック単位でオンデマンド割り当て | 連続領域確保の $\sim 90\%+$ の無駄を解消し同時実行バッチ容量を $> 10\times$ に拡大 |

<!--en:0f1b10f1-->
| **プレフィックスキャッシュ** | 一致する連鎖ブロックハッシュ間で KV ブロックを再利用 | 静的なシステムプロンプトや正規化コンテキストを動的なタイムスタンプやユーザークエリの*前*に配置 |

<!--en:f5d4a93f-->
| **グッドプットと受付制御** | 過負荷はキューを肥大化させ、生のスループットは高いままグッドプットが崩壊 | チャンク化プレフィル、TTFT に基づく早期受付制御、クライアントキャンセル伝播を導入 |
