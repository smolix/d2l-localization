# 分散モデル訓練

<!--en:31fbbddd-->
:numref:`chap_performance` のマルチ GPU に関する各節では、1 台のマシン上の 4 基の GPU それぞれにモデルのコピーを持たせることで ResNet と GPT を訓練し、さらに訓練状態を GPU 間で分割することで単一の GPU には収まらないモデルのための領域をどう確保するかを導出した。実務でファインチューニングされるモデルは、それよりさらに大きいことも珍しくない。70 億パラメータの言語モデルを Adam で訓練する場合、活性化値を 1 つも保存する前の時点で、重み、勾配、およびオプティマイザ状態（optimizer state）だけで約 112 GB を必要とする。これは H100 の 80 GB を上回っており、このようなモデルを 1 基の GPU 上でゼロから訓練しようとすれば何年もかかるだろう。

<!--en:b56d6631-->
1 回の訓練実行における状態と計算を、場合によっては複数のマシンにまたがる多数のアクセラレータに分散させ、同じ結果をより短時間で計算するにはどうすればよいだろうか。どの解決策も何かを分割する。すなわち、バッチ、訓練状態、層、あるいは系列である。分割を増やすたびに通信が加わり、ワーカーを 1 つ追加するたびに実行が失敗しうる箇所が 1 つ増える。したがって、実測済みの単一デバイスのベースラインから出発し、観測されたメモリまたはスループットの制約を取り除く最も単純な手法を追加していく。本節では、各手法を取り除く制約の順に並べ、2026 年 11 月時点でそれらを実装しているライブラリに対応づけ、最後に数週間に及ぶ実行を途切れさせないための実践手法を扱う。

## 並列性の形態

<!--en:0ff34f78-->
### スケーリングラダー

<!--en:d7bd8d9e-->
以下の各手法は、1 つ前の手法の限界を取り除く代わりに通信を増やすため、*スケーリングラダー*（:numref:`fig_tools_training_ladder`）の段を上るように順番に採用していく。

<!--en:55fbf3be-->
![実用的なスケーリングラダーは、単一のアクセラレータから複製、シャーディング、複合的な並列性へと段階的に進む。](../img/tools-training-ladder.svg)

<!--en:19311187-->
1. **単一のアクセラレータ**で基準を確立する。具体的には、損失曲線、毎秒トークン数または毎秒データ例数、ピークメモリ、そして信頼できるチェックポイントである。

<!--en:385fa20b-->
1. **データ並列**（data parallelism、DDP）は、すべての GPU 上にモデルを複製し、それぞれにバッチの異なるスライスを入力して、各逆伝播の後に勾配を平均する。モデル、勾配、オプティマイザ状態が 1 つのデバイスに収まる限り、常にこれが適切な選択肢となる。

<!--en:e2839387-->
1. **完全シャーディングデータ並列**（fully sharded data parallelism、FSDP）は ZeRO ファミリのステージ 3 にあたり、パラメータ、勾配、オプティマイザ状態を複数の GPU にシャーディングし、各層が使用されている間だけ集約する（:numref:`subsec_mgp-fsdp`）。これによりデバイスあたりの状態メモリは GPU 数分の 1 になり、通信量は DDP の約 1.5 倍となる。

<!--en:2d06d5b3-->
1. **テンソル並列、パイプライン並列、コンテキスト並列、エキスパート並列**（tensor, pipeline, context, and expert parallelism）はそれぞれ、個々の層、連続する層のグループ、系列次元、および混合エキスパート（mixture of experts、:numref:`sec_moe`）の各エキスパートを分割する。単一の軸だけでは十分にスケールしないため、大規模システムではこれらのいくつかを組み合わせる。

<!--en:6c259180-->
PyTorch では、DDP と FSDP の実行にランチャとラッパが必要である。

<!--en:4d947696-->
`train.py` の内部では、`DistributedDataParallel(model)` が DDP を適用し、`fully_shard(model)`（`torch.distributed.fsdp` で提供）が FSDP を適用する。FSDP2 と呼ばれるこの API は、シャーディングされた各パラメータを `DTensor` として保持するものであり、PyTorch は従来の `FullyShardedDataParallel` ラッパよりもこちらを推奨している。JAX では、配列がデバイスメッシュ上の `NamedSharding` を持ち、それらの配置が意味する集団通信（collective）を `jax.jit` がコンパイルする（:numref:`sec_multi_gpu_concise`）。

<!--en:9ffe9991-->
テンソル並列はすべての層の内部で活性化値を交換するのに対し、パイプライン並列はステージの境界でのみ活性化値を送信する。Hugging Face の *Ultra-Scale Playbook*（4,000 回を超える実行を最大 512 基の GPU 上で行った調査に基づく）によると、テンソル並列を 1 台の 8 GPU ノードから 2 台へ広げると通常スループットの約 43% が失われたのに対し、各ステップのマイクロバッチ数が少ない条件下でパイプライン並列を同様に広げた場合の低下は 14% であった。テンソル並列は NVLink がトラフィックを運ぶノード内に留め、通信量が最大の集団通信を最も高速なリンクに割り当てるべきである。

<!--en:a82e512b-->
どの段においても 1 つの恒等式が成り立つ。オプティマイザから見たバッチサイズは次の式で与えられる。

<!--en:00a1b670-->
すなわち、デバイスあたりのバッチサイズに、データ並列のランク数と、オプティマイザの 1 ステップあたりに累積されるマイクロバッチ数を掛けた値である。したがって、デバイスあたりのバッチサイズや学習率を調整せずに GPU 数を変更すると、最適化問題そのものが変わってしまう。データに関してはさらに 2 つの原則がある。分散サンプラはデータ例を重複させてはならず、評価時には正しい分母を用いて検証指標を集約しなければならない。いずれかに違反することが、マルチ GPU 実行で異なる正解率が報告される主な原因である。

<!--en:1b9865b8-->
### 訓練メモリ

<!--en:567a9a13-->
大半のジョブが 1 基の GPU に収まらなくなる原因は訓練状態が入りきらないことにあるため、最初に行う計算はメモリバジェットの見積もりである（:numref:`fig_tools_training_memory`）。

<!--en:1d117875-->
![シャーディング、チェックポイント保存、勾配累積、オフロードはそれぞれ異なるメモリ項目を削減し、異なるコストをもたらす。](../img/tools-training-memory.svg)

<!--en:d6d93568-->
ピーク時の訓練メモリは、パラメータ、勾配、オプティマイザ状態、活性化値、通信バッファ、およびアロケータのオーバーヘッドの合計である。70 億パラメータのモデルを BF16 と Adam で訓練する場合、パラメータと勾配がそれぞれ 14 GB、Adam の 2 つの FP32 モーメント（一次モーメントと二次モーメント）が 56 GB を占める。混合精度訓練が保持するパラメータの FP32 マスターコピーがさらに 28 GB 加わり、合計 112 GB、すなわち 1 パラメータあたり 16 バイトとなる。以下の簡易モデルではその 28 GB のマスターコピーを省略し（GB の数値をそのまま GiB として流用すると、モデル状態は $14 + 14 + 56 = 84\text{ GiB}$ 残る）、18 GiB の活性化値と 5 GiB の一時バッファを加えている（合計 $107\text{ GiB}$）。大まかな計算ではあるが、各戦略の順位を正しく捉えており、GPU なしで実行できる。

<!--en:c47bf712-->
通常の訓練には 107 GiB が必要であり、80 GB の H100 の容量を超える。活性化チェックポイント（activation checkpointing）を併用した DDP でも、各 GPU 上になお 95 GiB が必要となる。84 GiB の状態が複製され、縮小するのは活性化値だけだからである。8 基の GPU 上でチェックポイント保存を併用した FSDP ならば、状態が 8 分割されるため、デバイスあたり 22 GiB で済む。

<!--en:f52d10b5-->
標準的なメモリ削減手法は、それぞれ異なるコストと引き換えに合計の異なる項目を変化させる。**混合精度**（mixed precision）は、選択されたテンソルと演算が使用するバイト数を減らす。**勾配累積**（gradient accumulation）は、:eqref:`eq_global_batch` のグローバルバッチを維持したままステップあたりのマイクロバッチを小さくして実行することで、モデル状態は変わらないものの活性化メモリ（activation memory）を削減する。**活性化チェックポイント**は、誤差逆伝播法（backpropagation）の最中に選択された活性化値を再計算する手法であり、メモリの節約量と計算オーバーヘッドはどの活性化値を保持するかに依存する。**CPU または NVMe オフロード**（DeepSpeed の ZeRO-Offload など）は、状態をデバイスメモリから移動させ、毎ステップにホスト・デバイス間の転送を追加する。**LoRA と QLoRA** は全重みの代わりに小さな低ランクアダプタを訓練することで、大半の勾配とオプティマイザ状態を不要にする。さらに QLoRA は凍結した重みを 4 ビットで保持するため、7B モデルを 1 枚の 16 GB カード上でファインチューニングできる。複数の手法は慎重に組み合わせる必要がある。個々には妥当な最適化であっても、コンパイル、通信と計算のオーバーラップ、あるいは数値精度と干渉することがあるからである。

## ソフトウェアライブラリ

<!--en:7d406ca9-->
1 ノードを超える規模では、これらの手法を手書きする人はほとんどいない。各手法はライブラリによって実装されており、どれを選ぶかは主にジョブの規模によって決まる。以下のプロジェクトは 2026 年 11 月時点で保守され広く使われていたものである。この領域は変化が速いため、採用する前に各プロジェクトの最新リリースを確認されたい。

<!--en:33f5f6db-->
**PyTorch の組み込み機能。**DDP と FSDP2 のほかにも、PyTorch には `DTensor` 上に構築されたテンソル並列およびコンテキスト並列の API と、パイプライン並列の API である `torch.distributed.pipelining` がある。ドキュメント上では依然として実験的（experimental）またはアルファ版と位置づけられているが、以下で紹介する上位ツールの大半はこれらのプリミティブへの呼び出しを生成する。

<!--en:fe24493f-->
**Hugging Face スタック。**`accelerate` はコードを変更することなく設定ファイルの切り替えだけで同じスクリプトを DDP、FSDP2、または DeepSpeed 上で起動する。その上に `transformers.Trainer` が載り、`peft` が LoRA と QLoRA を実装し、`trl` が教師ありファインチューニング、DPO、および GRPO 型の強化学習向けのトレーナを提供する。1 ノードまたは小規模クラスタにおける大半のファインチューニングジョブは、このスタックで賄える。

<!--en:073dadb5-->
**DeepSpeed。**ZeRO のステージ 1〜3（オプティマイザ状態、次いで勾配、さらにパラメータを順にシャーディングする）に加え、CPU および NVMe オフロードを提供する。現在 FSDP2 がネイティブに備えているシャーディングを導入したのは ZeRO であり、FSDP2 も状態を CPU メモリへオフロードできる。それでも、ジョブが NVMe へのオフロードを行う場合や、他のフレームワークが基盤として利用している場合には、依然として DeepSpeed が定番の選択肢である。

<!--en:3ffc5da7-->
**Megatron Core と TorchTitan。**大規模な事前学習（pretraining）向けのライブラリである。NVIDIA の Megatron Core は FP8 および FP4 訓練を伴うテンソル並列、パイプライン並列、コンテキスト並列、エキスパート並列を実装しており、Megatron-LM はそのリファレンス訓練スタックにあたる。TorchTitan はこれに相当する PyTorch ネイティブの実装であり、FSDP2 とテンソル並列、パイプライン並列、コンテキスト並列、エキスパート並列を組み合わせるコンパクトなリファレンススタックである。Llama 3 405B や DeepSeek-V3 を含むモデル定義を備え、最大 512 基の GPU での実測値も公開されている。いずれも複数の形態の並列性を同時に必要とするモデルに適している。

<!--en:55007933-->
**ファインチューニング用フロントエンド。**Unsloth は融合カーネルによる単一 GPU 上の高速な LoRA および QLoRA から始まり、現在ではフルファインチューニング、GRPO、およびマルチ GPU にも対応している。その高速化の度合いはモデル、系列長、ハードウェアに依存する。Axolotl は FSDP2 と DeepSpeed をバックエンドとして、1 つまたは複数のノード上でのフルファインチューニングやパラメータ効率的ファインチューニングを 1 つの YAML ファイルから駆動する。LLaMA-Factory も Web インターフェースを備えて同様の範囲をカバーしている。なお、PyTorch チームの `torchtune` は 2025 年に活発な開発を終了した。

<!--en:dc2faa5a-->
**JAX。**MaxText は TPU および GPU 上での事前学習と事後学習（post-training）のためのリファレンススタックである。Levanter を用いて訓練する Marin は、生データから最終モデルに至るまでの訓練実行を失敗した実験も含めて記録し、第三者が再現できるようにコード、データパイプライン、およびログを公開している。

<!--en:7c97c656-->
**強化学習による事後学習。**veRL は FSDP、FSDP2、または Megatron による訓練と、ロールアウト生成用の vLLM または SGLang とを組み合わせる。OpenRLHF は Ray、DeepSpeed、および vLLM の上に構築されている。

## 長時間実行における耐障害性

<!--en:154ed00e-->
10 日目にクラッシュして再開できない実行は、何も生み出さなかったのと同じである。ワーカー数が増えジョブの実行期間が長くなるにつれて、ハードウェア、ネットワーク、ソフトウェアの障害は日常茶飯事になるため、復旧の仕組みも訓練の他の部分と同様に設計・テストしておかなければならない。

<!--en:4e6556dd-->
* **完全かつアトミックにチェックポイントを保存する。**再開可能なチェックポイントには、モデル状態とオプティマイザ状態、学習率スケジュールとステップ数、データローダの位置、および乱数生成器（RNG）の状態が含まれる。書き込み途中に訓練プロセスがクラッシュしても直前のチェックポイントを破壊しないよう、一時パスに書き出してから完了時にリネームし、復元がテストされるまでは複数の世代を保持しておく。シャーディングされた（ランクごとの）チェックポイントを使えば、単一ホストのメモリを超える大きさのモデルを 1 か所に集約せずに済む。

<!--en:f24f9752-->
* **復旧の予行演習をしておく。**意図的にジョブを強制終了させ、新しいワーカー上で復元し、損失、ステップ数、およびデータの読み出し位置が何事もなかったかのように継続することを確認する。スポット価格のインスタンス（:numref:`sec_cloud_instances`）は中断のたびに再開できてこそコスト削減につながるため、それに頼る前に復旧をテストしておく必要がある。

<!--en:99bf43c1-->
* **アクセラレータへのデータ供給を絶やさない。**ストレージからの読み出し、デコードとデータ拡張、トークン化、およびホストからデバイスへの転送といったデータの読み込み処理を、演算とは切り離してプロファイリングする。入力待ちが生じる GPU はスループットが低下し、データ律速のジョブに GPU を追加しても競合が増えるだけで速度は上がらない。

<!--en:7ec275cf-->
* **速度だけでなく収束も監視する。**トークン処理速度が高くても、損失が下がっているとは限らない。その両方に加えて、集団通信とチェックポイント保存に費やされた時間もログに記録する。分散実行の障害をデバッグする際は、すべてのログ行にランクとホスト名を出力したうえで、まず 1 プロセス、次に 1 ノード、最後に多数ノードの順で問題を再現させる。

<!--en:2ec91de0-->
以上の実践によって実行は再開可能になるが、チェックポイント保存と再起動のたびになお時間のコストがかかる。演習問題では、与えられた故障率のもとでそのコストから最適なチェックポイント間隔がどう決まるかを導出する。

<!--en:30ac03ff-->
## まとめ

<!--en:dffc5f25-->
分散訓練は、バッチ、訓練状態、層、または系列をワーカー間で分割する。実測した単一 GPU のベースラインから出発し、モデル状態がメモリに収まる間は DDP を使い、収まらなくなれば FSDP または ZeRO へ移行し、モデルの規模がそれを必要とする場合に限ってテンソル並列、パイプライン並列、コンテキスト並列、またはエキスパート並列を追加する。その際、通信量の大きいテンソル並列は NVLink ノード内に留める。ピークメモリは異なる項目の和であるため、シャーディング、活性化チェックポイント、勾配累積、ホストオフロード、および LoRA は、通信、再計算、または転送時間という予測可能なコストと引き換えに、それぞれ特定の項目を縮小する。2026 年 11 月時点での一般的な選択肢は、単一 GPU では Unsloth または PEFT、単一ノードでは FSDP2 を用いた Accelerate または Axolotl、マルチノードの事前学習では Megatron Core、TorchTitan、または MaxText、強化学習による事後学習では TRL または veRL である。チェックポイントが完全かつアトミックに書き出され、復旧の予行演習が事前に実施され、データパイプラインが演算に追随し、スループットと並んで収束がログに記録されていれば、数週間にわたる実行も確実に完遂できる。

## 演習問題

<!--en:2c003954-->
1. **グローバルバッチサイズ。**ある事前学習ジョブでは、長さ 4,096 トークンの系列と、$2^{22} \approx 4.2$ 百万トークン、すなわちオプティマイザの 1 ステップあたり 1,024 系列のグローバルバッチを用いる。各 GPU はマイクロバッチあたり最大 4 系列を保持できる。
    1. $N_{\textrm{ranks}} \in \{32, 64, 128, 256\}$ に対し、$B_{\textrm{device}}$ と $N_{\textrm{accumulation}}$（:eqref:`eq_global_batch`）を、グローバルバッチが 1,024 系列のまま累積ステップ数が最小になるように選べ。データ並列のみでこのグローバルバッチを訓練できる最大のワールドサイズはいくつか。
    1. 4 系列のマイクロバッチ 1 個にかかる時間を $t_{\textrm{mb}}$ とし、各オプティマイザステップの最後に行う勾配の all-reduce にかかる時間をオーバーラップなしで $t_{\textrm{ar}}$ とする。オプティマイザ 1 ステップあたりの時間と GPU あたりの毎秒トークン数を $N_{\textrm{ranks}}$ の関数として書き下せ。$t_{\textrm{ar}} = 2t_{\textrm{mb}}$ のとき、ワールドサイズが 32 から 64 へ、また 128 から 256 へと倍増すると、一定数のトークンを訓練する時間はそれぞれどの程度の比率で短縮されるか。ワールドサイズが大きくなるにつれて高速化を制限するものは何か。
    1. 同僚がジョブを 64 基から 128 基の GPU に移行し、$B_{\textrm{device}}$ と $N_{\textrm{accumulation}}$ をそのままにしたとする。一定数のトークンに対するグローバルバッチとオプティマイザステップ数はどう変化するか。Adam のような適応的手法に対して、:numref:`sec_batch_size` では学習率をバッチサイズの平方根に比例して $\eta(b) = \sqrt{b/b_0}\,\eta_0$ とスケーリングする（ここで $\eta_0$ はバッチサイズ $b_0$ で調整された学習率である）。拡大後のバッチをそのまま使う場合、この規則はどの学習率を示唆するか。また、ステップ数で指定されたウォームアップには何が起きるか。
   :exlabel:`ex_training-systems-global-batch`

1. [code] **パディングされた評価シャード。**10,001 個のデータ例からなる評価セットを 8 つのランクで評価し、ランク $r$ は `DistributedSampler(dataset, num_replicas=8, rank=r, shuffle=False)` を反復処理するものとする。`num_replicas` と `rank` が明示的に渡されるため、プロセスグループを起動しなくても 1 つのプロセスで全ランクのサンプラを構築できる。
    1. 8 つのサンプラすべてのインデックスを `dataset = list(range(10001))` に対して収集せよ。インデックスは合計いくつあるか、どのデータ例が 2 回現れるか、また重複によって測定される正解率は最大で何パーセントポイントずれるか。
    1. `drop_last=True` として同じ実験を繰り返せ。どのデータ例が一度も評価されないか。
    1. ランク間で 10,001 個のデータ例をパディングなしで分割し、各ランクが自身の正解予測数とデータ例数を数え、`torch.distributed.all_reduce` でそれらのカウントを集約する厳密な評価処理を実装せよ。ランダムな予測を用いて 8 つのランクをシミュレートし、all-reduce をランク間の和に置き換えることで、1 つのプロセス内でこの集約をテストせよ。これらのシャードにおいて、8 つのランクごとの正解率の平均が厳密な値にならないのはなぜか。
   :exlabel:`ex_training-systems-padded-evaluation`

1. [code] **再開時の一致性。**再開された実行が正しいといえるのは、中断なしの実行と同じパラメータを計算するときである。CPU 上で小規模な実験を構築せよ。ドロップアウト付きの 2 層の多層パーセプトロンを、20 個の特徴量を持つ 1,024 個のランダムなデータ例上で、`LambdaLR` のウォームアップスケジュールを伴う Adam によって訓練する。データ例は `DataLoader`（バッチサイズ 32、`shuffle=True`）から供給し、そのシャッフルにはエポックごとに専用の `torch.Generator` でシードを与えるものとする。
    1. 中断なしで 64 ステップ訓練せよ。2 回目の実行では、40 ステップ訓練してチェックポイントを保存し、異なるシードからモデル、オプティマイザ、スケジューラ、データローダを再構築したうえでチェックポイントを復元し、残りの 24 ステップを訓練せよ。両方の実行の最終パラメータをビット単位で一致させよ。:numref:`subsec_training_long_run` に挙げられた各状態は、この実験のどのオブジェクトが保持しているか。また、復元処理はどのようにしてエポックの途中からデータローダを再開させるか。
    1. 復元対象から各状態を 1 つずつ順番に省き、64 ステップ後のパラメータの最大差を報告せよ。損失曲線に現れるのはどの状態の欠落であり、気づかれずに見過ごされるのはどの状態の欠落か。
    1. チェックポイントのバイト列の前半半分だけを最終パスに書き出すことで `torch.save` の最中のクラッシュをシミュレートし、そのファイルを読み込んでみよ。次に、各チェックポイントを同じディレクトリ内の一時ファイルに書き出し、`os.replace` で所定の位置へ移動させよ。2 番目の手順の最中に訓練プロセスがクラッシュしたとき、最終パスに必ず完全なチェックポイント（直前のものまたは新しいもの）が残るのはなぜか。停電が起きると、ファイルの中身より先にリネーム結果だけがディスクに残ることがある。停電にも耐えられるようにするには、この手順にどの呼び出しが必要か。
   :exlabel:`ex_training-systems-resume-parity`

1. **オプティマイザのオフロード。**● ZeRO-Offload :cite:`Ren.Rajbhandari.Aminabadi.ea.2021` は、順伝播と逆伝播のために 16 ビットのパラメータを GPU 上に保持し、FP32 のマスターパラメータと Adam の 2 つのモーメントをホストメモリ上に保持して CPU でパラメータ更新を実行する。各ステップでは、16 ビットの勾配をホストへ送り、更新された 16 ビットのパラメータを送り返す。元論文は BF16 と同じサイズの FP16 を用いている。実効 400 TFLOP/s を維持する 1 基の GPU 上の 7B モデルを考えよう。この GPU は双方向それぞれ 50 GB/s の PCIe で、メモリ帯域幅 200 GB/s のホストに接続されているものとする。
    1. 2 回の転送を続けて実行したときの 1 ステップあたりの転送時間を計算せよ。
    1. CPU 上での更新はメモリトラフィックによって律速される。この配置において Adam の更新が読み書きする 1 パラメータあたりのバイト数を数え、更新にかかる時間を推定せよ。
    1. 順伝播と逆伝播には、トークンあたり約 $6N$ FLOPs（パラメータ数 $N$ のモデルの場合、:numref:`sec_scaling-laws`）の計算コストがかかる。何もオーバーラップしない場合、転送と更新の合計時間がステップ時間の 20% 未満に収まるには、1 ステップに少なくとも何トークン含まれていなければならないか。
    1. ZeRO-Offload の 1 ステップ遅延パラメータ更新では、ステップ $k$ の勾配からの更新を CPU 上で計算するのと並行して、GPU がステップ $k + 1$ の順伝播と逆伝播を（ステップ $k - 1$ の勾配から生成されたパラメータを用いて）実行する。このとき、更新の実質的な所要時間がゼロになるのはどの条件のもとでか。また、この遅延によって最適化の何が変化するか。
   :exlabel:`ex_training-systems-optimizer-offload`

1. **少ないワーカー数での再開。**● あるジョブが 64 ランクの FSDP で $B_{\textrm{device}} = 4$ 系列、$N_{\textrm{accumulation}} = 4$ として訓練し、シャーディングされたチェックポイントを書き出していたが、2 ノードを失ったため 48 ランクで再開しなければならなくなったとする。
    1. :numref:`subsec_training_long_run` に挙げられた再開可能なチェックポイントの内容を、すべてのランクで同一の状態と、ランク間で異なる状態とに分類せよ。ランクごとに異なる各項について、ランク数が変化した際に復元処理が何をしなければならないかを述べよ。
    1. 48 ランク上では $B_{\textrm{device}}$ と $N_{\textrm{accumulation}}$ をどのように選んでも、1,024 系列のグローバルバッチを再現できないことを示せ。異なるグローバルバッチを採用する方法と、ランク間で不均等なマイクロバッチを用いる方法という 2 つの対処法について、それぞれが最適化の何を変化させ、損失の正規化に何を要求するかを比較せよ。
    1. 再開後の実行が、任意のランク数に対してそのエポックの残りのデータ例をちょうど 1 回ずつ処理するようなデータ順序を設計せよ。各ランクの読み出し位置をそれぞれのシャードに保存するだけでは不十分なのはなぜか。
   :exlabel:`ex_training-systems-elastic-resume`

1. [extended] **パイプラインスケジュール。**●● $p$ ステージのパイプラインで、オプティマイザの 1 ステップあたり $m$ 個のマイクロバッチを訓練する。1 個のマイクロバッチが 1 つのステージを通過する順伝播には時間 $t_f$ がかかり、逆伝播には $t_b = 2t_f$ がかかる。あるステージは、前のステージがマイクロバッチ $j$ の順伝播を終えればその順伝播を実行でき、次のステージが $j$ の逆伝播を終えれば自身の $j$ の逆伝播を実行できる。各ステージは、順伝播から逆伝播までの間、$j$ の活性化値を保持する。GPipe :cite:`Huang.Cheng.Bapna.ea.2019` はすべての逆伝播の前にすべての順伝播を実行するのに対し、:citet:`Narayanan.Shoeybi.Casper.ea.2021` の 1F1B スケジュールはウォームアップとして数回の順伝播を実行した後、1 回の順伝播と 1 回の逆伝播を交互に繰り返す。スケジュールのバブル率は、ステップ時間から理想時間 $m(t_f + t_b)$ を引いた値を理想時間で割ったものである。
    1. 各ステージでの演算の順序を受け取り、ステージが空きかつ入力が揃い次第ただちに各演算を実行して、ステップ時間と、各ステージが同時に活性化値を保持するマイクロバッチの最大数とを返すシミュレータを作成せよ。
    1. 任意の $p$ と $m$ に対して GPipe と 1F1B の演算順序を生成せよ。その際、1F1B の各ステージが必要とするウォームアップ順伝播の回数を導出せよ。これらを $p \in \{2, 4, 8\}$ および $m \in \{1, 4, 8, 32\}$ に対して実行し、その結果から各スケジュールのバブル率と活性化メモリを $p$ と $m$ の関数として導出せよ。
    1. :citet:`Narayanan.Shoeybi.Casper.ea.2021` のインターリーブ割り当てでは、各デバイスが連続しない $v$ 個の層のチャンクを保持する。このとき、1 つのマイクロバッチは $pv$ 個のステージを通過し、すべてのデバイスを $v$ 回ずつ、それぞれ $1/v$ のコストで訪問する。すべての順伝播を先に行う方式で、$v \in \{1, 2, 4\}$ についてこれをシミュレートせよ。バブル率と 1 ステップあたりのポイントツーポイント転送回数は $v$ にどう依存するか。
    1. パイプラインの外側に並列度 $d$ のデータ並列を組み合わせ、マイクロバッチを $b$ 系列とすると、1,024 系列のグローバルバッチ（演習問題 :exref:`ex_training-systems-global-batch`）のもとで $m = 1024/(db)$ となる。$p = 8$、$b = 1$ のとき、$d = 8$、16、64 における 1F1B のバブル率を計算せよ。グローバルバッチを固定したとき、パイプライン化されたジョブのデータ並列度を制限するものは何か。
   :exlabel:`ex_training-systems-pipeline-schedules`

[理解度の確認]{.kicker}

<!--en:82bb2da5-->
次の 3 つの分散訓練シナリオについて考えてみよう。

<!--en:5cf54973-->
1. ある事前学習ジョブは $B_{\text{global}} = 1{,}024$ 系列（各 4,096 トークン、計 $\approx 4.2\text{M}$ トークン）の固定グローバルバッチを維持しており、各 GPU はマイクロバッチあたり最大 $B_{\text{device}} = 4$ 系列を保持できる。最小の勾配累積数 $N_{\text{accumulation}}$（$N_{\text{ranks}} = 64$ 基の GPU 上）はいくつか。また、データ並列のみでこのグローバルバッチを訓練できる最大のワールドサイズはいくつか。

<!--en:a990bf3a-->
2. チェックポイントからの復元時に、同僚がモデルの重み、Adam のモーメント、データローダの位置は復元したが、`LambdaLR` スケジューラの状態を復元し忘れた。訓練の実行はどうなるか。また、例外は送出されるか。

<!--en:4d68d2ac-->
3. FSDP2 がステップあたり DDP の約 $1.5\times$ のデータ量を通信するのはなぜか。

<!--en:ea89a84b-->
::: {.slide title="理解度チェック：シャーディング、バッチの不変条件、復旧（続き）"}

<!--en:929b7671-2-->
[理解度の確認]{.kicker}

<!--en:557b98b6-->
**解答：**

<!--en:9cf4ce3b-->
1. 64 基の GPU で $B_{\text{device}} = 4$ のとき、$N_{\text{accumulation}} = 1024 / (64 \times 4) = \mathbf{4}$ となる。純粋なデータ並列での最大ワールドサイズ（$B_{\text{device}} = 1, N_{\text{accumulation}} = 1$ のとき）は **$N_{\text{ranks}} = 1{,}024$ GPU** である（または $256$ GPU、ただし $B_{\text{device}} = 4$ を維持する場合）。

<!--en:228b99e7-->
2. **例外は一切送出されない**が、学習率がステップ 0 にリセットされ（ウォームアップの再実行やピーク値 $\eta_{\max}$ への急戻りが起き）、**突然の損失スパイクや気づかないうちの正解率低下を引き起こす**。

<!--en:f3292fb3-->
3. パラメータ数 $N$、サイズ $S = 2N$ バイトに対し、DDP は勾配の `all_reduce` を 1 回実行する（GPU あたり $\approx 2S$ バイトの送受信）。FSDP は順伝播で重みの `all_gather`（$S$）、逆伝播でもう 1 回重みの `all_gather`（$S$）、さらに勾配の `reduce_scatter`（$S$）を実行し、合計 **$3S$ バイト（DDP の $1.5\times$）**となる。
