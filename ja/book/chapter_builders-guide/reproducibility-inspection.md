# 再現性と検査

<!--en:8d1c4c05-->
訓練スクリプトを 1 行だけ書き換えたところ、Fashion-MNIST における検証正解率が 0.3 パーセントポイント上がったとしよう。ぬか喜びする前に、スクリプトを*変更しない*まま 2 回実行しただけでどの程度結果がばらつくかを知る必要がある。:numref:`subsec_seed_spread` では、乱数シード（random seed）だけを変えてソフトマックス回帰（softmax regression）を 5 回実行する。すると、初期重みとバッチのシャッフルが異なるだけで最終的な正解率には 1〜4 パーセントポイントもの幅が生じ、0.3 ポイントの改善など完全に埋もれてしまうことがわかる。

<!--en:413b2575-->
クラッシュする訓練のデバッグは、これと表裏一体の問題である。数時間の訓練の後に損失が爆発して NaN になった場合、クラッシュに至るまでのステップ列を正確に再現し、実行中のネットワークの内部を調べて、どの層が最初に非有限値を出力したのかを突き止めたい。

<!--en:79b67299-->
本節では、この両面をまとめて扱う。まず、擬似乱数生成器（pseudorandom number generator）、すなわちグローバルシード、専用のジェネレータオブジェクト、マルチワーカーのデータローダを制御して実行を再現可能にし、続いて GPU 特有のさらに厄介な問題である、並列アトミックリダクションのもとでの浮動小数点演算の非結合性に取り組む。次に、*フック*（および各フレームワークにおける同等の仕組み）を用いて、モデルのコードを変更することなく実行中のモデルを検査し、活性化値（activation）のスケールの記録、最初に NaN を出す層の捕捉、勾配ノルム（gradient norm）の監視を行う。この両面は互いに補完し合う関係にある。内部の診断結果を 2 つのコードバージョン間で比較できるのは、実行間で他の条件が一切変わらない場合に限られるからである。初読時はジェネレータオブジェクトとデータローダのワーカーに関する項を軽く読み流し、データパイプラインでランダムなデータ拡張（data augmentation）を扱うようになってから読み返してもよい。

<!--en:b067c583-->
## シードと乱数生成器

<!--en:0127875f-->
訓練パイプラインには、多くの実務者が意識している以上に多様な箇所からランダム性が入り込む。たとえば、重みの初期化（:numref:`sec_init_param`）、毎ステップのドロップアウトマスク、エポックごとのミニバッチのシャッフル、ランダムなデータ拡張（切り抜き、反転、色ジッター）、そして並列に動作するデータローダのワーカープロセスなどである。すべての乱数は*擬似乱数生成器*（PRNG）から生成される。これは、初期*シード*によって出力系列全体が決定される決定論的なアルゴリズムである。したがって、パイプラインが利用するすべての乱数生成器にシードを設定すれば、あらゆる乱数抽出を固定できる。

<!--en:2ba98bfe-->
### グローバルシード

<!--en:9d73e200-->
深層学習フレームワークは、共有されたグローバルな乱数生成器から乱数を引き出すか、あるいは生成器の状態を引数として明示的に渡すことを要求する。以下では、重みと合成入力のすべてをシード付きの 1 つの乱数源から生成する、5 ステップの小規模な訓練ループでシード設定の実例を示す。

<!--en:cf3ba6fc-->
`mnp.random.seed(k)` は、フレームワークの CPU および GPU 用のグローバルな乱数生成器にシードを設定する（Python の `random` や NumPy の `np.random` を使う場合は、別途シードを設定する必要がある）。

<!--en:53506c71-->
`torch.manual_seed(k)` は、フレームワークの CPU および GPU 用のグローバルな乱数生成器にシードを設定する（Python の `random` や NumPy の `np.random` を使う場合は、別途シードを設定する必要がある）。

<!--en:68f19a14-->
`tf.keras.utils.set_random_seed(k)` は、1 回の呼び出しで Python の `random`、NumPy のグローバル RNG、TensorFlow のグローバル RNG にまとめてシードを設定する。

<!--en:7fd5ff02-->
JAX にはグローバル RNG がない。すべての乱数関数は明示的な*キー*（`jax.random.key(seed)`）を受け取り、`jax.random.split` によって独立したストリームを派生させる。

<!--en:057b4195-->
`seed=0` を指定した 2 回の実行は*ビット単位で*一致する（すべての重みと最終損失が同一になる）。同一の初期重み、データ、および決定論的な算術演算からは同一の勾配が生じるからである（演算順序については :numref:`subsec_deterministic_arithmetic` で調べる）。シードを `1` に変更すると、異なる軌跡（trajectory）と損失が得られる。

<!--en:9c977d4e-->
ここでは TensorFlow の実行を CPU 上に配置した。GPU 上では、同じシードを設定したコードでも損失は一致するが、実行によっては重みの最下位ビットが異なる場合がある。

<!--en:6090b59f-->
### ジェネレータオブジェクト

<!--en:793e7e1e-->
単一のグローバル PRNG に依存すると、そこから乱数を引くすべてのコードが結合してしまう。層を 1 つ追加したり、デバッグ中に乱数を伴う一時的な表示処理を入れたりするだけで、後続の乱数ストリーム全体がずれ、訓練・検証データの分割、重みの初期化、ドロップアウトマスクが気づかないうちに一斉に変わってしまう。専用の*ジェネレータオブジェクト*を使えば、独自のシードの背後にストリームを分離できるため、他の箇所での無関係な乱数抽出によって乱されることは決してない。

<!--en:e1f6826f-->
MXNet には専用のジェネレータオブジェクトがないため、固定したい乱数抽出の直前でシードを再設定する。

<!--en:d9fa398e-->
`torch.Generator().manual_seed(42)` は、グローバルな乱数抽出の影響を受けない独立した PRNG ストリームを生成する。

<!--en:30e176b6-->
`tf.random.Generator.from_seed(42)` は、グローバルな乱数抽出の影響を受けない独立した PRNG ストリームを生成する。

<!--en:1987db8e-->
JAX のキーはすべて最初から状態を持たない独立した値であるため、`key_other` を使った乱数抽出が `key_split` に影響することは決してない。

<!--en:819be5c3-->
### データローダのワーカー

<!--en:d0fdb1b0-->
データローダが並列の*ワーカー*プロセスでミニバッチを準備する場合、ランダムなデータ拡張には気づきにくい 2 つの失敗モードがある。ワーカーが OS の `fork` によってメインプロセスのクローンとして起動され、シードが再設定されない場合、すべてのワーカーがまったく同じ生成器の状態を引き継ぎ、同一の「ランダム」なデータ拡張を生成してしまう。逆に、各ワーカーが OS のエントロピーから初期化されると、2 回の実行が一致することは二度となくなる。

<!--en:4c5a77d1-->
Gluon の `DataLoader` は、NumPy のグローバル RNG 状態の同一コピーを持つワーカープロセスを fork するが、`worker_init_fn` を受け付けない。ワーカー間で同一の乱数が引かれるのを防ぐには、例ごとの `np.random.default_rng([seed, i])` を `__getitem__` 内でシード設定する（ローダのシャッフル順序については `np.random.seed` でシードを設定する）。

<!--en:40c42393-->
`DataLoader` は各ワーカーの PyTorch、`random`、およびグローバルな NumPy の RNG に `base_seed + worker_id` からシードを設定する。しかし、専用の `np.random.default_rng()` 属性を `Dataset` に持たせた場合、`worker_init_fn` で `torch.utils.data.get_worker_info().seed` を使ってシードを再設定しない限り、fork されたワーカー間で同一のクローンが作られてしまう。

<!--en:ced52432-->
`tf.data` は 1 つのプロセス内で並列スレッドを実行し、明示的なシードを受け取るため（`Dataset.shuffle(buffer_size, seed=0)`）、設計上 fork による RNG の複製問題は生じない。

<!--en:366eae85-->
JAX では、ワーカーは `jax.random.split(key, num_workers)` や `jax.random.fold_in(key, epoch)` で派生させた明示的なキーを受け取るため、2 つのワーカーに同じキーを渡さない限り、意図しない状態の共有は起こり得ない。

<!--en:47ae25b0-->
ワーカーごと、または例ごとのシード再設定がない場合、1 行目では両方のワーカーが同一の「ランダム」な数値を出力する。適切にシードを設定した 2 行目では、互いに異なりかつ再現可能な乱数が得られている。

<!--en:433648de-->
### 値としてのランダム性

<!--en:abb71f5b-->
上述のワーカーに関するバグはいずれも、隠れた可変な生成器の状態が裏側で暗黙のうちにコピーまたは共有されることに起因する。関数型の乱数 API は、ランダム性を明示的な値として扱うことで隠れた状態を排除する。すなわち、すべての乱数呼び出しはキーを受け取り、同じキーで 2 回呼び出せば同一の数値が返り、独立したストリームはキーを明示的に分割することで得る。誤ってキーを再利用してしまう可能性は残るものの、その再利用はコード上にそのまま現れる。その代償は、確率的なすべての関数にキーを引き回す手間である。グローバルシードとはこの同じ契約を暗黙に略記したものにすぎず、専用のジェネレータオブジェクトを使えば必要な箇所で明示的な分離を取り戻せる。

<!--en:79286e64-->
JAX の `jax.random` はこの方式で動作する。

<!--en:5bfdcc53-->
### シード間のばらつき

<!--en:b09ee08c-->
ここで、本節の冒頭で触れたシード間の分散を実際に測定してみよう。以下では、Fashion-MNIST に対するソフトマックス回帰（:numref:`sec_softmax_concise`）を GPU 上で 3 エポック、5 つのシード（0〜4）にわたって訓練する。関係するすべての乱数生成器にシードを設定し、各実行の最終的な検証正解率と重みを返す。

<!--en:0eba80b7-->
5 回の実行すべてで同一のコードとハイパーパラメータを実行しているにもかかわらず、最終的な正解率は 81% 前後で 1〜4 パーセントポイントの広がりを見せており、1 回の実行で得られた 0.3 ポイントの上昇は単なるノイズにすぎないことが確認できる。信頼できる実験比較では、必ず複数のシードにわたる平均とばらつきを報告する。

<!--en:dfccefef-->
この差がシードの選択だけによって生じたことを確かめるため、`seed=0` を再実行し、正解率とすべての重みを最初の実行と比較してみよう。

<!--en:22f03a31-->
再実行の検証正解率は最初の実行と完全に一致する。個々の重みが最下位ビットまで一致するかどうかは、GPU が浮動小数点数を一定の順序で足し合わせるかどうかに依存しており、これはシードだけでは制御できない（:numref:`subsec_deterministic_arithmetic`）。

<!--en:a3b12252-->
GPU 上では、TensorFlow のバイアス勾配のリダクションが非決定論的なスレッド順で項を足し合わせるため、同一のシードを設定した 2 回の GPU 実行でも最下位ビット付近で $\sim 10^{-6}$ 程度の差が生じ得る。

<!--en:b5c89c5b-->
## 決定論的な算術演算

<!--en:d65803ff-->
シードの設定は、実行時に*どの*乱数を引くかを固定するものであり、浮動小数点演算がそれらを*どのように*組み合わせるかまで固定するわけではない。浮動小数点の加算は毎回、表現可能な最も近い値へと丸められるため、結合法則を満たさ*ない*。すなわち、足し合わせる順序を変えると結果が変わり得る。

<!--en:8521042d-->
3 つの float32 の数値を使えば、この影響は一目瞭然となる。$10^8$ 付近では、隣り合う float32 の数値の間隔が 8 になるため（:numref:`sec_numerics`）、$-10^8 + 1$ は丸められて元の $-10^8$ に戻ってしまう。

<!--en:4b435b31-->
括弧の位置をずらすだけで、答えが `1.0` から `0.0` に変わってしまう。長いリダクションではこのずれはより微妙になるが、至る所で生じる。100 万個の浮動小数点数を先頭から足す場合と末尾から足す場合とでは、最下位ビット付近が日常的に食い違う。

<!--en:53fd63a2-->
スレッド数が固定された CPU 上では、リダクションの順序は通常一定に保たれるため、シードを設定した実行はきれいに再現される。一方 GPU 上では、数千ものスレッドが並列に競合しており、いくつかの高速なカーネル（埋め込みの勾配、スキャッタ加算（scatter-add）、一部の畳み込みの逆伝播、各種リダクションなど）は、スレッドが完了した順に到着する*アトミック加算*（atomic addition）によって部分結果を累積する。そのため、同じ GPU 上で同一のシードを設定した 2 回の実行であっても最下位ビットに差異が生じ、それがカオス的な勾配ステップによってやがて目に見えるほど異なる損失曲線へと増幅され得る。どのフレームワークにも、通常いくらかの速度コストと引き換えに一定の加算順序を強制する決定論モード（または代替カーネル）が用意されている。以下では、GPU 上の*スキャッタ加算*で 100 万個の乱数を 10 個のビンに 2 回続けて足し合わせ、この現象を直接観察してみよう。

<!--en:b25f296d-->
`MXNET_ENFORCE_DETERMINISM=1` は cuDNN の畳み込みアルゴリズムを制限するが、GPU 上の `npx.index_add` は非決定論的なままである。スキャッタ加算をワンホット行列積に書き換えると、順序が固定された cuBLAS のリダクションが使われる。

<!--en:2fa8700c-->
`torch.use_deterministic_algorithms(True)` は、`index_add_` のような演算を決定論的カーネルに切り替える（該当するカーネルが存在しない場合は `RuntimeError` を送出する）。

<!--en:382a8f91-->
`tf.config.experimental.enable_op_determinism()` は、プロセスの終了まで決定論的な GPU カーネル（`tf.math.unsorted_segment_sum` など）の使用を強制する。

<!--en:3ca14d76-->
`compiler_options={'xla_gpu_deterministic_ops': True}` を `jax.jit` に渡す（または `XLA_FLAGS=--xla_gpu_deterministic_ops=true` を設定する）と、決定論的な XLA GPU リダクションが強制される。

<!--en:bd0d194f-->
決定論モードを有効にしない場合、まったく同じ GPU データに対する連続した 2 回のスキャッタ加算では、数百規模の和に対して数千分の 1 程度の差が生じる。決定論的カーネルを使えば、両方の呼び出しはビット単位で一致する。

<!--en:eb43d523-->
このスイッチを有効にすると、乱数演算には必ずシードを指定しなければならない。オペレーティングシステムから自動的にシードを取得する演算もまた非決定論的だからである。グローバルシードを消去することで、この規則を確認できる。

<!--en:b227241b-->
ビット単位の再現性が成り立つ範囲を正しく認識しておく必要がある。それが保証されるのは同一のマシン、ソフトウェアスタック、ハードウェア構成の上だけであり、ライブラリのバージョンアップや異なる GPU アーキテクチャ、あるいは CPU と GPU の間でビット単位の一致を約束するフレームワークは存在しない。ビット単位の決定論は、2 回の実行が分岐する正確なステップを二分探索で特定するための非常に有用な*デバッグ*手段である。一方、科学的な再現性はこれより緩やかであると同時に、より強い要請でもある。本質的な改善（「このアーキテクチャ変更によって正解率が向上する」といった主張）は複数のシードにわたって頑健に成り立たなければならず、:numref:`subsec_seed_spread` と同様に平均とばらつき（約 81%、幅 1〜4 ポイント）として報告すべきである。16 ビット形式の場合（:numref:`sec_numerics`）と同じく、シードの変更や最下位ビットの丸めによって覆るような主張には、より強い根拠が必要である。

<!--en:7a4c3dc7-->
## フックによるモデルの検査

<!--en:1dab14a0-->
バグを確実に再現できたとしても、それで証明されるのはバグが実在することだけであり、ネットワーク内部の*どこで*発生しているかまではわからない。すべての層の `forward` メソッドに print 文を挿入するのは不格好であり、ソースコードをフォークしたくないサードパーティ製ライブラリのモデルでは現実的でもない。*フック*を使えば、この問題をきれいに解決できる。フックとはモデルの外部から登録するコールバックであり、層の実行前または実行後にフレームワークが自動的に呼び出す仕組みである。

<!--en:94e3a019-->
`block.register_forward_hook(f)` は `f(block, inputs, output)` を `__call__` 内で `forward` の後に実行する（`register_forward_pre_hook` はその前に実行する）。

<!--en:85a52851-->
`module.register_forward_hook(f)` は `f(module, inputs, output)` を `__call__` 内で `forward` の後に実行する（新しいテンソルを返すと出力が置き換わる）。

<!--en:0059043d-->
Keras には外部フック API がない。代わりに、関数型グラフの中間シンボリックテンソルを公開する補助的な `tf.keras.Model` を構築するか、カスタムの `call` 内でテンソルを記録する。

<!--en:93fd9ace-->
`nnx.capture(net, nnx.Intermediate, method_outputs=nnx.Intermediate)(X)` は、モデルのコードを変更することなく、1 回の関数呼び出しですべてのサブモジュールの戻り値を取得する。

<!--en:110a38bd-->
![パイプラインとしての `__call__` ラッパー。入力は事前フック、forward、フックを順に通って出力へと流れる。forward の青い実線に対し 2 つのフック段階はオレンジ色の破線で示されており、フック段階から横に出る矢印は値の取得・検査・変更を行うオブザーバを表す。](../img/bg-hooks.svg)

<!--en:eadf3c9b-->
検査の例として、入力数 20 の層と出力数 10 のヘッドの間に幅 64 の残差ブロック（residual block）を 8 個積み重ねたネットワークを構築する（:numref:`sec_model_construction`）。各ブロックは $\mathbf{h} = \mathbf{x} + \textrm{body}(\mathbf{x})$ を計算し、重みには Xavier 初期化（:numref:`subsec_xavier`）、バイアスにはゼロを用いる。実行ごとに新しいランダムな重みが引かれるよう、このネットワークにはあえてシードを設定しないでおく。以下の診断結果の測定値を典型的な範囲として示しているのはそのためである。

<!--en:6c29c95f-->
ここまでのシード付き実行によって MXNet のグローバルな乱数生成器が固定された状態になっており、そのままではこのモデルの重みまで固定されてしまうため、このセルではまずオペレーティングシステムのエントロピーから生成器のシードを再設定している。

ここまでのシード付き実行によって PyTorch のグローバルな乱数生成器が固定された状態になっており、そのままではこのモデルの重みまで固定されてしまうため、このセルではまず `torch.seed()` によってオペレーティングシステムのエントロピーから生成器のシードを再設定している。

### 活性化値の統計量

<!--en:17ec0ccf-->
:numref:`sec_init_param` では、ブロックを手動でループして深さ方向の活性化値の標準偏差を測定した。フックを使えば、モデルに一切手を加えることなく、標準正規分布に従う 256 個の入力からなるミニバッチに対してわずか数行でまったく同じプロファイルを収集できる。

<!--en:1972d24e-->
活性化値の標準偏差は深さとともに着実に増加し、入力層の直後では約 0.7 だったものが 8 番目のブロックの後では 3〜4.5 前後に達しており、理論値とよく一致している。Xavier 初期化により $20 \to 64$ の入力層の重みの分散は $2/84$ となり、出力の分散は $20 \cdot 2/84 \approx 0.48$（標準偏差 0.69）となる。続く各残差ブロックは、入力とほぼ無相関で分散が入力分散の半分となる body 出力を加算するため（最初の線形層は分散を保ち、ReLU が二乗平均を半分にし、2 番目の線形層がその半分を保つ）、ブロックごとに全体の分散は $1.5$ 倍（標準偏差は $\sqrt{1.5} \approx 1.22$ 倍）になる。8 ブロック全体では $0.69 \times 1.5^4 \approx 3.5$ となり、実測値のちょうど中央に収まる。これは :numref:`sec_init_param` で行った分散増加の解析そのものであり（ここでは係数が $1.5$ であり、He 初期化のもとでの $2$ とは異なる）、深い残差ブランチにおいて出力射影（output projection）のスケールを縮小することが有効な理由を改めて裏づけている。

<!--en:bed2233b-->
フックによるメモリリークを防ぐには 2 つの原則がある。フック内で保存するテンソルは必ず `.detach()` すること（さもないと自動微分の計算グラフ全体がステップをまたいでメモリ上に残り続ける）、そして検査が終わったら必ずフックのハンドルを解除すること（`h.detach()`）である。

### NaN 検出器

<!--en:2686433e-->
ステップ 40,000 で訓練損失（training loss）が突然 NaN になったとき、最初の診断上の疑問は*どの層が最初に非有限値を出力したのか*である。フックは順伝播（forward pass）の実行順に呼び出されるため、すべてのリーフ層に有限性チェックのフックを取り付ければ、1 回の順伝播で原因箇所を特定できる。この検出器を試すため、3 番目の残差ブロック（インデックス 3）の重みの 1 つに意図的に NaN を注入してみよう。

<!--en:bfe1cfc8-->
層のクラス定義の中に print 文を 1 つも追加することなく、フックによってブロック 3 内の破損した層が即座に特定される。もちろん、意図的に仕込んだ NaN を捕まえるのはわかりやすいデモの例にすぎない。実際の訓練クラッシュでは、この検出器が示すのは最初の*症状*であり、根本的な原因（活性化値の暴走的な増大が最終的にオーバーフローに至るなど）はさらに数層手前から始まっていることもある。

### 勾配の検査

<!--en:7ae18d83-->
逆伝播（backward pass）も同じ精度で監視できる。8 個の残差ブロックを通るにつれて順伝播の活性化値が増大したのだから、勾配も逆方向に増大するのだろうか。標準正規分布に従う 256 個の入力に対する出力の二乗平均を損失として用い、各残差ブロックの出力における勾配ノルムと、ブロック 3 の最初の線形層における重みおよびバイアスの勾配ノルムを記録してみよう。

<!--en:e54545bf-->
逆伝播フックを使わずに中間出力の勾配を検査するため、各ブロックの出力にゼロテンソル `Z` を加算し、`Z` に関して微分する。

<!--en:d9dc6213-->
`module.register_full_backward_hook(f)` は、`f(module, grad_input, grad_output)` を `backward()` の実行中に呼び出す（最後のブロックから最初のブロックへと、逆トポロジカル順に発火する）。

<!--en:762f5296-->
`tape.gradient(loss, [acts[1:], net.trainable_variables])` は、1 回の呼び出しで中間出力と訓練可能な変数の両方に関する勾配を計算する。

<!--en:32df3dcf-->
8 番目のブロックから 1 番目のブロックへと逆向きにたどると、出力の勾配ノルムはブロックごとに約 $1.2\times$ から $1.4\times$ ずつ（スタック全体では 5〜6 倍）増大しており、順伝播での $1.22\times$ の増大とちょうど対称になっている。理由もまったく同じで、逆伝播において各残差ブロックがブランチ側の勾配をスキップ接続（skip connection）の勾配に足し戻すからである。個々のパラメータの勾配ノルムを単独で見てもあまり意味はないが、深さ方向に比較したり訓練ステップにわたって追跡したりすれば、勾配の消失や爆発の挙動が即座に浮かび上がる（演習問題を参照）。

<!--en:3580cd70-->
これらのデバッグツールが何を解決し、何を解決しないのかを押さえておこう。異なる 2 台のマシンをビット単位で一致させることはできないし、1 回の実行だけで実験上の改善が本物かどうかを決着させることもできない（そのためには複数のシードにわたる分布を比較する）。しかし、再開可能なチェックポイント（:numref:`sec_read_write`）と組み合わせれば、失敗するジョブをクラッシュ直前まで正確に再生し、診断用のフックを取り付けて原因となっている層をピンポイントで特定するために必要な道具はすべて揃ったことになる。

<!--en:f37062da-->
本章の冒頭で取り上げた 80 億パラメータの言語モデルが小さくなったわけではない（fp32 では依然として 32 GB を占める）。しかし、フレームワークがそれをどのように扱うかについて、もはやブラックボックスは何もない。設定からのアーキテクチャ構築、パラメータとバッファの監査、深いスタックの初期化、カスタム層とカスタム勾配の実装、混合精度（mixed precision）での訓練、クラッシュに強いチェックポイントの保存、GPU メモリの管理、そして実行中のモデルの検査は、すべてまったく同じモジュール木の上で動作している。このエンジニアリングの道具立てを備えた今、実世界のデータの構造に合わせて設計されたアーキテクチャへと進む準備が整った。まずは :numref:`chap_cnn` の畳み込みニューラルネットワーク（convolutional neural network）から始めよう。

## まとめ

<!--en:36926a5c-->
訓練におけるあらゆるランダムな選択（初期化、シャッフル、ドロップアウト、データ拡張）は、シードによって制御される擬似乱数生成器に行き着く。また、専用のジェネレータオブジェクトや明示的なキーを用いれば、無関係なコードによってストリームが乱されるのを防げる。浮動小数点の加算は結合法則を満たさず、並列な GPU のアトミック演算は任意のスレッド順で和を計算するため、ビット単位の再現性を得るには決定論的カーネルも必要であり、しかもそれが成り立つのは同一のマシンとソフトウェアスタックの上だけである。したがって、ビット単位の決定論はデバッグのための手段であり、科学的な結論は複数のシードにわたって成り立たなければならない。最後に、順伝播および逆伝播のフック（ならびに各フレームワークにおける同等の仕組み）を使えば、モデルに手を加えることなく、活性化値のスケール、勾配ノルム、最初に発生した NaN を内部から検査できる。

<!--en:1daec1f8-->
1. 訓練スクリプトの先頭でフレームワークの PRNG に `0` をシード設定する。データセットの `__getitem__` 内では、`self.rng = np.random.default_rng()`（`__init__` 内で生成）を用いてガウスノイズを加える。単一プロセスでの 2 回の実行は一致するか。`fork` を用いる 4 つのデータローダワーカーでは何が起きるか。

<!--en:bcceb214-->
2. Xavier 初期化した残差スタックでは、活性化値の標準偏差がブロックごとに $\sqrt{1.5} \approx 1.225$ 倍になる。何ブロック（$k$）を通過すると、活性化値の標準偏差は入力層直後の値の $100\times$ を超えるか。

<!--en:86d9f588-->
3. 訓練中、順伝播フックが毎ステップ `history.append(output)` を `.detach()` なしで実行すると、GPU メモリには何が起きるか。

<!--en:557b98b6-->
**解答：**

<!--en:9de27530-->
1. `np.random.default_rng()` はフレームワークのシードを無視して新しい OS エントロピーを取得するため、**単一プロセスの実行は毎回異なる**。**fork された 4 つのワーカーでは、4 つすべてが同一のクローンを引き継ぐ**ため、`self.rng` から同一のノイズが加えられる

<!--en:b49f938b-->
2. **$1.5^{k/2} \ge 100 \implies k \ge \frac{2 \ln 100}{\ln 1.5} \approx 22.7$（23 ブロック）**

<!--en:ac6ecb24-->
3. **メモリ不足（OOM）によるクラッシュ：**各 `output` が自動微分の計算グラフ全体と中間活性化値を `history` 内に永続的に保持し続ける

<!--en:27af68a7-->
- **PRNG のシード設定と統計報告：**フレームワーク、NumPy、Python の `random`、データローダのワーカーにシードを設定し、平均 $\pm$ 標準偏差を $N \ge 5$ 個のシードにわたって報告する

<!--en:84835d37-->
- **ビット単位の決定論：**バグの二分探索時には決定論的 GPU カーネルを有効にし、非結合的な並列アトミック加算を順序固定のリダクションに置き換える

<!--en:3ea0da55-->
- **実行フック：**順伝播の活性化値と逆伝播の勾配を外部から捕捉し（保存するテンソルは detach し、終了時にハンドルを削除する）、スケールのプロファイリングや最初の `NaN` 層の捕捉を行う
