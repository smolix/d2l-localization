# GPU、デバイス、メモリ

<!--en:916eade1-->
:numref:`sec_oo-design` 以降、`Trainer` は `num_gpus` 引数を受け取りつつも、それを黙って無視してきた。これまでの章で扱った小さなモデルでは、CPU での訓練が数秒で終わるため、それでもほとんど問題にならなかった。しかし、モデルが大規模になると、デバイス配置（device placement）が数秒で済むか数時間かかるかの違いを生む。現代のデスクトップ GPU は 2 つの $4096 \times 4096$ 行列の積を 2 ms 未満で計算するが、CPU では 0.1 秒以上かかるからである（:numref:`subsec_async_dispatch` でベンチマークする）。この圧倒的な計算速度には、厳しいハードウェア上の制約が伴う。GPU は専用のメモリ（たとえばデスクトップ向けカードなら 24 GB）を備えており、GPU が演算するすべてのテンソルはそのメモリ上に置かれていなければならない。

<!--en:50553a47-->
そもそも目的のモデルはメモリに収まるのだろうか。ここまで例に挙げてきた 80 億パラメータのモデルは、bf16 の重みに 16 GB を必要とするため、推論であれば余裕をもって収まる。しかし、このモデルを fp32 の Adam で訓練するには、活性化値（activation）を 1 つ保存する前でも 128 GB の静的な状態が必要となり（:numref:`sec_parameters`）、単一の 24 GB や 80 GB のカードの容量をはるかに超えてしまう。モデルがデバイスに収まるかどうか、そして GPU が休みなく計算を続けられるかデータ待ちで停止してしまうかは、すべてのテンソルがどこに存在し、何バイトを消費するかに帰着する。

<!--en:c5e4f454-->
本節では、3 つの中心的な問いに答える。すなわち、テンソルとモデルをどのように CPU や GPU 上に配置し、デバイス間でコピーするか、GPU の非同期実行（asynchronous execution）はどのように動作するか（また GPU カーネルを正確にベンチマークするにはどうすればよいか）、そして訓練中に実際何が GPU メモリを占めるのか（余分な計算と引き換えにメモリ使用量を劇的に削減する*活性化チェックポイント*（activation checkpointing）の仕組みを含む）である。そのうえで、これらすべてを本書の残りの章で用いるデバイス対応の `Trainer` に組み込む。:numref:`sec_parameters` と :numref:`sec_numerics` ではパラメータあたり・数値あたりのバイト数を数えたが、本節ではそれらのバイトを実際のハードウェア上に載せる（マルチ GPU 訓練は :numref:`chap_performance` に譲る）。すべてのコードセルは、GPU が利用できない環境でも CPU へスムーズにフォールバックし、実行時間の計測には GPU が必要であっても動作の正しさは確認できるようになっている。

## デバイスと配置

<!--en:d81f641b-->
### デバイスオブジェクト

<!--en:b6c53d98-->
すべてのテンソルは特定の*デバイス*上に存在する。すなわち、ホスト RAM と対になった CPU か、オンボードメモリと対になった個々の GPU のいずれかである。ターミナルで `nvidia-smi` を実行すると、マシン上のすべての NVIDIA GPU、その総メモリ量と使用中メモリ量、および実行中のプロセスが一覧表示される。デバイスの命名法はフレームワークごとに多少異なるものの、4 つのフレームワークはすべて 1 つの基本原則に従っている。それは、演算は単一のデバイス上で実行されるため、そのオペランドはすべて同じデバイス上に存在しなければならないという原則である。

<!--en:fd176641-->
`npx.cpu()` と `npx.gpu(i)` は、それぞれ CPU と GPU $i$ を表す（MXNet 2.0 より前は `ctx` と呼ばれていた）。

<!--en:50ad4bdc-->
`torch.device('cpu')` と `torch.device(f'cuda:{i}')` は、それぞれ CPU と GPU $i$ を表す。

<!--en:7dd4df34-->
`tf.device('/CPU:0')` と `tf.device(f'/GPU:{i}')` は、デバイス配置のスコープを作成する。

<!--en:3b6b0920-->
`jax.devices('cpu')[0]` と `jax.devices('gpu')[i]` は、ハードウェアデバイスのハンドルを返す。

<!--en:908bf274-->
デバイスの取得処理を、本書の以降の章でインポートする 3 つの小さなヘルパ関数にまとめておこう。CPU 用のもの、GPU $i$ 用のもの、そして利用可能な GPU の数を数えるものの 3 つである。

<!--en:9e7663db-->
デバイスオブジェクトの構築は常に成功し、ハードウェアが存在するかどうかはテンソルをその上に配置した時点で初めて確認される。

<!--en:ff4f3abe-->
デフォルトでは、TensorFlow は*ソフトプレースメント*を使用し、指定された GPU スコープが存在しない場合は暗黙的に CPU へフォールバックする。

<!--en:88afa312-->
`jax.devices('gpu')` は実機のハードウェアを即座に照会し、GPU が存在しない場合はエラーを送出する。

<!--en:359a59a9-->
`num_gpus` を土台として、GPU があればそれを選択し、なければ CPU にフォールバックする 2 つのヘルパ関数を定義する。これにより、ノート PC でも GPU サーバーでも同じノートブックのコードを一切変更せずに実行できる。

<!--en:a3d4d8c0-->
Apple シリコンの GPU（`mps`）や Google TPU などの他のアクセラレータも独自のデバイス識別子を用いるが、以下で述べる配置の原則はそれらすべてに等しく当てはまる。本書全体を通して、CPU と CUDA GPU に焦点を当てる。

<!--en:0502bb7b-->
### デバイス上の配列

<!--en:7783326f-->
すべてのテンソルは、`device` 属性を通じて自身の配置先を公開している。

<!--en:c5512ceb-->
MXNet のテンソルは、`device=` を渡さない限りデフォルトで CPU に配置される。

<!--en:011cba51-->
PyTorch のテンソルは、`device=` を渡さない限りデフォルトで CPU に配置される。

<!--en:0197a876-->
TensorFlow のテンソルは、GPU が利用可能であればデフォルトで最初の GPU に配置される（または `with tf.device(...):` で明示的に配置できる）。

<!--en:cfd40027-->
JAX の配列は、GPU が利用可能であればデフォルトで最初の GPU に配置される（または `jax.device_put` で明示的に配置できる）。

<!--en:2b5ccf37-->
目的のデバイス上に直接メモリを確保すれば、CPU から GPU への余分なコピーを避けられる。以下では、`X` を 1 番目の GPU に、`Y` を 2 番目の GPU に配置し（GPU が 2 基未満の場合は CPU にフォールバックする）、両者の加算を試みる。

<!--en:d9fba4f3-->
異なるデバイス上のテンソル同士を加算しようとすると即座にエラーが送出され、意図しないデバイス間転送を防ぐ。

<!--en:fb299e23-->
明示的なデバイススコープの外では、TensorFlow は異なるデバイス上のオペランドを暗黙的にデフォルトデバイスへコピーする（ただし `tf.config.experimental.set_device_policy('explicit')` を有効にした場合を除く）。

<!--en:64b4456c-->
### デバイス間のコピー

<!--en:0e64e58e-->
デバイス間でテンソルを移動する処理は、デバイス上での計算よりはるかに遅いため（この差は :numref:`subsec_async_dispatch` で計測する）、異なるデバイス上のオペランドを暗黙的にコピーしてしまうと深刻な速度低下のバグが隠れてしまう。そこで、`X` を `Y` のデバイス上へ明示的にコピーしてから（:numref:`fig_copyto`）加算する。

<!--en:10c2249b-->
![X は GPU 0 上に、Y は GPU 1 上に存在する。GPU 1 上に X のコピー Z（破線）を作ることで、Y + Z をすべて GPU 1 上で実行できる。](../img/bg-copyto.svg)

<!--en:0d398bd5-->
これで加算が実行され、結果も両オペランドと同じ 2 番目の GPU 上に置かれる。実践上の原則は単純である。計算の境界で一度だけデータを転送し（すでにそのデバイス上にあるテンソルの移動は実質的に何もしない操作である）、内側ループの演算はすべてその単一のデバイス上に留めることである。

<!--en:4481e7eb-->
このような移動に使うメソッドは `to_device` であり、配列がすでに移動先にある場合はその配列自身を返す。一方、`copyto` は常にコピーを作成する。

<!--en:ceaed4ec-->
### デバイス上のモデル

<!--en:e9a6ff47-->
順伝播（forward pass）では入力とモデルパラメータを組み合わせるため、モデル全体がミニバッチと同じデバイス上に存在しなければならない。:numref:`sec_model_construction` で見たモジュールツリーのおかげで、どのフレームワークでも 1 回の呼び出しですべてのパラメータを移動または初期化できる。

<!--en:caa51f7c-->
入力とパラメータが同じデバイス上に揃っていれば、順伝播はそのデバイス上で実行され、出力も同じデバイス上に返される。

<!--en:2d2aba5b-->
配置に関する 2 つの原則を心に留めておこう。1 つ目は、オプティマイザを構築する*前*にモデルを目的のデバイス上へ移動または初期化すること（これによりオプティマイザのモーメントも同じデバイス上に確保される）、2 つ目は、`forward` 内で新たに生成するテンソルをデフォルトの CPU ではなく `X.device` 上に確保することである。

<!--en:e4d81c1f-->
## 非同期実行

<!--en:30ce4cc6-->
### 実行キュー

<!--en:222b5f47-->
GPU は、Python から演算が呼び出された瞬間にそれを同期的に実行するわけではない。その代わり、Python は各カーネル起動（kernel launch）をデバイスのコマンドキューに追加して即座に制御を返し、GPU がキュー内の処理を順番にこなしている間に CPU が後続の処理を準備できるようにする。このパイプライン化によって Python のオーバーヘッドは隠蔽されるが、時間計測においては重要な落とし穴がある。Python ループの所要時間を測っても、計測されるのは*実行*ではなく*キューへの投入*にかかる時間なのである。以下では、$4096 \times 4096$ 行列の積を 32 回キューに投入し、実時間（ウォールクロック時間）を 2 回確認する。Python がキューへの投入を終えた直後と、デバイスが計算を終えた直後の 2 回である。

<!--en:01664299-->
MXNet は CPU と GPU の両方で非同期にディスパッチする。`npx.waitall()` は計算が完了するまでブロックする。

<!--en:91d24936-->
JAX は CPU と GPU の両方で非同期にディスパッチする。`B.block_until_ready()` は計算が完了するまでブロックする。

<!--en:16430a33-->
GPU カーネルは非同期に実行される一方、CPU 演算は同期的に実行される。`torch.cuda.synchronize()` はキューに入ったすべての GPU 処理が完了するまで待機する。

<!--en:cf43f427-->
GPU カーネルは非同期に実行される一方、CPU 演算は同期的に実行される。`tf.test.experimental.sync_devices()` はキューに入ったすべての GPU 処理が完了するまで待機する。

<!--en:2525d7ad-->
Python は、実際の計算時間のほんの一瞬のうちに 32 個すべての行列積をキューに投入し終える。では、CPU が実際にブロックして待機するのはいつだろうか。それは、テンソルの表示、スカラーから Python の浮動小数点数への変換、NumPy への変換、あるいは `if` 文でのテンソル値に基づく分岐など、Python がホスト側で具体的な値を必要とするときだけである。このような*同期ポイント*（synchronization point）のたびに、GPU がその値までのキューを消化し終えるまで Python は停止し、その後 Python が追いつくまでの間、今度は GPU がアイドル状態になる（:numref:`fig_bg_async_queue`）。ミニバッチごとに損失を Python の数値として記録すると、毎ステップ同期の空白時間（バブル）が生じてしまう。`Trainer` が `d2l.Averager` 内で損失をデバイス上に保持し、エポックごとに 1 回だけ Python の浮動小数点数に変換しているのはこのためである（:numref:`sec_oo-design`）。

<!--en:87df6748-->
![Python は演算 op1 から op4 までをキューに投入して先へ進み、その間に GPU がそれらを順番に実行する。損失を Python の数値として読み出す処理は同期ポイントとなる。GPU がキューを消化し終えるまで CPU はブロックし、その後 Python が再開する間、GPU は次の処理を受け取るまでアイドル状態になる。](../img/bg-async-queue.svg)

<!--en:2dbb6705-->
非同期ディスパッチの仕組みから、信頼できる GPU ベンチマークのための 4 つの原則も導かれる。（1）初回限りのメモリ確保、ライブラリの初期化、JIT コンパイルを除外するため、最初にウォームアップ呼び出しを実行すること、（2）タイマの開始*直前*と停止*直前*の両方でデバイスを同期すること、（3）複数回の反復にわたって平均をとること、（4）サブミリ秒の分解能を得るために `time.perf_counter` を使用することである。（上の実演セルではウォームアップと同期は実施したものの、32 回の積の合計時間を報告していた。以下で定義する `Benchmark` ヘルパは、本章および以降の章のためにこれら 4 つの原則をすべて自動化する。）

<!--en:cd2324f3-->
JAX はデバイス全体ではなく特定の配列の完了を待機するため、計測対象の関数は計算結果を返す必要があり、`Benchmark` は最後の呼び出しが返した値の完了を待機する。

<!--en:0d29e549-->
さっそく `Benchmark` を使って、先ほどの 2 つの主張を検証しよう。すなわち、大規模な行列積において GPU が CPU よりどれだけ高速か、そして計算に比べてホストからデバイスへの転送がいかに高コストかである。以下では、$4096 \times 4096$ 行列の積を CPU（fp32）、GPU の tf32（:numref:`sec_numerics`）および 16 ビット精度で計測し、あわせて単一の $4096 \times 4096$ 行列を CPU RAM から GPU へコピーする時間も計測する。

<!--en:193954e5-->
MXNet はデフォルトで fp32 の行列積に tf32 を使用する。MXNet の行列積は bf16 を受け付けないため、ここでの 16 ビットの積には fp16 を用いているが、同じテンソルコア上で同じ速度で実行される。

<!--en:c1a51f33-->
TensorFlow はデフォルトで fp32 の行列積に tf32 を使用する。

<!--en:3e6cfe6c-->
JAX のデフォルトの行列積の精度設定では、この GPU 上で tf32 が選択される。

<!--en:ef8714f0-->
現代の GPU では、$4096 \times 4096$ の積は 2 ms 未満で完了するのに対し、CPU では約 100 ms から 2 s を要する（CPU のコア数に応じて約 $100\times$ から $1000\times$ の高速化である）。16 ビット精度に落とすと GPU の計算時間はさらにほぼ半減し、:numref:`sec_numerics` で予告したテンソルコアによる高速化が実現される。

<!--en:0155e3f0-->
最後の行に特に注目してほしい。行列の積ではコピーされた要素 1 つあたり 4096 回の積和演算が実行されるにもかかわらず、CPU メモリから GPU へ行列を単に*コピーする*だけで、到着後に積を計算するよりも 3〜6 倍*長く*かかっている。通常のホストからのコピーでは、GPU の DMA エンジンが直接データを引き出せるよう、まず*ピン留め*（pinned、ページロック）ホストメモリにデータを中継する。バッチをあらかじめピン留めしておけば、この余分なコピーが不要になり、データ転送と計算をオーバーラップさせることができる（:numref:`sec_hardware`）。

<!--en:4a829697-->
## GPU メモリ

<!--en:d885ec77-->
### メモリの 3 つのビュー

<!--en:dcae694e-->
訓練スクリプトがどれだけの GPU メモリを使用しているかを尋ねると、ソフトウェアスタックのどの層に問い合わせるかによって 3 つの異なる数値が返ってくる。CUDA ドライバにメモリを直接要求する処理は遅いため、各フレームワークは内部で*キャッシングアロケータ*を動かし、ドライバから大きなメモリ領域（スラブ）をまとめて取得してテンソルへ細分化して割り当て、解放されたスラブも即座に返却せず再利用のために保持する。これにより、入れ子になった 3 つのメモリビューが生じる（:numref:`fig_bg_allocator`）。すなわち、生存中のテンソルが現在占有しているバイト数、フレームワークのアロケータが予約しているより大きなプール、そして CUDA ドライバがそのプロセスに割り当てた総メモリ量（`nvidia-smi` に表示される数値）である。

<!--en:4a027632-->
![3 つのメモリビューは入れ子になっている。nvidia-smi が報告するプロセスへのドライバ割り当ての中にアロケータの予約済みブロックが含まれ、さらにその中に生存中の配列が含まれる。](../img/bg-allocator.svg)

<!--en:440bcbe9-->
`npx.gpu_memory_info(0)` は、`gpu().empty_cache()` の実行後に CUDA ドライバからデバイス全体の空きバイト数と総バイト数を取得する。

<!--en:bf510a4a-->
`torch.cuda.memory_allocated()` は生存中のテンソルのバイト数を報告し、`torch.cuda.memory_reserved()` はキャッシングアロケータのプール量を報告する。

<!--en:57f94f2d-->
`tf.config.experimental.get_memory_info('GPU:0')` は、TensorFlow の GPU アロケータ内における生存バイト数の現在値（`'current'`）とピーク値（`'peak'`）を報告する。

<!--en:ae4b5222-->
`gpu().memory_stats()` は、JAX が事前確保した GPU プール内での使用中バイト数（`'bytes_in_use'`）とピーク使用バイト数（`'peak_bytes_in_use'`）を報告する。

<!--en:4f2a0a91-->
1 GiB の float32 テンソルを確保して直ちに削除し、これらのカウンタがどう反応するか見てみよう。

<!--en:27321a35-->
MXNet はドライバレベルの使用量のみを報告するため、`empty_cache()` がスラブを返却した時点で数値が下がる。

<!--en:de4e0091-->
`big` を削除すると生存中のテンソル 1 GiB 分が解放されるが、フレームワークのキャッシングアロケータは解放された 1 GiB のスラブを予約プール内に保持し続けるため、`nvidia-smi` の表示はピクリとも動かない。（訓練ループの内部でスラブを強制的に CUDA ドライバへ返却してはならない。毎ステップ低速なドライバ割り当てが発生してしまうからである。）最も外側のドライバビューは、メモリ不足の絶対的な上限を定める。ドライバはカードが物理的に搭載している以上の RAM を貸し出せないためである。コード内の*どこに*メモリが使われているかを診断するには、生存バイト数のカウンタ、とりわけ呼び出し中に達した*ピーク*メモリを調べる。このピーク値が、ステップが成功するかメモリ不足（out-of-memory、OOM）でクラッシュするかを決定する。

<!--en:08924997-->
`torch.cuda.reset_peak_memory_stats()` と `torch.cuda.max_memory_allocated()` を使えば、任意の呼び出しにおける生存メモリの正確なピーク増分を計測できる。

<!--en:a0ad8633-->
XLA はコンパイル済み関数のメモリを静的に計画するため、`compiled.memory_analysis().temp_size_in_bytes` によって入出力以外に必要な一時ワークスペース・活性化メモリのバイト数が報告される。

<!--en:d52c9932-->
MXNet の C++ キャッシングアロケータは生存テンソル数やピークバイト数のカウンタを Python に公開していないため、デバイスメモリの調査には `nvidia-smi` またはフレームワークのプロファイラを使用する。

<!--en:beaeb034-->
### 訓練時のメモリ

<!--en:a31fdc85-->
:numref:`sec_parameters` では、fp32 の Adam 訓練における静的メモリの下限を $16N$ バイト（パラメータ数を $N$ として、重みに $4N$、勾配に $4N$、Adam のモーメントに $8N$）と導出した。実際の訓練ステップでは、ここに 4 つ目の項として*活性化値*が加わる。誤差逆伝播法（backpropagation）では、順伝播の中間出力を逆伝播（backward pass）で消費するまで保持しなければならず、静的な $16N$ とは異なり、活性化メモリはミニバッチサイズと層の幅に比例して増大する。実測する前に計算してみよう。1024 次元の入力を受け取る幅 4096・隠れ層 3 層の MLP（パラメータ数は $N \approx 3.8 \times 10^7$、したがって重みは $4N \approx 144$ MiB）を、ミニバッチサイズ 4096 で動かすとする。3 つの隠れ層の出力はそれぞれ 64 MiB の $4096 \times 4096$ fp32 テンソル（合計 192 MiB）となり、この時点ですでに重み自体より 3 分の 1 大きい。

<!--en:95436ba6-->
MXNet はステップごとの生存バイト数を取得するアロケータのカウンタを Python に公開していないため、本項には MXNet のコードはないが、以下で述べる $16N$ プラス活性化値という解析的なメモリ見積もりはそのまま当てはまる。

<!--en:6a1af672-->
出力された数値は、訓練ステップのライフサイクルを正確にたどっている。まず重み（$4N$ バイト）と入力がメモリ上に置かれ、順伝播によって保存された活性化値（約 192 MiB、重みを上回る）が加わり、逆伝播がその活性化値を消費・解放しつつ勾配（$4N$）を実体化し、最初のオプティマイザステップが Adam の 2 つのモーメント（$8N$）を確保する。:numref:`fig_bg_step-memory` は、16 MiB の入力バッチを除いたこれら 4 つの段階を示したものである。2 ステップ目以降は、毎ステップの中でメモリが増減する。順伝播で重みと Adam のモーメントの上に活性化値が保存され、逆伝播でそれが勾配に置き換わる。ピーク使用量は高々、静的な $16N$ に活性化値を加えた量であり、次の順伝播の前に古い勾配を解放するループでは最大 $4N$ だけ低くなる。活性化値が原因でメモリ上限を超えてしまう場合、アーキテクチャを変えずに活性化メモリを削減できるミニバッチサイズの縮小が最も手軽な対策となる。対照的に、メモリが*ステップを追うごとに*着実に増え続ける場合は、古い計算グラフを生かし続けているメモリリークを疑うべきである。典型的な原因は、生の損失テンソルを切り離さずそのまま Python のリストに追加してしまうことである。

<!--en:0e0babbf-->
`optimizer.zero_grad()` はデフォルト（`set_to_none=True`）で勾配を解放するため、順伝播の前にこれを呼び出すループでは、活性化値を保持している間のパラメータ関連メモリは $12N$ バイト（$16N$ ではなく）にとどまる。

<!--en:f6f79d8d-->
![幅 4096 の MLP をミニバッチサイズ 4096 で訓練した際の、最初の訓練ステップの各段階後における使用中メモリ（入力バッチは含めない）。順伝播では重み（$4N$）に 3 つの保存された活性化値が加わる。逆伝播では活性化値が解放されて勾配（$4N$）が残る。オプティマイザステップでは Adam の 2 つのモーメント（$8N$）が加わる。](../img/bg-step-memory.svg)

<!--en:d3e5e3e9-->
### 活性化チェックポイント

<!--en:7e8d23b1-->
活性化メモリを抑えるには、アーキテクチャ面での 2 つ目の手段がある。通常の誤差逆伝播法は、逆方向の計算で一度読み出すためだけに、すべての層の中間出力を保存している。*活性化チェックポイント*（*勾配チェックポイント*（gradient checkpointing）や*再実体化*（rematerialization）とも呼ばれる :cite:`Chen.Xu.Zhang.ea.2016`）は、順伝播中に大半の中間活性化値を破棄して選択したセグメントの境界にある入力だけを保持し、逆伝播中に各セグメント内部の活性化値をその場で再計算する。（同じ「チェックポイント」という語を含むが、このメモリ上の手法は :numref:`sec_read_write` で扱ったディスクへのチェックポイント保存とは無関係である。）

<!--en:2a9e7017-->
均一な $K$ 個の層を $s$ 層ずつのセグメントに分割すると、保持されるのは $K/s$ 個のセグメント境界と、処理中のセグメント内部で生存している $s$ 個の活性化値のみとなる（約 $K/s + s$ 個のテンソルであり、$K$ 個すべてではない）。$s = \sqrt{K}$ と選べば、ピークの活性化メモリは $O(K)$ から $O(\sqrt{K})$ へと減少する。その代償は、誤差逆伝播法におけるセグメントあたり 1 回分の追加の順伝播である（:numref:`fig_bg_activation_checkpoint`）。線形層の逆伝播が 2 回の行列積（入力勾配と重み勾配）を計算するのに対し、順伝播は 1 回の行列積で済むため、順伝播が 1 回増えてもステップ全体の計算量は順伝播換算で約 3 回分から 4 回分に増えるだけであり、ハードウェアや層の構成にもよるが大まかな上限として約 33% の増加にとどまる。

<!--en:d5da1496-->
![(a) 通常の誤差逆伝播法はすべての層の活性化値を保存する。(b) チェックポイントを用いると、セグメントの入力（塗りつぶし）のみを保存し、各セグメント内部の活性化値（白抜き）は逆伝播中に再計算する。$K$ 個の層を $\sqrt{K}$ 層ずつのセグメントに分けると、1 回分の追加の順伝播をコストとして、保存される活性化値は $O(K)$ から $O(\sqrt{K})$ に減少する。](../img/bg-activation-checkpoint.svg)

<!--en:019550d8-->
活性化チェックポイントが真価を発揮するのは、:numref:`sec_model_construction` の残差 MLP や現代の Transformer のように、同一構造のブロックを深く積み重ねたモデルである。以下では、重みを $\mathcal{N}(0, 0.01^2)$、バイアスを 0 で初期化した `ResidualBlock` と、ブロックをセグメントにまとめて任意でチェックポイントを適用する `run_stack` ヘルパを定義する。

<!--en:b1c9c0f5-->
MXNet には Python から利用できるセグメント単位のチェックポイント API がないため（ハイブリッド化されたグラフに対するプロセス全体のフラグ `MXNET_BACKWARD_DO_MIRROR=1` のみ）、本項には MXNet のコードはない。

<!--en:b4655b18-->
`torch.utils.checkpoint.checkpoint(segment, X, use_reentrant=False)` は `segment` 内部の中間活性化値を破棄し、乱数生成器の状態を保存・復元して（ドロップアウトの一貫性を保ちつつ）、`segment` を `backward()` の実行中に再実行する。

<!--en:6fe66306-->
`tf.recompute_grad(segment)` は `segment` をラップし、`GradientTape` がセグメント境界の入力のみを保持して逆方向の計算時に内部の活性化値を再計算するようにする。

<!--en:5130abfd-->
`jax.checkpoint`（または `jax.remat`）は（`nnx.split` で得られる）純粋関数を変換し、`jax.grad` がセグメント境界の入力のみを保存して誤差逆伝播法の実行中に内部の活性化値を再実体化するようにする。

<!--en:461e5fa6-->
まず健全性チェックとして、活性化値の再計算によって数学的な計算結果が一切変わらないことを確認しておこう。8 ブロックのスタックを 2 つのチェックポイント付きセグメントに分割し、すべての勾配が通常の誤差逆伝播法と一致することを検証する。

<!--en:665d079e-->
この正しさの確認はどの環境でも実行できるが、メモリと計算量のトレードオフを実測するため、次は GPU 上でより深い 16 ブロックのスタック（幅 1024、バッチサイズ 8192）を 4 ブロックずつのセグメントにまとめ、*ステップメモリ*（パラメータと入力を除いたピークメモリ）と `Benchmark` による実時間の両方を計測する。

<!--en:646ba6e9-->
時間を計測する他のすべての TensorFlow コードと同様に、このステップも `tf.function` でコンパイルしている。

<!--en:71f477ab-->
ここでのステップメモリとは、コンパイルされたステップが入力以外に使用する計画のメモリ、すなわち一時配列（主に活性化値）とその出力である勾配の合計である。JAX では `peak_bytes_in_use` をリセットできず、前のセルの実行ですでに値が上がっているため、この目的には使えない。

<!--en:4c312377-->
チェックポイントなしでは、逆伝播は 16 ブロックすべての活性化値を同時に保持する。4 ブロックずつのセグメントにまとめると、保持されるのは 4 つのセグメント境界と処理中の 1 セグメントのみとなり、計算時間が約 4 分の 1 増える（先ほどの概算による上限 33% の範囲内である）だけで、ステップメモリは約 1.1 GiB から 0.4〜0.5 GiB へと削減される。この有利なトレードオフにより、大規模な Transformer や深い視覚モデルの訓練において、活性化チェックポイントは標準的な手法となっている。

<!--en:235e276d-->
## デバイス対応の Trainer

<!--en:491c6993-->
これでようやく `num_gpus` を `d2l.Trainer` に組み込むことができる。ここまでの原則を実践に移すには、たった 2 つの手順で済む。訓練が始まる前にモデルパラメータを目的のデバイス上に配置すること、そして毎ステップの冒頭で各ミニバッチをそのデバイスへ移動することである。

<!--en:dd8b2c31-->
`min(num_gpus, d2l.num_gpus())` を使うことで、`num_gpus` は必須条件ではなく上限として扱われる。CPU のみのマシンでは `self.gpus` が空になり、訓練はそのままシームレスに CPU 上で実行される。本書の残りの章におけるすべての `Trainer(num_gpus=1)` 呼び出しの背後にあるのは、まさにこのフォールバック機構である。

<!--en:d2aef107-->
小さなモデルの訓練は、GPU によって実際どれほど速くなるのだろうか。$4096 \times 4096$ の行列積は約 $100\times$ 以上高速化されたが、エンドツーエンドの訓練ループにはデータ読み込み、Python のディスパッチ、そしてより小さな層が含まれる。以下では、幅 256 の残差ブロック（:numref:`subsec_activation_checkpointing`）を 2 つ重ね、重みを $\mathcal{N}(0, 0.01^2)$、バイアスを 0 で初期化した Fashion-MNIST 分類器で計測してみよう。

<!--en:e49206c6-->
上の項には MXNet のチェックポイント用コードがないため、このセルでは :numref:`sec_model_construction` の残差ブロックの Gluon 版を定義している。モデルの `initialize` はすべての重みを $\mathcal{N}(0, 0.01^2)$ からサンプリングする。

<!--en:f2de6b31-->
Fashion-MNIST におけるウォームアップ後の 1 エポックの実行時間を、`num_gpus=0` と `num_gpus=1` で比較する。

<!--en:f6b3a4c8-->
この高速化倍率は良い現実確認になる。この小さな Fashion-MNIST ネットワークでは、GPU での 1 エポックは CPU より高々数倍速いだけであり、$100\times$ の向上（$4096 \times 4096$ の行列積での倍率）には遠く及ばない。ここでは最大の行列でも $784 \times 256$ にすぎないため、GPU の計算能力の大部分が遊んでしまい、データの読み込みとカーネル起動のオーバーヘッドが実行時間の大半を占めている。次章以降で扱うように、大きな畳み込み、アテンションヘッド、幅の広い線形層が計算負荷の主役になって初めて、GPU は本領を発揮する。

<!--en:8d88d85b-->
メモリの観点では、この小さな SGD モデルは数 GB もの余裕を残して楽に収まる。しかし、80 億パラメータのモデルに立ち返ってみよう。バッチサイズを縮小し活性化チェックポイントを有効にすれば活性化メモリは抑えられるものの、fp32 の重み・勾配・Adam のモーメントが占める 128 GB の静的な下限は手つかずのままであり、しかも `Trainer` は OOM に直面する前に事前警告を出すことはできない。概算によるメモリ見積もりは依然として不可欠であり、単一デバイスのメモリを超えてスケールさせるには :numref:`chap_performance` で扱うマルチ GPU の並列性（parallelism）へと進むことになる。

<!--en:30ac03ff-->
## まとめ

<!--en:f3e5932f-->
すべてのテンソルとモデルパラメータは特定のデバイス上に存在し、あらゆる演算はそのオペランドが同じデバイス上にあることを要求する。ホスト・デバイス間の転送は GPU の計算よりはるかに遅いため、モデルは最初に一度だけ配置し、バッチはステップの境界で転送し、内側ループはデバイス上に留める必要がある。GPU はコマンドキューから非同期に実行するため、Python が停止するのは同期ポイント（スカラーから Python の浮動小数点数への変換や NumPy への変換など）のみであり、信頼できるベンチマークにはウォームアップ、明示的な同期、および反復試行が欠かせない。訓練時のメモリは静的なモデル状態・オプティマイザ状態とバッチ依存の活性化値からなり、活性化チェックポイントは約 1 回分の追加の順伝播をコストとして活性化メモリを $O(K)$ から $O(\sqrt{K})$ へと削減する。最後に、デバイス対応の `Trainer` は単一 GPU への配置を自動化する一方で、GPU がない環境では CPU へとスムーズにフォールバックする。

<!--en:f58d36fd-->
::: {.slide title="明示的なデバイス転送：境界での 1 回のコピー"}

<!--en:5083407f-->
[デバイス間でのテンソルの移動]{.kicker}

<!--en:0744ea13-->
異なるデバイス上のテンソルを組み合わせるには、`X` を `Y` のデバイス上へ明示的にコピーする。

<!--en:9e91418b-->
- **転送の原則：**ループの境界で一度だけデータを移動し、内側ループの演算はすべて単一のデバイス上に留める

<!--en:c54e3b79-->
::: {.slide title="モデルツリー全体の対象デバイスへの配置"}

<!--en:7c3225c8-->
[パラメータと入力の同一デバイス配置]{.kicker}

<!--en:5e36afea-->
- オプティマイザを構築する**前**にモデルを対象 GPU 上へ移動または初期化し（Adam のモーメントを GPU 上に確保するため）、`forward` 内の新規テンソルは `X.device` 上に確保する

<!--en:91e04f59-->
::: {.slide title="GPU の非同期実行：コマンドキュー"}

<!--en:56be30d2-->
[Python が GPU を駆動する仕組み]{.kicker}

<!--en:3d59c9af-->
Python は `B = A @ A` の完了を待たず、GPU の**実行キュー**にカーネル起動を積んで次の処理へ進む。

<!--en:8a89ed54-->
- **キュー投入と計算の差：**$4096 \times 4096$ 行列の積 32 個をキューに投入する処理は CPU 上で数 ms で終わるが、GPU がキューを消化するには数十 ms かかる

<!--en:9e3dcbdd-->
::: {.slide title="CPU・GPU パイプラインを停滞させる同期ポイント"}

<!--en:1a664a18-->
[パイプラインを止めない]{.kicker}

<!--en:adce65fb-->
- **同期による停滞の原因：**`loss.item()`、`float(loss)`、`print(tensor)`、`.numpy()` の呼び出しやテンソル値での分岐（`if loss < best:`）は、キュー内の GPU 処理がすべて終わるまで CPU をブロックさせ、Python が追いつく間 GPU をアイドル状態にする

<!--en:460adef1-->
- **実装のベストプラクティス：**ステップごとの損失はデバイス上のテンソル内に累積し、エポックの最後にのみ Python の浮動小数点数へ変換する

<!--en:e577977b-->
::: {.slide title="正確な GPU ベンチマークのための 4 つの原則"}

<!--en:7ad4674a-->
[非同期カーネルの時間計測]{.kicker}

<!--en:0036085e-->
- **ウォームアップと前後の同期：**ウォームアップ反復を実行し、`perf_counter()` の開始前とタイマ停止前の両方で同期する

<!--en:25b23459-->
::: {.slide title="原則に従う Benchmark ヘルパ"}

<!--en:7ad4674a-2-->
[非同期カーネルの時間計測]{.kicker}

<!--en:6d757652-->
::: {.slide title="4096×4096 行列積と PCIe ホスト・デバイス間コピーの比較"}

<!--en:5dd66761-->
[計算スループットとメモリ帯域幅]{.kicker}

<!--en:e99b77dd-->
$4096 \times 4096$ の行列積を CPU（`fp32`）と GPU（`tf32` および 16 ビット）で計測し、CPU から GPU へのコピーと比較すると、深層学習における根本的なハードウェアのボトルネックが明らかになる。

<!--en:c2094a41-->
- **計算は GPU 上で $100\text{--}1000\times$ 高速：**テンソルコアは $4096^3 \approx 6.9 \times 10^{10}$ 回の積和演算を `2 ms` 未満で完了する（16 ビット精度ならさらに半減）

<!--en:ae723c7d-->
- **PCIe コピーは行列積より $3\text{--}6\times$ 長時間：**PCIe 経由で $4096^2 \times 4\text{ B} = 64\text{ MiB}$ をコピーする方が、GPU 上で要素あたり $4096$ 回の積和演算を実行するより時間がかかる

<!--en:d676be16-->
::: {.slide title="入れ子になった GPU メモリの 3 つのビュー"}

<!--en:f9eac136-->
[生存テンソル・キャッシングアロケータ・CUDA ドライバ]{.kicker}

<!--en:617eb86b-->
プロセスがどれだけの GPU メモリを使用しているかを調べると、メモリ階層のどの層に問い合わせるかによって 3 つの異なる答えが返ってくる。

<!--en:a1f202d1-->
- **なぜ `del big` でも `nvidia-smi` が変わらないのか：**フレームワークは**キャッシングアロケータ**を用い、低速な CUDA ドライバ呼び出しを避けて即座に再利用できるよう、解放された GPU スラブを予約プール内に保持する

<!--en:8c4647a2-->
::: {.slide title="1 訓練ステップにわたるメモリ内訳の解剖" except="mxnet"}

<!--en:5dd358e4-->
[重み + 活性化値 + 勾配 + オプティマイザのモーメント]{.kicker}

<!--en:91d9bccb-->
隠れ層 3 層の MLP（$1024 \to 4096 \to 4096 \to 4096 \to 10$、重み $4N \approx 144\text{ MiB}$、バッチサイズ $B = 4096$）の 1 訓練ステップにわたって生存 GPU メモリをたどると、4 つのメモリ要素が現れる順序がわかる。

<!--en:0c208b2e-->
- **重みを上回る活性化値（$+192\text{ MiB}$）：**3 つの $4096 \times 4096$ 隠れ層出力（$3 \times 64\text{ MiB} = 192\text{ MiB}$）が `forward` 中にメモリを占め、`backward` 中に解放される一方で勾配（$+144\text{ MiB}$）と Adam のモーメント（$+288\text{ MiB}$）が実体化する

<!--en:d4c2a4bf-->
::: {.slide title="1 訓練ステップにわたるメモリ内訳の解剖" only="mxnet"}

<!--en:5dd358e4-2-->
[重み + 活性化値 + 勾配 + オプティマイザのモーメント]{.kicker}

<!--en:993006ea-->
- **静的なパラメータ状態（$16N \approx 576\text{ MiB}$）：**重み（$4N = 144\text{ MiB}$）、勾配（$4N = 144\text{ MiB}$）、Adam のモーメント（$8N = 288\text{ MiB}$）

<!--en:da7fdbe1-->
- **動的な順伝播の活性化値（$\approx 192\text{ MiB}$）：**3 つの $4096 \times 4096$ `fp32` 隠れ層出力（$3 \times 64\text{ MiB}$）で、順伝播から逆伝播へ移る時点でピークに達する

<!--en:e0e66f5a-->
::: {.slide title="8B モデルは 24 GB または 80 GB の GPU に収まるか？"}

<!--en:9a205237-->
[静的メモリバジェットと動的メモリバジェット]{.kicker}

<!--en:ac96ef2b-->
- **推論（`16 GB` の `bf16` 対 `32 GB` の `fp32`）：**`bf16` なら単一の `24 GB` GPU に収まり、KV キャッシュや活性化値用に `8 GB` の余裕が残る

<!--en:12aa9087-->
- **訓練（ヘッドのみの `38.3 GB` 対 `128 GB` の全体 `fp32` Adam）：**ヘッドのみのファインチューニングは 1 基の `80 GB` GPU に収まるが、全体の `fp32` Adam には $\ge 2$ 基の GPU が必要

<!--en:26cf7121-->
- **活性化値による OOM（$O(K \cdot B \cdot T \cdot d)$）：**まずマイクロバッチサイズ $B$ を半減させ、次に**活性化チェックポイント**を有効にする

<!--en:fa5d83dc-->
::: {.slide title="活性化チェックポイント：1 回の追加計算で O(√K) メモリを実現"}

<!--en:21644f0c-->
[計算量と活性化メモリのトレードオフ]{.kicker}

<!--en:4416c3b2-->
**活性化チェックポイント**（Chen et al., 2016）はセグメント境界のみを保存し、残りを `backward` 中に再計算する。

<!--en:d3aecc7b-->
- **ピーク活性化値を $O(K) \to O(\sqrt{K})$ に削減：**$K$ 個の層をサイズ $s$ のセグメントに分割すると、$K/s$ 個の境界テンソルと $s$ 個の生存中の内部テンソルを保持する（合計 $K/s + s$ 個、$s = \sqrt{K}$ で最小の $2\sqrt{K}$ 個）

<!--en:4d911c2f-->
- **抑えられた計算オーバーヘッド：**各セグメントの再計算で増えるのは順伝播 1 回分のみ（ステップ時間は約 $20\text{--}30\%$ の増加）

<!--en:c0bc9a8d-->
::: {.slide title="セグメント単位の活性化チェックポイントの実装" except="mxnet"}

<!--en:3577dafb-->
[残差ブロックのスタックに対するチェックポイント]{.kicker}

<!--en:21797b75-->
- `ResidualBlock` モジュールを `segment_size = 4` のセグメントにまとめ、各セグメントをフレームワークのチェックポイント用ラッパで包むことで、$O(\sqrt{K})$ のメモリで正確な勾配が得られる

<!--en:ecff7885-->
::: {.slide title="チェックポイント使用時の勾配と通常の誤差逆伝播法の一致" except="mxnet"}

<!--en:3577dafb-2-->
[残差ブロックのスタックに対するチェックポイント]{.kicker}

<!--en:7b1a1e83-->
- 活性化値の再計算で数学的な結果が変わってはならない。2 セグメントに分割した 8 ブロックのスタックで、すべての勾配が通常の誤差逆伝播法と一致する

<!--en:04292743-->
::: {.slide title="実測結果：約 25% の時間増でステップメモリを 50% 以上削減" except="mxnet"}

<!--en:f5963e5e-->
[GPU 上での 16 個の残差ブロック]{.kicker}

<!--en:1b677c70-->
16 ブロックの残差スタック（$d = 1024$、バッチサイズ $B = 8192$、4 ブロックセグメント）において、活性化チェックポイントはピークのステップメモリを $\sim 1.1\text{ GiB}$ から $\sim 0.45\text{--}0.5\text{ GiB}$ へと削減する。

<!--en:deaf5da7-->
::: {.slide title="セグメント単位 API を使わない活性化メモリの制御" only="mxnet"}

<!--en:d9b13bc2-->
[活性化メモリ使用量の制御]{.kicker}

<!--en:74dac4f5-->
- **バッチサイズに対する線形スケーリング（勾配累積）：**物理的なミニバッチサイズ $B$ を半分にすると活性化メモリも半減し、2 つのハーフバッチにわたって勾配を累積すれば実効的な更新ステップは保たれる

<!--en:65be1c3b-->
- **解析的な $\sqrt{K}$ チェックポイント則：**$K = 16$ ブロックを $s = \sqrt{16} = 4$ ブロックずつのセグメントに分割すると、保存される活性化値は $16$ 個から $16/4 + 4 = 8$ 個のテンソルに減る

<!--en:3638837e-->

[デバイス対応の Trainer]{.kicker}

<!--en:f90988b2-->
- `d2l.Trainer` は `self.gpus[0]` へモデル（`prepare_model` 内）と各ミニバッチ（`prepare_batch` 内）を移動し、GPU がなければ CPU にフォールバックする

<!--en:ba315cbc-->
::: {.slide title="CPU と GPU におけるデバイス対応 Trainer の時間計測"}

<!--en:935f0267-2-->
[デバイス対応の Trainer]{.kicker}

<!--en:6f6eea49-->
- **小さなモデルで GPU の高速化が控えめな理由：**幅 256 の Fashion-MNIST 用 MLP では行列が高々 $784 \times 256$ であり、データ読み込みと Python のカーネル起動レイテンシが支配的になる。幅の広い層、畳み込み、アテンションが計算の大半を占めると GPU は $100\times$ の高速化をもたらす

<!--en:9e5865e3-->
::: {.slide title="理解度チェック：非同期キューと活性化メモリ"}

<!--en:26a317d8-->
[理解度チェック]{.kicker}

<!--en:7185e946-->
次の 3 つのシナリオでシステムの直感を確かめてみよう。

<!--en:4e5555d5-->
1. GPU 上の訓練ループで、毎ミニバッチステップごとに `if loss < best_loss: best_loss = loss` を実行している。この単一の `if` 文が GPU 使用率を損なうのはなぜか。また、どのように書き換えるべきか。

<!--en:2588e01e-->
2. 深い Transformer が $K = 36$ 個の同一ブロックを積み重ねている。チェックポイントなし（$s = 36$）、毎ブロックのチェックポイント（$s = 1$）、および最適セグメントサイズ $s = \sqrt{36} = 6$ のそれぞれにおいて、逆伝播のピーク時に保持されるブロック入力の活性化テンソルは何個か。

<!--en:4a47e46c-->
3. `2 GiB` の GPU テンソルを削除すると、フレームワークの確保済みメモリカウンタは `2 GiB` 減るのに、`nvidia-smi` の表示はまったく変化しない。なぜか。

<!--en:557b98b6-->
**解答：**

<!--en:b707bb8d-->
1. **Python の `bool`（`loss < best_loss`）を評価すると毎ステップ CPU・GPU 間の同期が強制され**、コマンドキューが空になる。対策：`best_loss = minimum(best_loss, loss)` をデバイス上で更新し、エポックごとに 1 回だけ読み出す

<!--en:98883d91-->
2. **ピーク時に保持されるブロック活性化値数（$K/s + s$）：**チェックポイントなしでは $36$ 個、$s = 1$ では $36/1 + 1 = 37$ 個、最適な $s = 6$ ではわずか $36/6 + 6 = 12$ 個（$3\times$ の削減）

<!--en:cb00f757-->
3. **キャッシングアロケータが解放されたスラブを予約プール内に保持し**、CUDA ドライバ（`nvidia-smi`）へ返却せずに将来のテンソル用に再利用するため

<!--en:1cd6e238-->
::: {.slide title="まとめ：GPU、デバイス、メモリバジェット"}

<!--en:c5a222f8-->
[重要ポイント]{.kicker}

<!--en:67063ea2-->
- **同一デバイス配置と非同期キュー：**オプティマイザ構築前にモデルを GPU へ移動し、各バッチは境界で一度だけ転送し、毎ステップのホスト同期による停滞を避ける

<!--en:2f51346d-->
- **ベンチマークとメモリビュー：**GPU タイマの前後では必ずウォームアップと同期を実施する。生存中の確保済みバイト数、キャッシングアロケータのプール、`nvidia-smi` の表示を区別する

<!--en:99902994-->
- **活性化チェックポイント：**$K$ 個の層を $s = \sqrt{K}$ ごとにセグメント化すると、活性化メモリを $O(K)$ から $O(\sqrt{K})$ に削減できる（追加計算は $\sim 25\text{--}33\%$）
