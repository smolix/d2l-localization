# 保存、読み込み、事前学習済みの重み

<!--en:825598a2-->
訓練済みのニューラルネットワークは驚くほど脆いものであり、それを訓練したプロセスのメモリ上にしか存在しない。スクリプトが正常終了したか、エラーに遭遇したか、サーバーの電源コードが抜けたか、あるいはプリエンプティブルなクラウドインスタンス上で実行されていたかにかかわらず、そのプロセスが終了した瞬間に、学習したすべての重みはディスクに保存していない限り消えてしまう。これまでの章で扱ったトイモデルであれば、途中経過を失っても数分を失うだけで済む。しかし現代の大規模な訓練では数週間分の計算が水泡に帰しかねず、しかもハードウェア障害は珍しい例外ではなく日常茶飯事である。実際、最大 16,384 基の GPU を用いて Llama 3 405B を事前学習（pre-training）した 54 日間のうちに、Meta は予期しない中断を 419 回、すなわち約 3 時間に 1 回の頻度で記録している :cite:`Grattafiori.Dubey.Jauhri.ea.2024`。信頼できるチェックポイント保存（checkpointing）と再開の仕組みがなければ、この規模の実行は決して完走できないだろう。

<!--en:f165cb98-->
重みの保存には、もう 1 つ同様に広く浸透した目的がある。それは訓練済みモデルを共有し、他者が一から訓練することなく推論（inference）を実行したりファインチューニングしたりできるようにすることである（:numref:`sec_fine_tuning`）。どちらのワークフローでも、実務上同じ疑問が生じる。ディスクには具体的に何を保存すべきか、どのファイル形式なら安全に読み込めるか、そして重みが対象のアーキテクチャと一致していることをどう検証すべきか。

<!--en:d3955fb7-->
*何を*保存すべきかという問いへの答えは、:numref:`sec_parameters` から直接導かれる。モデルはコードと状態からなり、コードがアーキテクチャと順伝播（forward pass）を定義する一方、*状態*（state）は訓練によって生成される名前付きテンソル（パラメータとバッファの両方）の集まりである。シリアライズするのは名前をテンソルに対応付けるこの状態のみであり、モデルの再構築はコード上でアーキテクチャをインスタンス化して、そこにテンソルを読み込み直すことで行う。中断された訓練を再開するには、さらに多くの情報が必要になる。モデルの重みに加え、オプティマイザ状態（optimizer state、たとえば Adam の移動モーメントなど）、乱数生成器（random-number generator、RNG）の状態、ステップカウンタ、およびアーキテクチャ設定も保存しなければならず、そのため訓練チェックポイントは推論用の重みファイルよりも数倍大きくなる。

<!--en:33e33be8-->
この実践的な節では、まずモデルの状態を確認してシリアライズし、次に危険性を伴う pickle ファイルと安全な `safetensors` 形式を対比する。続いて、ビット単位で完全に再開可能なアトミックな訓練チェックポイントを構築し、最後に事前学習済み ResNet-50 の重みを改変したアーキテクチャへ読み込みつつ、欠落キーと予期しないキーを検証する。

<!--en:032e08b7-->
## モデルの状態

<!--en:3aff9f9c-->
モデルは数十から数百ものテンソルを含むため、その保存には名前からテンソルへの対応付けを記録する必要がある。各フレームワークはモジュールツリー（module tree）を走査することでこの対応付けを自動生成し（:numref:`sec_model_construction`）、すべてのテンソルにルートからのパスをキーとして割り当てる。以下では、256 個の隠れユニットを持つ単純な単一隠れ層 MLP の状態を確認する。

<!--en:13379995-->
`collect_params()` と `state_dict()` は、ドット区切りのパス（`hidden.weight`、`output.bias`）をパラメータやバッファに対応付ける。

<!--en:28140a0f-->
`net.weights` は層ツリーの `path`（`mlp/hidden/kernel`）を持つ変数を列挙する。パスを決定論的に保つため、明示的な `name=` 引数を用いている。

<!--en:7118c8dd-->
`nnx.state` は、モジュールの属性パス（`hidden.kernel`、`output.bias`）をキーとする入れ子状の状態ツリーを返す。

<!--en:ab27789a-->
この状態辞書（state dictionary）には名前、形状、数値のみが記録されており、それ以外の情報は一切含まれない点に注目してほしい。`MLP` クラスや順伝播のロジック、活性化関数（activation function）の痕跡は残っていないのである。したがってモデルを復元するには、完全に一致する名前と形状を再構築する Python コードが必要になる。属性名を `output` から `head` に変更しただけでも、計算する関数は同一であるにもかかわらず対応付けは壊れてしまう。このような不一致を検出し診断する方法は、本節の後半で示す。

<!--en:6bd7119d-->
## Pickle と safetensors

<!--en:bc7c95d4-->
チェックポイントファイルが自身のディスク外に出ない限り、ほぼどのようなシリアライズ形式でも事足りる。しかし、公開ハブから事前学習済みの重みをダウンロードしたり、他者からチェックポイントを受け取ったりした瞬間、セキュリティ上の疑問が生じる。そのファイルを読み込むだけで、手元のマシン上で任意のコードが実行されうるのだろうか。残念ながら、Python のデフォルトのシリアライズ形式では、その答えは「イエス」である。

<!--en:9eba8659-->
### 読み込み時のコード実行

<!--en:fe99b532-->
Python 標準の `pickle` モジュールは、受動的なデータを保存しているわけではない。Python オブジェクトを再構築するバイトコードプログラムを保存しており、pickle の復元処理はそのプログラムを*実行する*ため、インポート可能な任意の関数を呼び出せてしまう。どのクラスも `__reduce__` を通じて呼び出し可能オブジェクトとその引数を返すことで、pickle が実行する内容をカスタマイズできる。以下の `Tripwire` の例は無害に `print` を呼び出すだけだが、悪意あるチェックポイントであれば同じくらい容易に `os.system` を呼び出せる。

<!--en:b290ae44-->
NumPy はプリミティブでない Python オブジェクトを保存する際につねに `pickle` を使用する。`allow_pickle=True` を指定して読み込むと、ペイロードが即座に実行される。

<!--en:1359154e-->
`torch.save` は pickle アーカイブを書き出す。`weights_only=False`（PyTorch 2.6 より前のデフォルト）を指定して読み込むと、ペイロードが即座に実行される。

<!--en:4fdaaf4c-->
デフォルトでは、各ローダは任意の Python オブジェクトを拒否する。

<!--en:f11bf97f-->
`np.load` は `allow_pickle=True` を指定しない限り pickle の読み込みを拒否する。

<!--en:9fa910b8-->
`torch.load` は PyTorch 2.6 以降、デフォルトで `weights_only=True` となっている。

<!--en:8c57456f-->
制限付き Unpickler による保護は許可リスト（allowlist）にバグがない範囲でしか機能せず、過去には強化された制限付きローダさえ回避する脆弱性が発見されている。実行可能な命令をそもそもエンコード*できない*ファイル形式であれば、設計上その攻撃対象領域を丸ごと排除できる。

<!--en:99828c52-->
PyTorch の `weights_only` モードは、こうした制限付きローダの一種である。

<!--en:a73e64ff-->
TensorFlow 独自のチェックポイントや Keras の `.weights.h5` ファイルには pickle が含まれない。モデル全体を保存する `.keras` アーカイブは `Lambda` 層の関数としてコードを保持できるが、Keras は `safe_mode=False` を渡さない限りその実行を拒否する。

<!--en:c4901f55-->
### safetensors 形式

<!--en:792ab894-->
*safetensors* 形式は生のテンソルデータとメタデータのみを厳密に格納し、コードは一切含まない。そのバイナリレイアウトは連続した 3 つのセグメントだけで構成されている（:numref:`fig_bg_safetensors_layout`）。すなわち、ヘッダ長を表す 8 バイトのリトルエンディアン整数、各テンソル名をその dtype・形状・バイトオフセットに対応付ける UTF-8 の JSON ヘッダ、そして隙間なく詰め込まれた生のテンソルバッファである。読み込み時にコードは一切実行されず、リーダは JSON ヘッダを検証してすべてのバイト範囲がファイル内に収まっていることを確認するだけである。システム面のさらなる利点として、正確なバイトオフセットがあらかじめわかっているため、メモリマッピング（`mmap`）や、ファイル全体を読み込まずに個々のテンソルへランダムアクセスすることが可能になる。フレームワークに依存せず高速な safetensors は、Hugging Face Hub における標準の重み配布形式となっている。

<!--en:7c502263-->
![後述する MLP の safetensors ファイルを 1 本のバイト列として示したもの。8 バイトの長さ、各テンソルの dtype・形状・バイト範囲を記した JSON ヘッダ、そして 4 つのテンソルの生バイト列が名前順に隙間なく並ぶ。データの下のオフセットは、ヘッダが記録している範囲を表す。](../img/bg-safetensors-layout.svg)

<!--en:c4a6ee38-->
この MLP の状態を `mlp.safetensors` に保存し、新しく作成したクローンに読み込んで、両方のインスタンスが同一の出力を生成することを確認しよう。

<!--en:7357e40b-->
保存と読み込みの往復変換はビット単位で完全に一致する。さらに都合がよいことに、ヘッダは固定オフセットにあるプレーンな JSON であるため、Python の標準ライブラリだけでファイルの中身を調べられる。

<!--en:6414a2a1-->
どのバイト区間も、テンソルの要素数に 4 バイト（`F32` = float32）を掛けた長さに等しい。256 要素の隠れ層バイアスが最初の 1,024 バイトを占め、$256 \times 20 = 5{,}120$ 要素の隠れ層重みが続く 20,480 バイトを占め、各ブロックは直前のブロックが終わった位置からすぐ始まる。隠れたコードを一切含まない、純粋なテンソルデータである。

<!--en:ab229a0a-->
手元のマシン上で一時的に使う個人用のチェックポイントであれば、フレームワーク標準の形式でまったく問題ない。しかし、ユーザー向けに公開したりウェブからダウンロードしたりするなど、重みが信頼境界（trust boundary）を越える場合には、safetensors のようなコードを含まない形式を用い、受け手が完全性を検証できるよう暗号学的チェックサムを併記すべきである。

<!--en:60bb8bfd-->
## 訓練チェックポイント

<!--en:0f008482-->
単なる重みファイルは推論には十分だが、訓練の再開には*不十分*である。その理由は、状態を持つ最適化にある。現代の深層学習の実行の多くは *Adam*（:numref:`sec_adam`）を用いており、パラメータごとに 2 つの移動平均を追跡する（:numref:`sec_parameters`）。すなわち、$\mathbf{m}$（勾配 $\mathbf{g}$ 用）と $\mathbf{v}$（要素ごとの二乗 $\mathbf{g} \odot \mathbf{g}$ 用）であり、直近の勾配が大きかった箇所では更新幅を抑えつつ、平滑化された勾配と逆方向へ各パラメータを次の式で更新する。

<!--en:8efaf481-->
ここで、$\eta$ は学習率（learning rate）、$\epsilon$ は小さな定数（通常は $10^{-8}$）であり、除算と平方根は要素ごとに作用し、ハット記号はゼロ初期化を補うバイアス補正（bias correction）項を表す（導出は :numref:`sec_adam` を参照）。重要なのは、$\mathbf{m}$ と $\mathbf{v}$ が最適化の履歴を保持している点である。これらを破棄すれば、Adam はあたかも訓練が一から始まったかのように振る舞う。

<!--en:aee1de8b-->
したがって、真に再開可能な訓練チェックポイントには 5 つの異なる要素が詰め込まれる（:numref:`fig_bg_checkpoint_contents`）。すなわち、(1) モデル状態（パラメータとバッファ）、(2) オプティマイザ状態（$\mathbf{m}$ と $\mathbf{v}$）、(3) ミニバッチのシャッフルやドロップアウトを切れ目なく継続するための乱数生成器の状態、(4) Adam のバイアス補正や学習率スケジュール（learning-rate schedule）を制御するステップカウンタ、そして (5) アーキテクチャの再構築に必要なモデル設定である。勾配は次のステップですぐに再計算されるため省略される。結果として、fp32 での Adam 訓練中に保持されるパラメータあたり 16 バイトのうち 12 バイト（重みと 2 つのモーメント）が残る（:numref:`sec_parameters`）。そのため、80 億パラメータのモデルに対する再開可能なチェックポイントは 96 GB に達し、これは 32 GB の fp32 重みの 3 倍、16 GB の bf16 推論用ファイルの 6 倍にあたる（:numref:`sec_numerics`）。

<!--en:616348d0-->
![チェックポイントファイルの 5 つの区画と、再開時にそれぞれが復元する対象を矢印で対応付けた図。モデル状態は重み、オプティマイザ状態は Adam の 2 つの移動平均、RNG 状態はデータ順序とドロップアウト、ステップはスケジュール内の位置、設定はアーキテクチャを復元する。](../img/bg-checkpoint-contents.svg)

<!--en:770bd138-->
チェックポイント保存は*クラッシュセーフ*でもなければならない。既存のチェックポイントをその場で上書きすると、書き込み途中でジョブが異常終了した際に新旧両方のバージョンを失う危険がある。そこで代わりに一時ファイルへ書き出し、完了後に保存先へアトミックにリネームすることで、どのリーダから見ても完全な前回のチェックポイントか完全な新しいチェックポイントのいずれか一方だけが見えることを保証する。このリネームによりプロセスのクラッシュからは保護される。電源喪失にまで耐えるにはファイルとそのディレクトリの両方に対する `os.fsync` も必要になるが、これについては演習問題で扱う。

<!--en:0296bfb1-->
`.params`（モデル）、`.states`（Trainer の pickle であり、信頼できるディスクからのみ読み込むこと）、および `.json`（ステップ、設定、NumPy の RNG 状態）をいったん `.tmp` ファイルに書き出してから、それぞれ `os.replace` でアトミックに置き換える。個々のファイルの置き換えはアトミックだが、3 ファイルの組全体としてはそうではない。2 回のリネームの合間にクラッシュすると、新しいパラメータと古いオプティマイザ状態が組み合わされてしまうためであり、演習問題ではこの隙間を埋めるマニフェストを構築する。

<!--en:48aed0b9-->
モデル状態、オプティマイザ状態、ステップ、`asdict(cfg)`、および CPU・CUDA・`torch.Generator` の RNG 状態を、`weights_only=True` と互換性のある純粋なテンソルとプリミティブ型のみの辞書にまとめ、`.tmp` ファイルと `os.replace` を介して保存する。

<!--en:bc0d1680-->
チェックポイントからの再開をテストするため、64 個の隠れユニットを持つ小さな MLP 回帰モデルを Adam（$\eta = 0.05$）により 20 次元のノイズ付き線形データ 256 例で訓練する。その際、シードを 0 に固定した専用の乱数生成器を使って 64 例ずつのミニバッチを抽出し、ミニバッチの順序もチェックポイントの状態に含まれるようにする。:numref:`sec_model_construction` と同様、`Config` データクラスにアーキテクチャと訓練のすべてのハイパーパラメータをまとめ、チェックポイント内部に直接同梱できるようにする。

<!--en:e1660af2-->
まず 200 ステップ訓練してチェックポイントを書き出し、そのまま同じ実行をさらに 5 ステップ続けて、中断なしの 205 ステップ分の正解を作成する。`train` の各呼び出しは、各更新ステップの直前にミニバッチ損失を記録する。

<!--en:09806220-->
`tf.train.Checkpoint` はモデル、オプティマイザ、ステップ変数、`tf.random.Generator` を連番付きのチェックポイントファイル（`run-tf-1` など）にまとめ、設定ファイル `.cfg.json` と対にする。TensorFlow は GPU が認識されているとこれらの演算を GPU 上で実行するが、GPU 上ではバイアスの勾配の各項を固定順序で加算しないため、2 回の実行で下位ビットに差が生じることがある。そこで `train` は CPU 上で実行する。

<!--en:6fbdf3c3-->
モデル状態ツリー、オプティマイザ状態ツリー、PRNG キー配列、ステップ、設定辞書を 1 つの辞書にまとめ、Orbax（`ocp.StandardCheckpointer`）を介してアトミックに保存する。

<!--en:669a91fe-->
ここで、新しいプロセスでの再起動をシミュレートしよう。`resume` は保存された設定からモデルとオプティマイザを再構築し、重みとあわせてオプティマイザ状態や RNG 状態を任意で復元したうえで、`num_steps` に達するまで残りのステップを実行する。また、`max_diff` は 2 つのモデル間における要素ごとの重みの最大誤差を返す。

<!--en:ee5793df-->
Keras の `Adam` は最初の更新時にモーメント変数を遅延生成するため、`resume` はオプティマイザへ状態を復元する前に `opt.build(model.trainable_variables)` を呼び出す。

<!--en:3341a913-->
完全なチェックポイントを復元した場合と、乱数生成器だけを省いた場合（`restore_rng=False`、スクリプトが単にシード `0` を再設定したかのような状態）とを比較し、中断なしで 205 ステップ実行した `net` に対する重みの最大誤差を測定する。

<!--en:bcc1b07f-->
完全なチェックポイントを復元すると、中断なしの重みが誤差ゼロ（ビット単位の一致）で再現される。一方、RNG 状態を省くと、再開後のループは次のミニバッチを抽出する代わりに最初のミニバッチを再生してしまい、重みに約 0.004〜0.02 の差が生じる（なお、ビット単位の完全一致には決定論的な演算も前提となるが、これについては :numref:`sec_repro` で詳しく調べる）。

<!--en:94f37c91-->
*オプティマイザ*状態の破棄ははるかに破壊的である。以下では、保存された重みと RNG 状態はそのまま引き継ぎつつ、新しく構築した Adam オプティマイザを使って再開し、再開後 5 ステップのミニバッチ損失を並べて比較する。

<!--en:2c8b9088-->
保存されたオプティマイザ状態を用いれば、訓練は滑らかに再開し、損失は 0.01 前後かそれ以下で推移する。ところが新規の Adam オプティマイザを用いると、*たった 1* ステップで損失が約 1,000 倍に跳ね上がり、4 ステップ後でも再開前の 100 倍以上の水準にとどまってしまう。

<!--en:33d95eb6-->
なぜ新規の Adam を 1 ステップ実行しただけで、ほぼ収束したモデルが壊れてしまうのだろうか。:eqref:`eq_saving_adam` がその理由をすべて物語っている。$\mathbf{m} = \mathbf{0}$ と $\mathbf{v} = \mathbf{0}$ から出発すると、ステップ 1 における Adam のバイアス補正が初期化の減衰因子をちょうど打ち消すため、$\hat{\mathbf{m}} = \mathbf{g}$ および $\hat{\mathbf{v}} = \mathbf{g} \odot \mathbf{g}$ となる。したがって、非ゼロの勾配を持つすべてのパラメータは、勾配がどれほど微小であっても $\eta\, |g_i| / (|g_i| + \epsilon) \approx \eta = 0.05$、すなわち学習率そのものの大きさで移動してしまう。対照的に、保存された $\mathbf{v}$ は訓練序盤のはるかに大きな二乗勾配を記憶しているため、訓練終盤の微小な勾配に対して $\sqrt{\hat{\mathbf{v}}}$ が大きく保たれ、更新は穏やかなまま維持される。モデルが収束（convergence）に近づいているほど、未初期化の Adam による再開の衝撃は激しくなる。重みだけでは、訓練の再開には決して十分ではないのである。

## 事前学習済みの重み

<!--en:322ecdc8-->
ここからは、保存された状態のもう 1 つの主要な用途である、他者が訓練した重みからの初期化に目を向けよう。ImageNet（1,000 カテゴリにわたる 120 万枚の画像）で訓練されたバックボーンは、新しいタスクへきれいに転移できる豊かな視覚表現を学習している。これを 10 クラスの分類問題に適応させるのは簡単で、最終の分類器*ヘッド*を除くすべての層を読み込み、新しい 10 出力の線形層に差し替えるだけでよい。以下では ResNet-50（約 2500 万個のパラメータ、1,000 クラスのヘッドを除くと 2350 万個）を使ってこれを実演する。畳み込みネットワークについては :numref:`chap_cnn` と :numref:`chap_modern_cnn` で学ぶが、重みの読み込みという観点では、ResNet-50 は単に数百個の名前付きテンソルからなる状態辞書にすぎない。

<!--en:531e0ff2-->
外部の重みファイルが独自の対象モデルと 1 対 1 で一致することはまれであり、不一致を黙って無視するのは悪名高いバグの温床である。慎重なローダが部分的な転移をどのように監査するかを見るため、事前学習済み ResNet-50 の状態から 2 つのテンソル群を取り除く。1 つは置き換えを*意図して*いる分類ヘッド、もう 1 つは破損または不一致のチェックポイントを模したバックボーンの最終ステージ全体である。残りのテンソルを新規の 10 クラス ResNet-50 に読み込むと、2 つの診断用集合を確認できる。すなわち、*欠落*キー（missing keys、ファイルに存在せずランダム初期化のまま残されるモデルパラメータ）と、*予期しない*キー（unexpected keys、モデル側で使われないファイル内のエントリ）である。

<!--en:a3eb0abb-->
`load_state_dict(..., strict=False)` は一致するキーを読み込み、`(missing_keys, unexpected_keys)` を直接返す。

<!--en:7be5dd27-->
欠落キーと予期しないキーを、モデルのパラメータパスとチェックポイントのキーとの差集合として計算する。

<!--en:2a347227-->
新しい 10 クラス用ヘッドの重みとバイアスに対する欠落キーは、そのヘッドがランダム初期化から始まるため想定どおりである。一方、バックボーン最終ステージの欠落キーは危険信号である。もし部分一致のまま漫然と読み込んでいれば、「事前学習済み」ResNet-50 の大部分が人知れずランダムノイズのまま残るところだった。今回の例では予期しないキーの集合は空だが、これが空でない場合は通常、モジュール名の変更によって重みがまったく読み込まれなかったことを示唆する。本番コードでは、欠落キーと予期しないキーの集合が置き換えや削除を意図した層*のみ*と一致することを必ず明示的にアサートし、それ以外が含まれていればエラーを送出すべきである。

<!--en:49f5938e-->
検証が済めば、転移学習（transfer learning）では通常、まず事前学習済みバックボーンを*凍結*（freezing）して（:numref:`subsec_freezing`）初期の更新で新しいヘッドのみを訓練し、その後より深い層の凍結を選択的に解除していく（:numref:`sec_fine_tuning`）。

<!--en:994397f0-->
本章でここまで扱ってきたものはすべて、ホスト CPU メモリ上に置かれていた。続く :numref:`sec_use_gpu` では、状態と計算の両方を GPU 上へ移す。

## まとめ

<!--en:da6ca64c-->
モデルの永続化とはその*状態*（モジュールツリーのパスをパラメータやバッファのテンソルに対応付ける辞書）を保存することであり、アーキテクチャ自体はコード内に存在する。Python の `pickle` は読み込み時に任意のコードを実行するため、信頼境界を越えて共有する重みには `safetensors`（8 バイトの長さプレフィックス、JSON ヘッダ、および隙間なく詰め込まれたテンソルバイト列）のようなコードを含まない形式を用いるべきである。クラッシュセーフな訓練チェックポイントは一時ファイルを介してアトミックに書き出され、モデル状態、オプティマイザ状態、RNG 状態、ステップカウンタ、設定という 5 つの要素を保持する。5 つすべてを復元すれば訓練はビット単位で再開されるが、RNG 状態を省くとデータストリームがドリフトし、Adam のモーメントを省くと再開後の最初のステップですべてのパラメータが学習率そのものの大きさで移動して損失が何桁も急騰する。事前学習済みの重みを改変したアーキテクチャへ読み込む際は、不一致を黙って無視するのではなく、欠落キーと予期しないキーの集合を自身の想定と照らし合わせて必ず監査すべきである。

[概念チェック]{.kicker}

<!--en:e8025b20-->
チェックポイント保存に関する次の 3 つの問いを考えよう

<!--en:72bbc623-->
1. MLP（$20 \to 256 \to 10$、`float32`）を保存した `mlp.safetensors` の JSON ヘッダが $n = 296$ バイトであるとする（正確な長さはフレームワークが書き出すテンソル名に依存する）。ファイル全体の正確なサイズは何バイトか。

<!--en:f2885448-->
2. $20 \to 64 \to 1$ の回帰モデルは $20 \times 64 + 64 + 64 \times 1 + 1 = 1{,}409$ 個のパラメータを持つ。新規の Adam オプティマイザを使って $\eta = 0.05$ で再開し（$\mathbf{m}=\mathbf{v}=\mathbf{0}$）、すべての勾配要素が非ゼロであるとき、最初のパラメータ更新のユークリッドノルム $\|\Delta \mathbf{w}\|_2$ はいくらか。

<!--en:b7b4e128-->
3. ResNet-50 の `self.fc` を `self.classifier` に改名し、元の事前学習済みチェックポイントを `strict=False` で読み込むと、`missing_keys` と `unexpected_keys` には何が現れるか。

<!--en:557b98b6-->
**解答：**

<!--en:31be5ef7-->
1. **$8 + 296 + 4 \times 7{,}946 = 32{,}088$ バイト：**8 バイトの長さプレフィックス $+$ 296 バイトの JSON ヘッダ $+$ $31{,}784$ バイト（$7{,}946$ 個の `float32` パラメータ分）

<!--en:4bd3b3b7-->
2. **$\|\Delta \mathbf{w}\|_2 \approx 0.05 \sqrt{1{,}409} \approx 1.88$：**すべての座標が $\pm \eta = \pm 0.05$ ずつ移動する（$\|\mathbf{g}\|_2$ がどれほど小さくても変わらない）

<!--en:977ea09b-->
3. **`missing_keys` には `classifier.weight, classifier.bias`（ランダムなまま残る）が入り、`unexpected_keys` には `fc.weight, fc.bias`（ファイルから無視される）が入る**

<!--en:a83bda2d-->
::: {.slide title="まとめ：保存、読み込み、事前学習済みの重み"}

<!--en:c5a222f8-->
[重要ポイント]{.kicker}

<!--en:0d7345e7-->
- **状態辞書と `safetensors`：**ツリーパスをキーとしてテンソルデータを保存。`safetensors`（8 バイト長 + JSON + 生バイト列）を使えば、任意コード実行ゼロかつゼロコピー `mmap` での共有が可能

<!--en:01cde870-->
- **5 要素のアトミックなチェックポイント：**モデル状態、オプティマイザの $\mathbf{m}, \mathbf{v}$、PRNG 状態、ステップ $t$、設定（8B モデルで $12\text{ B/param} = 96\text{ GB}$）を `.tmp` と `os.replace` で保存

<!--en:89ede936-->
- **事前学習済みキーの監査：**`missing_keys` と `unexpected_keys` が意図的に置き換えた層*のみ*と一致することをアサートする
