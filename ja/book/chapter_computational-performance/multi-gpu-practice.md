# データ並列の実践

<!--en:0ee7f281-->
:numref:`sec_multi_gpu` で手書きしたデータ並列（data parallelism）ループでは、2 基の GPU で LeNet がかえって遅くなった。その理由は 2 つある。単一の Python スレッドが両方の GPU へカーネルを逐次的にディスパッチしていたこと、そして出力に近い層の勾配はずっと早い段階で揃っていたにもかかわらず、逆伝播全体が完了するまでオールリデュースが待機していたことである。

<!--en:b84b4541-->
実用データ並列ツールは、これら両方のボトルネックを解消する。GPU ごとに 1 つのホストプロセスを実行するか、全 GPU にまたがる単一のシャーディングされたプログラムをコンパイルし、さらに勾配を*バケット*にまとめて逆伝播中に各バケットが埋まり次第そのオールリデュースを開始するのである。逆伝播の計算の背後に勾配交換をどれだけ隠蔽できるかを検証するため、ここでは LeNet から $64 \times 64$ の Fashion-MNIST 画像に対する ResNet-18 へと対象を移す（画像 1 枚あたり 22 億回の積和演算、45 MB の勾配 1 バイトあたり約 300 訓練 FLOPs を要し、画像 256 枚の 1 ステップあたり 1 基の RTX 4090 を約 100 ms 稼働させ続ける）。並列ステップが何を計算しているかを 1 ステップチェックで検証したうえで、1、2、4 基の GPU にわたる弱スケーリング（weak scaling）と強スケーリング（strong scaling）を計測し、コストモデルと比較する。

<!--en:607aceb6-->
## 実用データ並列

<!--en:c7dc4357-->
### 実行モデル

<!--en:ea6097a1-->
現代のあらゆるフレームワークは、次の 2 種類の*単一プログラム複数データ*（single program, multiple data、SPMD）設計のいずれかを用いて $k$ 基の GPU を駆動する。

<!--en:88ca6568-->
1. **マルチプロセス（$k$ 個の複製＋集団通信ライブラリ）：**ランチャが $k$ 個の独立した Python プロセス（GPU ごとに 1 つ、それぞれが $\{0, \ldots, k-1\}$ の固有の*ランク*と専用の CPU スレッドを持つ）を起動し、NCCL を介して勾配を同期する。各プロセスの内部では任意の Python コードを実行できる。

<!--en:491cd6bd-->
2. **コンパイラ分割型の単一プログラム：**単一デバイス向けのステップを記述し、デバイスメッシュ上での入力のシャーディングを注釈として指定すると、コンパイラが計算を分割し、集団通信演算（collective operations）を自動的に挿入・スケジューリングする :cite:`Xu.Lee.Chen.ea.2021`。

<!--en:ced4e3e3-->
PyTorch はマルチプロセス設計を採用しており、`torchrun` が $k$ 個のプロセスを起動し、`DistributedDataParallel`（DDP）がモデルをラップする。ノートブック自体は単一プロセスであるため、ここで定義するヘルパ関数 `torchrun` は自己完結したスクリプトを一時ファイルに書き出し、`torchrun --standalone --nproc-per-node=k` を実行して、各ランクの JSON 出力をパースする。

<!--en:db9b0d11-->
JAX はコンパイラ分割型設計を採用しており、`nnx.jit` が単一デバイス向けの訓練ステップをコンパイルする。複製されたパラメータ（`P()`）とバッチ軸に沿ってシャーディングされた入力（`P('data')`）を並べて配置することで、Shardy/GSPMD パーティショナが勾配のオールリデュースを自動的に挿入する。

<!--en:f7aad6d2-->
### 逆伝播と通信のオーバーラップ

<!--en:d27667dd-->
実用フレームワークは、層の逆順（誤差逆伝播法が勾配を生成する順序）で勾配を数十メガバイト単位の*バケット*に詰め込み、バケット内の最後の勾配が揃い次第、各バケットの非同期オールリデュースを起動する :cite:`Li.Zhao.Varma.ea.2020`（:numref:`fig_ddp_overlap`）。

<!--en:363b5d96-->
![上：オールリデュースが逆伝播全体の完了を待つ場合。下：勾配をバケットにまとめ、逆伝播が各バケットの勾配を生成し終え次第、そのオールリデュースを開始する場合。逆伝播の終了後に実行されるのは最後のバケットのみであり、それより前のバケットが隠蔽されるのは、逆伝播がまだ実行されている間に各オールリデュースが完了する場合に限られる。](../img/mdl-perf-ddp-overlap.svg)

<!--en:05f02a8e-->
バケットサイズは、呼び出しごとのレイテンシ $\alpha$ とオーバーラップのトレードオフを決める。極小のバケットでは $\alpha$ を何度も支払うことになり、単一の巨大なバケットでは逆伝播が完了するまで通信を開始できない。理想的なオーバーラップの*バケットモデル*のもとでは（すなわち、次のバケットが埋まる前に各バケットの通信を終えられるほど GPU 間リンクが高速であり、かつ通信が同時実行中の逆伝播カーネルを減速させないと仮定すると）、最後のバケットを除くすべてのバケットが逆伝播の背後に隠蔽される。

<!--en:7d28b52b-->
DDP は最初のバケットを 1 MiB で閉じ、それ以降のバケットを 25 MiB（`bucket_cap_mb`）で閉じる。ResNet-18 の 45 MB の勾配に対し、DDP は約 9、26、9 MB の 3 つのバケットを形成する（最後の 9 MB のバケットには、最も遅く計算される入力側の層が入る）。

<!--en:3af6d37e-->
XLA は 30 MiB のしきい値（`--xla_gpu_all_reduce_combine_threshold_bytes`）まで勾配のオールリデュースを結合し、ResNet-18 の 45 MB の勾配を、逆伝播計算と並行してスケジュールされる 2 組の非同期 `all-reduce-start` / `all-reduce-done` ペアにまとめる。

<!--en:c6d66c16-->
### 訓練ステップ

<!--en:98c1ff7a-->
:numref:`sec_resnet` の小画像向け ResNet-18（:numref:`chap_cv` でも利用するため `#@save` しておく）を定義し、その勾配バイト数 $S$（fp32 で 45 MB）を数える。

<!--en:c4b82ea0-->
次に、Fashion-MNIST を読み込み、ResNet-18 のパラメータ数 `num_params` と fp32 での勾配データ量 `S` を計算する。

<!--en:3b6eb283-->
また、DDP がオールリデュースを起動する前に逆順で詰め込む 1 MiB および 25 MiB の勾配バケット `buckets` も計算する。

<!--en:2a8c1699-->
続いて、$64 \times 64$ の Fashion-MNIST 画像に対するデータ並列の訓練ステップを定義する。

<!--en:bbdb1767-->
`TRAIN_DDP` は `resnet18` を `DDP` でラップし、プロセス間で `train_step` の実行時間を計測する（オプションとして `model.no_sync()` およびカーネルプロファイリングも備える）。

<!--en:45b09c1b-->
`setup` はモデルとデータセットを `'data'` メッシュ上に複製し、`train_step` はシャーディングされたミニバッチインデックス `idx` に対して JIT コンパイルされた SGD 更新を実行する。

<!--en:6b9ff784-->
### 1 ステップチェック

<!--en:9588c6d3-->
LeNet とは異なり、ResNet-18 は各チャネルをミニバッチの平均と分散で正規化するバッチ正規化（:numref:`sec_batch_norm`）を含んでいる。256 個の例からなるミニバッチを 2 基の GPU に分割したとき、各 GPU は自身の 128 例のシャード統計量で正規化するのだろうか（これは 1 基の GPU 上で 128 例のマイクロバッチ 2 つにわたって勾配累積した場合と一致する）。それとも、GPU 間で 256 例の大域的な統計量を同期するのだろうか。2 基の GPU による更新を、単一 GPU におけるこれら両方の参照結果と比較して確かめてみよう。

<!--en:3f4081f7-->
デフォルトでは、PyTorch DDP は各 GPU のシャードをシャードごとの局所統計量で正規化する。そのため、2 分割して累積した場合とは約 $10^{-7}$ の精度で一致する一方、フルバッチ統計量を用いた場合とは数パーセント異なる（`nn.SyncBatchNorm` に変換すれば、追加の集団通信と引き換えに大域統計量が同期される。演習問題 :exref:`ex_mgp-syncbn`）。

<!--en:e698ab3f-->
バッチ軸が `'data'` メッシュ軸に沿って `Auto` モードでシャーディングされるため、XLA のパーティショナはバッチ正規化の平均と分散をミニバッチ全体にわたって大域的に計算する。これにより、単一 GPU での 256 例のステップと一致し、2 つの大きな勾配バッファに加えてチャネルごとのバッチ正規化統計量に対する小さなオールリデュースが挿入される。

<!--en:18691108-->
マルチ GPU メッシュ上で `train_step` をコンパイルし、`allreduce_megabytes` を適用すると、2 つの大きな勾配オールリデュース（`big`、最後のバッファは `last_bucket` として記録）と並んで、チャネルごとのバッチ正規化に対する小さなオールリデュースが確認できる。

<!--en:f42cdf9b-->
## 4 基の GPU でのスケーリング

<!--en:273845bf-->
ここでは、$k \in \{1, 2, 4\}$ 基の GPU にわたって弱スケーリング（GPU あたり 256 例）と強スケーリング（全体で 512 例）を計測する。

<!--en:f437de37-->
まず、NCCL を介した単体の 256 MB オールリデュースで $\beta_\textrm{link}$ を測定し、弱スケーリングのもとでの露出通信時間（exposed communication time）$t_{\textrm{step}}(k) - t_{\textrm{step}}(1)$ に対する次の 2 つの予測を比較する。

<!--en:e9dfabbd-->
1. **オーバーラップなし：**$S = 45$ MB のリングオールリデュース全体が露出する（$\frac{2(k-1)}{k} S \beta_\textrm{link}$）。

<!--en:0fb0c95f-->
2. **完全なバケットオーバーラップ：**逆伝播の終了後に最後のバケットまたはバッファ（$last\_bucket$）のみが露出する。

<!--en:bf36961e-->
`allreduce_beta()` を呼び出すと実測リンクコスト `beta_link` が得られる。これを用いて、$k \in \{2, 4\}$ 基の GPU に対する `exposed[k]` を、オーバーラップなしモデル（$2(k-1)S\beta_\textrm{link}/k$）と完全オーバーラップモデル（`last_bucket`）の両方について計算する。

<!--en:b6403425-->
それでは、GPU あたり 256 例（`step_time(k, 256)`）で $k \in \{1, 2, 4\}$ 基の GPU にわたる弱スケーリングをベンチマークし、実測されたスループット、スケーリング効率、および露出オーバーヘッド `weak[k] - weak[1]` を両方の予測と比較しよう。

<!--en:fabf84c6-->
バス帯域幅が約 2.4 GB/s の場合、オーバーラップなしの 45 MB のオールリデュースには 2 基の GPU で約 18 ms、4 基で約 28 ms かかる。弱スケーリングの実測では、4 基の GPU は単一 GPU の $3.1\text{--}3.3\times$ のスループット（スケーリング効率 77〜83%）を達成した。これは*オーバーラップなし*の予測とよく一致しており、完全オーバーラップのバケット予測を大きく下回っている。

<!--en:8c2f51ca-->
強スケーリング（グローバルバッチを 512 例に固定するため、通信量が一定のまま $k$ 基の各 GPU が $512/k$ 例を処理する設定）のもとでは、$k = 4$ で効率がさらに低下する。

<!--en:b5d509d0-->
### バケットモデルの仮定

<!--en:4ca093b8-->
なぜオーバーラップによって通信がほとんど隠蔽されなかったのだろうか。バケットモデルは、（1）各バケットのオールリデュースが逆伝播の最中に開始すること、（2）NCCL が単体ベンチマークと同等の速度で動作すること、（3）NCCL が並行して動作しても逆伝播の計算カーネルが減速しないこと、の 3 つを仮定している。GPU 0 を 3 つの構成（1 基の GPU、通信なしの 2 基の GPU、通信ありの 2 基の GPU）にわたってプロファイリングすることで、これら 3 つの仮定すべてを検証できる。

<!--en:beb7c03b-->
GPU あたり $b = 256$ 例で、単一 GPU、勾配同期なしの 2 基の GPU、オールリデュースありの 2 基の GPU という 3 つの構成にわたって `profile_step` を実行し、実経過ステップ時間をデバイスの計算時間と NCCL カーネル時間に分離する。

<!--en:6292a865-->
通信なしの 2 基の GPU は単一 GPU と全く同じ速度でステップを実行し、NCCL のカーネルは 20〜22 ms 動作する（18 ms の単体ベンチマークと整合する）。破綻しているのは 3 つ目の仮定である。すなわち、**NCCL が逆伝播と並行して動作すると、計算カーネル自体が 8〜13 ms 遅くなる**のである。ピアツーピアアクセスを持たない GPU では、NCCL は独自の GPU SM カーネルを使ってホストメモリ経由でデータをコピーするため、本来であれば逆伝播が利用するはずのストリーミングマルチプロセッサとメモリ帯域幅を占有してしまう。

<!--en:44901085-->
非公式の NCCL フラグ（`NCCL_SHM_USE_CUDA_MEMCPY=1`、NCCL 2.28〜2.30 に存在）を用いると、単体のマイクロベンチマークにおいては、これらのホストメモリ経由のコピーを GPU の DMA コピーエンジンへオフロードできる。

<!--en:deda2485-->
同じフラグを DDP で使用すると、オールリデュースが逆伝播計算とオーバーラップした際にデッドロックを引き起こす。

<!--en:e5ef6ff2-->
NVLink（片方向あたり 450〜900 GB/s、:numref:`subsec_hw-interconnects`）で接続されたデータセンタ向け GPU 上では、ResNet-18 の 45 MB のオールリデュースは 1 ミリ秒を優に切る時間で完了し、ほぼ線形のスケーリングを達成する。しかし理想的なスケーリングが得られたとしても、データ並列は依然としてパラメータとオプティマイザ状態の全 $16N$ バイトをすべてのカード上に複製する。:numref:`sec_sharding` では、この状態を複数の GPU に分割する手法を扱う。

<!--en:30ac03ff-->
## まとめ

<!--en:36948aa3-->
実用データ並列は、NCCL を介して同期する $k$ 個の独立したプロセス、あるいはコンパイラ分割型の単一プログラムのいずれかによって $k$ 基の GPU を駆動し、勾配を 25〜30 MiB のバケットにまとめてオールリデュースを逆伝播とオーバーラップさせる。単一 GPU の参照結果に対する 1 ステップチェックを行えば、バッチ正規化がシャードごとの統計量を用いているのか、追加の集団通信を介して大域統計量を用いているのかが明らかになる。ホストメモリ経由で通信する 4 基の RTX 4090（バス帯域幅 2.4 GB/s）では、弱スケーリングのもとで単一 GPU の $3.1\text{--}3.3\times$ のスループットが得られたが、カーネルプロファイリングの結果、ホスト中継の NCCL カーネルによる SM 競合が、通信と逆伝播計算のオーバーラップで節約された時間の大部分を帳消しにしていることがわかる。

2. **弱スケーリングの外挿。**$k$ 基の GPU 上での 1 ステップに、単一 GPU 時間 $t_1$ と、リング通信量 $2(k-1)S/k$ に比例する露出通信時間がかかるとする。

    1. $a$ 個のマイクロバッチ（GPU あたり 256 例、最後のマイクロバッチでのみ通信する）にわたって勾配累積を行う場合、整数 $a$ のうち $E(4)$ を 95% 以上に引き上げる最小の値を求め、グローバルバッチサイズがどのように変化するか述べよ。

<!--en:553c3576-->
3. [code] **バケットサイズ。** ● バケットオーバーラップ（:numref:`fig_ddp_overlap`）を次の仮定のもとでモデル化せよ。時間 $t_b$ の逆伝播が等サイズの $n$ 個のバケットを時刻 $i\,t_b/n$（$i = 1, \ldots, n$）に順次放出し、各バケットのオールリデュースが逐次的に $\alpha + \tau/n$ を要するものとする（ただし $\tau = S\,\beta_\textrm{link}$）。

    1. `model`（`CHECK_DDP` 内）を `nn.SyncBatchNorm.convert_sync_batchnorm` で変換してから `DDP` でラップし、同じチェックを繰り返せ。今度はどちらの単一 GPU 参照結果と一致するか。

   :exlabel:`ex_mgp-syncbn`

3. [code] **バケットサイズ。** ● バケットオーバーラップ（:numref:`fig_ddp_overlap`）を次の仮定のもとでモデル化せよ。時間 $t_b$ の逆伝播が等サイズの $n$ 個のバケットを時刻 $i\,t_b/n$（$i = 1, \ldots, n$）に順次放出し、各バケットのオールリデュースが逐次的に $\alpha + \tau/n$ を要するものとする（ただし $\tau = S\,\beta_\textrm{link}$）。
    1. 逆伝播終了後の露出通信時間が次の式で与えられることを示せ。
       $$t_{\textrm{exposed}}(n) = \max\Bigl(\alpha + \frac{\tau}{n},\;

- **ピアツーピア（P2P）なしでの NCCL のデータ移動：**コンシューマ向けの RTX 4090 は NVLink も PCIe P2P も持たないため、NCCL は PCIe 越しに読み書きして SM 上でチャンクを加算する**専用の GPU SM カーネル**を実行し、全チャンクを共有ホスト DRAM（`SHM`）経由で中継する

<!--en:b29c6dd8-->
- **リソース競合：**これらの NCCL SM カーネルは、逆伝播の畳み込みカーネルや GEMM カーネルと**ストリーミングマルチプロセッサ**および **DRAM メモリ帯域幅**を直接奪い合う

<!--en:5f0a1604-->
ホスト中継コピーを DMA コピーエンジンへオフロード（`NCCL_SHM_USE_CUDA_MEMCPY=1`）すると単体オールリデュースの帯域幅は $4\text{--}5\times$ 向上するが、逆伝播計算とオーバーラップさせると PyTorch DDP がデッドロックする。転送フラグは必ず実際の訓練ループで検証すべきである

<!--en:1ee91468-->
3 つの確認問題で実用データ並列の理解度を確かめよう

<!--en:7284b3af-->
1. DDP はどのパラメータ順序で勾配をバケットに詰め込むか。また、順伝播の層順（$1, 2, \ldots, L$）で詰め込むと通信のオーバーラップが損なわれるのはなぜか。

<!--en:4b6706f7-->
2. 4 基の RTX 4090 上で、$b = 256$ 枚/GPU での弱スケーリング効率は $E(4) = t_1 / t_{\textrm{step}}(4) \approx 80\%$ であった（計算 $t_1 \approx 100\text{ ms}$＋露出オールリデュース $28\text{ ms}$）。オールリデュースを実行する前に $a = 5$ 個のマイクロバッチ（GPU あたり画像 $256$ 枚、最初の $4$ マイクロバッチでは `model.no_sync()` を使用）にわたって勾配累積すると、弱スケーリング効率 $E(4)$ はいくらになるか。

<!--en:df806d12-->
3. `BatchNorm` を含むネットワークで 2 GPU 訓練と 1 GPU 訓練を比較する 1 ステップチェックを実行したとき、デフォルトの `DDP` はどちらの単一 GPU 参照結果と一致するか。

<!--en:557b98b6-->
**解答：**

<!--en:71f82d96-->
1. **パラメータの逆順（$L, L-1, \ldots, 1$）：**`backward()` は層 $L$ から層 $1$ へ向かって逆順に勾配を生成するため。層 $1$ を含む順方向のバケットは `backward()` の最末尾まで起動できない

<!--en:518d6017-->
2. **$\mathbf{E(4) \approx 95\%}$：**局所計算が $5\times$ 増えて $5 \times 100 = 500\text{ ms}$ になる一方、単一のオールリデュースは $28\text{ ms}$ のままであるため、$E(4) = \frac{500}{500 + 28} \approx 94.7\%$ となる（引き換えにグローバルバッチは $5\times$ 大きい $B = 5 \times 4 \times 256 = 5{,}120$ になる）

<!--en:eaf3cd9c-->
3. **`DDP`** はデフォルトでシャードごとの統計量を用いる（**$B/2$ ずつ 2 分割して累積する 1 GPU** と一致）
