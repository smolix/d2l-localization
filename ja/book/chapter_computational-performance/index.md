# 計算性能

<!--en:549c6289-->
ここまでは、どのモデルを訓練するときも、ネットワークを書き、訓練ループを開始して完了を待つだけであり、ステップ時間とメモリは所与のものとして扱ってきた。しかし、実行に何日もかかる場合や、モデルがカードに収まらない場合、あるいは 2 基目の GPU を追加するとかえって訓練が遅くなる場合には、そのやり方は通用しなくなる。GPU により多くの処理を与えるため、:numref:`sec_gpt` の GPT の幅を 2 倍に広げたものを考えてみよう。1 回の訓練ステップの算術演算量を GPU のピーク演算速度で割れば、そのステップが取り得る最短時間が求まるはずだが、実測したステップにはその数倍の時間がかかる。残りの時間はどこへ消えているのだろうか。

<!--en:9065c484-->
コンピュータアーキテクトは、深層学習よりはるか前からこの問いに直面していた。1990 年代までにはプロセッサの速度がメモリを大きく引き離し、多くのプログラムが実行時間の大部分をデータ待ちに費やすようになっていた。2009 年に Williams、Waterman、Patterson は、その帰結を*ルーフライン*モデルとして定式化した :cite:`Williams.Waterman.Patterson.2009`。すなわち、プログラムは演算器が許す速度を超えて動作することはなく、また必要なバイト数をメモリが供給できる速度を超えて動作することもない。Python から駆動される GPU には、各演算を発行するホスト側のコストという 3 つ目の制約が加わる。これら 3 つのうちどれがステップを律速しているかによって、どの変更が高速化につながるかが決まる。この視点に立てば、大きなミニバッチや 16 ビット数値（:numref:`sec_numerics`）といった前章までの選択の理由が説明できるとともに、次のような方法論が得られる。ステップの算術演算量とバイト数を数え、実行時間を予測し、実測して、その差を説明するのである。

<!--en:c6fc2e2b-->
すべての土台となる :numref:`sec_perf_model` では、1 バイトの移動あたりに演算が実行する FLOPs である*演算密度*（arithmetic intensity）を導入し、この方法論を実際に適用する。ハードウェアの節（:numref:`sec_hardware`）では、ピーク演算性能と帯域幅がどこから生じるのかを説明する。コンパイル（:numref:`sec_compilation`）と :numref:`sec_memory_precision` のメモリ手法は、多くの実務者が日常的に使う単一 GPU 向けのツールである。続く 3 つの節では GPU を増やし、第一原理からのデータ並列（data parallelism、:numref:`sec_multi_gpu`）と実運用におけるデータ並列（:numref:`sec_multi_gpu_concise`）を扱ったのち、重み、勾配、オプティマイザ状態を複数のカードにシャーディングする手法（:numref:`sec_sharding`）を導入して、単一の GPU には収まらないほど大きなモデルを訓練できるようにする。最後に、ケーススタディ（:numref:`sec_fast_transformer`）では上述の GPT に立ち返り、1 基および 4 基の GPU 上でそのステップ時間の内訳をミリ秒単位で明らかにする。

<!--en:db7377ea-->
本章では、GPU コードの実行時間とピークメモリを計測でき（:numref:`sec_use_gpu`）、bf16 と tf32 を理解しており（:numref:`sec_numerics`）、GPT とそのキー・値キャッシュに触れていること（:numref:`sec_gpt`、:numref:`sec_kv-cache`）を前提とする。すべての計測値は、4 枚の RTX 4090 カード、PyTorch 2.11、JAX 0.12 を備えた 1 台のホスト上で取得したものである。手元のマシンでは実行時間こそ異なるだろうが、FLOPs とバイト数のカウントは変わらず、それらを予測へと変換する方法論も変わらない。

[中心的な問題]{.kicker}

<!--en:83f99cd3-->
- **演算性能（$P$）と帯域幅（$\beta$）：**大規模な $8192^2$ の `bf16` GEMM は $165\text{ TFLOP/s}$ 付近で Tensor Core を飽和させる一方、要素ごとの加算（$I = 0.25$）は $0.25\text{ TFLOP/s}$ で頭打ちになる

<!--en:c1bba8c6-->
- **ホストディスパッチ（$h$）：**Python から Eager カーネルを起動すると演算あたり $10\text{--}100\,\mu\text{s}$ のコストがかかり、マイクロ秒単位の呼び出しの合間に GPU がアイドル状態になる

<!--en:98072254-->
- **メモリ容量（$C$）：**`fp32` の Adam を用いる 1B GPT は、1 トークン分の活性化値を保持する前の時点で $16N \approx 15.1\text{ GiB}$ を消費する（容量 $24\text{ GiB}$ のカード上）

<!--en:d4347d14-->
::: {.slide title="3 つの下限による時間モデルとルーフラインのリッジポイント"}

<!--en:fdea0be7-->
[統一的な解析モデル]{.kicker}

<!--en:37d5a07f-->
- **演算密度（$I = \textrm{FLOPs}/\textrm{bytes}$）：**オフチップ DRAM とオンチップのレジスタ・SRAM 間で移動する 1 バイトあたりに実行される演算数を表す

<!--en:f13f4db5-->
- **リッジポイント（$I^* = P/\beta$）：**帯域幅ルーフ $I\beta$ と計算ルーフ $P$ が交わる点（RTX 4090 の `bf16` では $I^* \approx 164\text{ FLOP/B}$、H100 では $\sim 295$）

<!--en:81da9a50-->
- **マルチ GPU スケーリング：**$k$ 基の GPU に分散すると、集合通信のレイテンシと転送時間 $\alpha + \frac{2(k-1)}{k}S\beta_{\textrm{link}}$ が加わる

<!--en:aa13136d-->
- **ホスト起動（$h$）：**単一演算のディスパッチに $\sim 13\,\mu\text{s}$ のコストがかかる

<!--en:c64da95f-->

<!--en:123f19cf-->
[学習ガイド]{.kicker}

<!--en:e740867f-->
- **常に計測の前に予測する：**ベンチマークのセルを実行する前に、FLOPs、移動バイト数、および予測下限 $\max(h, \textrm{FLOPs}/P, \textrm{bytes}/\beta)$ を書き出すこと。実測値が机上の見積もりと食い違うとき、その乖離から未計上のメモリ転送、隠れたホストバリア、または SM の競合が明らかになる。

<!--en:51ab4ecd-->
- **まず数値的等価性を検証する：**勾配、バッチ正規化の統計量、または因果マスキングを暗黙のうちに変えてしまう最適化は、高速化ではなくバグである。すべての節で、実行時間のベンチマークを 1 ステップの勾配チェック（`allclose`）およびエンドツーエンドの検証損失によるゲートと対にしている。

<!--en:6ba34608-->
**次節（§{sec_perf_model} 性能モデル）：**演算密度を定義し、ルーフライン限界を構築し、非同期計測の落とし穴を回避したうえで、MLP の訓練ステップ全体をプロファイリングする。
